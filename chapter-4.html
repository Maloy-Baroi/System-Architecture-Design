📖 অধ্যায় ৪

অধ্যায় ৪: RDBMS vs NoSQL, Indexing ও Query Optimization

১. অধ্যায় পরিচিতি (Chapter Introduction)

প্রতিটি অ্যাপ্লিকেশনের হৃদয় হলো তার ডাটা। ব্যবহারকারীর তথ্য, অর্ডার, মেসেজ, ছবি — সবকিছু কোথাও না কোথাও সংরক্ষণ করতে হয়। এই সংরক্ষণের জন্য আমরা Database (ডাটাবেস) ব্যবহার করি। কিন্তু কোন ধরনের ডাটাবেস? এই একটি সিদ্ধান্ত আপনার পুরো সিস্টেমের scalability, পারফরম্যান্স ও নির্ভরযোগ্যতা নির্ধারণ করে দিতে পারে।

এই অধ্যায়ে আমরা দুটি প্রধান ডাটাবেস পরিবার — RDBMS (সম্পর্কভিত্তিক ডাটাবেস) ও NoSQL — তুলনা করব। এরপর শিখব কীভাবে ডাটাবেসের গতি বাড়ানো যায় Indexing (ইনডেক্সিং)-এর মাধ্যমে, এবং কীভাবে ধীর query-কে দ্রুত করা যায় (Query Optimization)।

System Design ইন্টারভিউতে "কোন ডাটাবেস বেছে নেবেন এবং কেন?" — এটি প্রায় নিশ্চিত প্রশ্ন। এই অধ্যায় সেই উত্তরের ভিত্তি গড়বে।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • RDBMS কী, এর গঠন এবং ACID বৈশিষ্ট্য
  • NoSQL কী এবং এর চারটি প্রধান ধরন
  • কখন RDBMS, কখন NoSQL বেছে নিতে হয় (ট্রেড-অফসহ)
  • Index কীভাবে query দ্রুত করে এবং এর খরচ
  • Query Optimization-এর মৌলিক কৌশল

৩. মূল ধারণা (Core Concepts)

৩.১ RDBMS (Relational Database Management System)

RDBMS হলো এমন ডাটাবেস যেখানে ডাটা সারি (row) ও কলাম (column)-বিশিষ্ট টেবিল (table)-এ সংরক্ষিত হয় এবং টেবিলগুলোর মধ্যে সম্পর্ক (relationship) থাকে। এর ভাষা SQL (Structured Query Language)।

উদাহরণ: MySQL, PostgreSQL, Oracle, SQL Server।

মূল বৈশিষ্ট্য:
- নির্দিষ্ট Schema (স্কিমা): আগে থেকে টেবিলের গঠন ঠিক করতে হয়।
- সম্পর্ক: Foreign Key দিয়ে টেবিলগুলো যুক্ত (যেমন orders টেবিল users টেবিলের সাথে যুক্ত)।
- ACID গ্যারান্টি — নির্ভরযোগ্য লেনদেনের ভিত্তি।

ACID বৈশিষ্ট্য:
- Atomicity (পরমাণুত্ব): একটি লেনদেন হয় পুরো হয়, নয়তো কিছুই হয় না।
- Consistency (সামঞ্জস্য): লেনদেনের আগে ও পরে ডাটা সবসময় বৈধ অবস্থায় থাকে।
- Isolation (বিচ্ছিন্নতা): একসাথে চলা লেনদেনগুলো একে অপরকে প্রভাবিত করে না।
- Durability (স্থায়িত্ব): একবার commit হলে ডাটা স্থায়ী, এমনকি ক্র্যাশেও হারায় না।

৩.২ NoSQL (Not Only SQL)

NoSQL হলো এমন ডাটাবেস যা সম্পর্কভিত্তিক টেবিল মডেল অনুসরণ করে না। এগুলো বিশাল পরিমাণ ডাটা ও উচ্চ scalability-র জন্য ডিজাইন করা।

NoSQL-এর চারটি প্রধান ধরন:

  1. Document (ডকুমেন্ট): JSON-সদৃশ ডকুমেন্টে ডাটা রাখে। MongoDB, CouchDB। নমনীয় schema।
  2. Key-Value (কী-ভ্যালু): সরল key-value জোড়া। অত্যন্ত দ্রুত। Redis, DynamoDB।
  3. Column-Family (কলাম-ফ্যামিলি): কলাম-ভিত্তিক, বিশাল ডাটার জন্য। Cassandra, HBase।
  4. Graph (গ্রাফ): সম্পর্ক (relationship) কেন্দ্রিক — যেমন সোশ্যাল নেটওয়ার্ক। Neo4j।

মূল বৈশিষ্ট্য:
- নমনীয় Schema (schema-less): আগে থেকে গঠন ঠিক করতে হয় না।
- Horizontal Scaling সহজ: ডাটা সহজে একাধিক মেশিনে ভাগ (shard) করা যায়।
- প্রায়ই BASE মডেল অনুসরণ করে (eventual consistency), কঠোর ACID নয়।

৩.৩ RDBMS vs NoSQL — তুলনা

বৈশিষ্ট্য RDBMS NoSQL
Schema নির্দিষ্ট, কঠোর নমনীয়
Scaling মূলত Vertical সহজ Horizontal
Consistency কঠোর (ACID) প্রায়ই Eventual (BASE)
সম্পর্ক/JOIN শক্তিশালী দুর্বল/নেই
উপযুক্ত যখন জটিল সম্পর্ক, লেনদেন বিশাল স্কেল, নমনীয় ডাটা
উদাহরণ ব্যাংকিং, ই-কমার্স অর্ডার সোশ্যাল ফিড, লগ, ক্যাশ

মূল সূত্র: ডাটার গঠন স্থির ও সম্পর্ক জটিল হলে এবং লেনদেনের সঠিকতা অপরিহার্য হলে → RDBMS। ডাটা বিশাল, নমনীয় এবং প্রচণ্ড scaling দরকার হলে → NoSQL। অনেক বড় সিস্টেমে দুটোই একসাথে ব্যবহৃত হয় (polyglot persistence)।

৩.৪ Indexing (ইনডেক্সিং)

Index হলো একটি ডাটা স্ট্রাকচার যা ডাটাবেসে নির্দিষ্ট তথ্য খুঁজে পাওয়ার গতি বাড়ায় — অনেকটা বইয়ের পেছনের সূচিপত্রের মতো।

Index ছাড়া ডাটাবেসকে পুরো টেবিল স্ক্যান করতে হয় (Full Table Scan) — ১ কোটি সারিতে একটি খুঁজতে ১ কোটি সারি দেখা! Index থাকলে কয়েক ধাপেই খুঁজে পাওয়া যায়।

বেশিরভাগ ডাটাবেস Index-এর জন্য B-Tree (ভারসাম্যপূর্ণ গাছ) ব্যবহার করে, যা log(n) সময়ে অনুসন্ধান করতে পারে।

Index-এর খরচ (Trade-off):
- সুবিধা: read/query অনেক দ্রুত হয়।
- অসুবিধা: write (INSERT/UPDATE/DELETE) ধীর হয় (কারণ Index-ও আপডেট করতে হয়) এবং অতিরিক্ত স্টোরেজ লাগে।

তাই যে কলামে ঘন ঘন অনুসন্ধান হয় (যেমন email, user_id) সেখানেই Index দিন — সব কলামে নয়।

৩.৫ Query Optimization (পরিচিতি)

Query Optimization হলো একটি query-কে দ্রুততম উপায়ে চালানোর প্রক্রিয়া। মৌলিক কৌশল:

  • সঠিক Index ব্যবহার — WHERE/JOIN-এ ব্যবহৃত কলামে Index।
  • SELECT * এড়ানো — শুধু প্রয়োজনীয় কলাম নির্বাচন করুন।
  • EXPLAIN ব্যবহার — query কীভাবে চলছে তা বিশ্লেষণ (Full Scan নাকি Index ব্যবহার হচ্ছে?)।
  • JOIN কমানো ও সঠিক করা — অপ্রয়োজনীয় JOIN ব্যয়বহুল।
  • Pagination — একসাথে লক্ষ সারি না এনে LIMIT/OFFSET ব্যবহার।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনার অ্যাপে users টেবিলে ৫ কোটি ব্যবহারকারী। লগইনের সময় আপনি query করেন:

SELECT * FROM users WHERE email = 'karim@example.com';

email কলামে Index না থাকলে ডাটাবেসকে ৫ কোটি সারি একে একে পরীক্ষা করতে হবে — প্রতিটি লগইনে কয়েক সেকেন্ড! হাজারো ব্যবহারকারী একসাথে লগইন করলে ডাটাবেস ধসে পড়বে।

email-এ Index যোগ করলে একই query মিলিসেকেন্ডে সম্পন্ন হয়। এই একটি সিদ্ধান্ত — Index — আপনার সিস্টেমকে ব্যবহারযোগ্য রাখে। এটিই দেখায় কেন ডাটাবেস জ্ঞান সিস্টেম ডিজাইনে অপরিহার্য।

৫. ভিজ্যুয়াল আর্কিটেকচার ডায়াগ্রাম (Visual Architecture Diagrams)

ডায়াগ্রাম ব্যাখ্যা:
- Components: সিদ্ধান্ত শুরু হয় ডাটার প্রকৃতি বিশ্লেষণ দিয়ে।
- Flow: জটিল সম্পর্ক ও লেনদেন থাকলে RDBMS; বিশাল নমনীয় ডাটা হলে NoSQL; সরল lookup হলে Key-Value।
- বাস্তবতা: এটি কঠোর নিয়ম নয় — অনেক সিস্টেম একাধিক ডাটাবেস একসাথে ব্যবহার করে (polyglot persistence)।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

SQL: টেবিল, Index ও Optimized Query

-- টেবিল তৈরি (RDBMS - নির্দিষ্ট schema)
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255),
    name VARCHAR(100),
    created_at TIMESTAMP
);

-- email কলামে Index (দ্রুত লগইন lookup)
CREATE INDEX idx_users_email ON users(email);

-- খারাপ: সব কলাম আনা
SELECT * FROM users WHERE email = 'karim@example.com';

-- ভালো: শুধু প্রয়োজনীয় কলাম, Index ব্যবহৃত হবে
SELECT id, name FROM users WHERE email = 'karim@example.com';

-- query কীভাবে চলছে তা বিশ্লেষণ
EXPLAIN SELECT id, name FROM users WHERE email = 'karim@example.com';

ব্যাখ্যা: CREATE INDEX email-এ Index তৈরি করে যা lookup দ্রুত করে। SELECT id, name শুধু দরকারি কলাম আনে (কম ডাটা = দ্রুত)। EXPLAIN দেখায় ডাটাবেস Index ব্যবহার করছে নাকি Full Scan করছে।

NoSQL: Document সংরক্ষণ (MongoDB)

// নমনীয় schema — আগে থেকে গঠন ঠিক করতে হয় না
db.users.insertOne({
  _id: 1,
  email: "karim@example.com",
  name: "Karim",
  hobbies: ["cricket", "reading"]   // array সহজে রাখা যায়
});

// email-এ Index তৈরি (NoSQL-এও Index দরকার)
db.users.createIndex({ email: 1 });

// query
db.users.find({ email: "karim@example.com" });

ব্যাখ্যা: MongoDB-তে একটি ডকুমেন্টে array (hobbies)-এর মতো জটিল ডাটা সরাসরি রাখা যায় — RDBMS-এ এর জন্য আলাদা টেবিল লাগত। তবে এখানেও দ্রুত query-র জন্য Index অপরিহার্য।
সীমাবদ্ধতা: নমনীয়তার মূল্য হলো — schema নিয়ন্ত্রণ আপনার অ্যাপ্লিকেশন কোডকেই করতে হয়।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Amazon (DynamoDB): তাদের শপিং কার্টের জন্য নিজস্ব Key-Value NoSQL (DynamoDB) তৈরি করে — উচ্চ availability ও বিশাল scale-এর জন্য, কঠোর consistency-র বদলে।
  • Facebook (Cassandra): Inbox search-এর জন্য Cassandra (Column-Family NoSQL) তৈরি করে বিশাল লেখার পরিমাণ সামলাতে।
  • ব্যাংকিং সিস্টেম: প্রায় সর্বত্র RDBMS (PostgreSQL/Oracle) ব্যবহার করে — কারণ আর্থিক লেনদেনে ACID গ্যারান্টি অপরিহার্য; eventual consistency-তে টাকা হারানো অগ্রহণযোগ্য।
  • Netflix: ভিউয়িং হিস্ট্রি ও বড় ডাটার জন্য Cassandra ব্যবহার করে, যখন কাঠামোগত মেটাডাটার জন্য RDBMS।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- সব কিছুতে SELECT * ব্যবহার করা।
- "NoSQL সবসময় দ্রুত/ভালো" — এই ভুল ধারণা।

Intermediate Mistakes:
- প্রতিটি কলামে Index দেওয়া — যা write ধীর করে ও স্টোরেজ অপচয় করে।
- WHERE/JOIN কলামে Index না দেওয়া।

Production Mistakes:
- আর্থিক/লেনদেন-নির্ভর সিস্টেমে eventual consistency NoSQL ব্যবহার করা।
- Pagination ছাড়া লক্ষ লক্ষ সারি একসাথে আনা।

Scalability Mistakes:
- শুরুতে scaling চাহিদা বিবেচনা না করে ভুল ডাটাবেস নির্বাচন, পরে migration-এ ভোগা।

Architecture Mistakes:
- জটিল সম্পর্কযুক্ত ডাটায় NoSQL ব্যবহার করে অ্যাপ্লিকেশন কোডে কৃত্রিম JOIN লেখা — যা ত্রুটিপ্রবণ।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: SQL আর NoSQL-এর মূল পার্থক্য কী?

SQL/RDBMS নির্দিষ্ট schema ও সম্পর্কভিত্তিক টেবিল ব্যবহার করে ও ACID দেয়; NoSQL নমনীয় schema ও সহজ horizontal scaling দেয়, প্রায়ই eventual consistency-তে।

Intermediate প্রশ্ন: Index query দ্রুত করলে আমরা কেন সব কলামে Index দিই না?

কারণ প্রতিটি Index write (INSERT/UPDATE/DELETE) ধীর করে এবং অতিরিক্ত স্টোরেজ নেয়। তাই শুধু ঘন ঘন অনুসন্ধান হওয়া কলামেই Index দেওয়া হয়।

Advanced প্রশ্ন: ACID-এর "Isolation" বলতে কী বোঝায়?

একসাথে চলা একাধিক লেনদেন এমনভাবে চলবে যেন তারা একে অপরের ফলাফল মাঝপথে দেখতে না পায় — ফলে কোনো লেনদেন অন্যটির অসম্পূর্ণ অবস্থা পড়ে ভুল করে না।

System Design প্রশ্ন: একটি সোশ্যাল মিডিয়া নিউজ ফিডের জন্য কোন ডাটাবেস বেছে নেবেন?

নমনীয়তা ও বিশাল read scale-এর জন্য NoSQL (যেমন Cassandra বা document store) উপযুক্ত হতে পারে ফিড স্টোর করতে, যখন ব্যবহারকারীর অ্যাকাউন্ট ও সম্পর্কের জন্য RDBMS বা Graph DB। অর্থাৎ polyglot — একাধিক ডাটাবেসের সমন্বয়।

১০. সেরা চর্চা (Best Practices)

  • ডাটা ও চাহিদা বুঝে ডাটাবেস নির্বাচন করুন — ট্রেন্ড দেখে নয়।
  • WHERE/JOIN/ORDER BY কলামে Index দিন, কিন্তু অতিরিক্ত Index এড়ান।
  • SELECT * এড়িয়ে শুধু প্রয়োজনীয় কলাম নিন।
  • EXPLAIN দিয়ে query বিশ্লেষণ করুন নিয়মিত।
  • আর্থিক/লেনদেনে ACID (RDBMS) নিশ্চিত করুন।
  • Pagination ব্যবহার করুন বড় ফলাফলে।
  • প্রয়োজনে polyglot persistence — সঠিক কাজে সঠিক ডাটাবেস।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- RDBMS = নির্দিষ্ট schema, সম্পর্ক, ACID; জটিল লেনদেনের জন্য আদর্শ।
- NoSQL = নমনীয় schema, সহজ horizontal scaling; চার ধরন (Document, Key-Value, Column-Family, Graph)।
- ACID = Atomicity, Consistency, Isolation, Durability।
- Index = অনুসন্ধান দ্রুত করে (B-Tree), কিন্তু write ধীর করে ও স্টোরেজ নেয়।
- Query Optimization = সঠিক Index, SELECT * এড়ানো, EXPLAIN, pagination।

গুরুত্বপূর্ণ পরিভাষা: RDBMS, SQL, NoSQL, ACID, BASE, Schema, Index, B-Tree, Full Table Scan, Eventual Consistency, Polyglot Persistence, Sharding।

Conceptual:

Practical:
3. একটি orders টেবিলে customer_id দিয়ে ঘন ঘন query হয়। উপযুক্ত Index তৈরির SQL লিখুন।
4. SELECT * FROM products WHERE category = 'books' query-টিকে optimize করুন।

Architecture Design:

Scenario-Based:

Interview Challenge:
