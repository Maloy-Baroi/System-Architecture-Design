অধ্যায় ১: সিস্টেম ডিজাইনের ভিত্তি

১. অধ্যায় পরিচিতি (Chapter Introduction)

আপনি যখন কোনো অ্যাপ ব্যবহার করেন — হোক সেটা WhatsApp-এ মেসেজ পাঠানো, Facebook-এ স্ক্রল করা, কিংবা Amazon-এ অর্ডার দেওয়া — তখন পর্দার আড়ালে হাজার হাজার সার্ভার, ডাটাবেস, এবং নেটওয়ার্ক একসাথে কাজ করে। এই পুরো ব্যবস্থাটি কীভাবে সাজানো হবে, কোন অংশ কোথায় বসবে, কীভাবে একে অপরের সাথে কথা বলবে — এই সিদ্ধান্তগুলো নেওয়াই হলো সিস্টেম ডিজাইন (System Design)।

একজন ডেভেলপার কোড লেখেন, কিন্তু একজন আর্কিটেক্ট (Architect) ঠিক করেন কোডটি কোন কাঠামোর ওপর দাঁড়াবে। ছোট অ্যাপ চালানো সহজ, কিন্তু যখন ১০ জন ব্যবহারকারী থেকে ১০ কোটি ব্যবহারকারীতে পৌঁছায় — তখন ভুল আর্কিটেকচার পুরো ব্যবসাকে ধসিয়ে দিতে পারে। তাই সিস্টেম ডিজাইন শুধু একটি প্রযুক্তিগত দক্ষতা নয়, এটি একটি প্রকৌশলগত শিল্প।

এই অধ্যায়ে আমরা সিস্টেম ডিজাইনের একদম মৌলিক ভিত্তি স্থাপন করব, যার ওপর পুরো বইটি গড়ে উঠবে।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • সিস্টেম ডিজাইন আসলে কী এবং কেন এটি গুরুত্বপূর্ণ
  • Functional ও Non-functional Requirements-এর পার্থক্য
  • Monolith (একক স্থাপত্য) আর্কিটেকচার কী এবং কখন উপযুক্ত
  • Microservices (মাইক্রোসার্ভিসেস) আর্কিটেকচার কী এবং এর ট্রেড-অফ
  • কোন পরিস্থিতিতে কোনটি বেছে নিতে হয়

৩. মূল ধারণা (Core Concepts)

৩.১ সিস্টেম ডিজাইন কী?

সিস্টেম ডিজাইন (System Design) হলো একটি সফটওয়্যার সিস্টেমের আর্কিটেকচার, কম্পোনেন্ট, মডিউল, ইন্টারফেস এবং ডাটা প্রবাহ সংজ্ঞায়িত করার প্রক্রিয়া, যাতে নির্দিষ্ট ব্যবসায়িক ও কারিগরি প্রয়োজন পূরণ হয়।

সহজভাবে বললে — একটি বাড়ি বানানোর আগে যেমন একজন স্থপতি (architect) নকশা আঁকেন (কোথায় ঘর, কোথায় বাথরুম, পানি-বিদ্যুতের লাইন কীভাবে যাবে), তেমনি সফটওয়্যার বানানোর আগে একজন সফটওয়্যার আর্কিটেক্ট সিদ্ধান্ত নেন:

  • কতগুলো সার্ভার লাগবে
  • কোন ডাটাবেস ব্যবহার হবে
  • ডাটা কীভাবে সংরক্ষণ ও প্রবাহিত হবে
  • লোড বেড়ে গেলে সিস্টেম কীভাবে বড় হবে (scale করবে)

৩.২ সিস্টেম ডিজাইনের দুই স্তর

  1. High-Level Design (HLD) — পুরো সিস্টেমের বড় ছবি। কোন কম্পোনেন্ট কোথায়, কীভাবে যুক্ত — যেমন লোড ব্যালেন্সার, সার্ভার, ক্যাশ, ডাটাবেস।
  2. Low-Level Design (LLD) — নির্দিষ্ট মডিউলের ভেতরের বিস্তারিত। ক্লাস, ফাংশন, ডাটা স্ট্রাকচার, API-এর গঠন।

৩.৩ Functional vs Non-functional Requirements

যেকোনো সিস্টেম ডিজাইনের প্রথম ধাপ হলো প্রয়োজনীয়তা (requirements) বোঝা। এগুলো দুই ধরনের।

Functional Requirements (কার্যগত প্রয়োজনীয়তা):
সিস্টেম কী করবে — তার আচরণ ও ফিচার। এগুলো ব্যবহারকারীর দৃশ্যমান কাজ।

উদাহরণ (একটি মেসেজিং অ্যাপের জন্য):
- ব্যবহারকারী মেসেজ পাঠাতে ও গ্রহণ করতে পারবে
- ব্যবহারকারী গ্রুপ তৈরি করতে পারবে
- ছবি/ভিডিও শেয়ার করা যাবে

Non-functional Requirements (অকার্যগত প্রয়োজনীয়তা):
সিস্টেম কতটা ভালোভাবে কাজ করবে — তার গুণমান। এগুলো সরাসরি ফিচার নয়, কিন্তু এগুলোই সিস্টেমের সাফল্য নির্ধারণ করে।

উদাহরণ:
- Scalability (স্কেলেবিলিটি) — কোটি ব্যবহারকারী সামলাতে পারা
- Availability (অ্যাভেইলেবিলিটি) — ২৪/৭ চালু থাকা
- Latency (লেটেন্সি) — মেসেজ ১০০ মিলিসেকেন্ডের মধ্যে পৌঁছানো
- Reliability (রিলায়েবিলিটি) — মেসেজ যেন হারিয়ে না যায়
- Security (সিকিউরিটি) — এন্ড-টু-এন্ড এনক্রিপশন

মনে রাখার সূত্র: Functional = "কী করে", Non-functional = "কেমনভাবে করে"। ইন্টারভিউতে বেশিরভাগ প্রার্থী functional নিয়েই আটকে থাকে, কিন্তু সিনিয়র আর্কিটেক্টরা non-functional-এ বেশি জোর দেন — কারণ এখানেই আসল চ্যালেঞ্জ।

৩.৪ Monolith vs Microservices

এটি আধুনিক আর্কিটেকচারের সবচেয়ে মৌলিক সিদ্ধান্ত।

Monolithic Architecture (মনোলিথিক / একক স্থাপত্য):
পুরো অ্যাপ্লিকেশনটি একটি একক, অখণ্ড কোডবেস ও ডিপ্লয়মেন্ট ইউনিট হিসেবে তৈরি হয়। User management, payment, notification — সব এক জায়গায়।

Microservices Architecture (মাইক্রোসার্ভিসেস):
অ্যাপ্লিকেশনটিকে ছোট ছোট স্বাধীন সার্ভিসে ভাগ করা হয়। প্রতিটি সার্ভিস একটি নির্দিষ্ট ব্যবসায়িক কাজ করে, নিজস্ব ডাটাবেস রাখে, এবং আলাদাভাবে ডিপ্লয় হয়।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনি একটি ই-কমার্স স্টার্টআপ শুরু করলেন। প্রথমে ৫ জন ডেভেলপার, ১০০ জন গ্রাহক। আপনি সব কোড একটি মনোলিথে রাখলেন — দ্রুত, সহজ, কাজ চলছে।

দুই বছর পর: ৫০ জন ডেভেলপার, ১০ লক্ষ গ্রাহক। এখন সমস্যা শুরু:

  • একটি ছোট বাগ ফিক্স করতে পুরো অ্যাপ আবার ডিপ্লয় করতে হয়
  • Payment টিম আর Search টিম একই কোডবেসে কাজ করতে গিয়ে দ্বন্দ্বে জড়ায়
  • Black Friday-তে শুধু "checkout" অংশে লোড বাড়ে, কিন্তু আপনাকে পুরো অ্যাপ scale করতে হয় — যা ব্যয়বহুল

এই সমস্যাগুলোই মাইক্রোসার্ভিসের জন্ম দেয়। কিন্তু মাইক্রোসার্ভিস নিজেও নতুন জটিলতা আনে — তাই সিদ্ধান্তটি কখনোই অন্ধভাবে নেওয়া যায় না।

ডায়াগ্রাম ব্যাখ্যা:

  • Components: মনোলিথে সব মডিউল একটি ইউনিটে; মাইক্রোসার্ভিসে প্রতিটি সার্ভিস স্বাধীন এবং নিজস্ব ডাটাবেসসহ।
  • Request Flow: মাইক্রোসার্ভিসে অনুরোধ প্রথমে API Gateway (এপিআই গেটওয়ে)-তে আসে, যা সঠিক সার্ভিসে রুট করে।
  • Failure Points: মনোলিথে একটি মডিউল ক্র্যাশ করলে পুরো অ্যাপ পড়ে যেতে পারে (single point of failure)। মাইক্রোসার্ভিসে একটি সার্ভিস ব্যর্থ হলেও বাকিগুলো চলতে পারে।
  • Scaling: মনোলিথে পুরো অ্যাপ একসাথে scale করতে হয়; মাইক্রোসার্ভিসে শুধু চাপগ্রস্ত সার্ভিসটি (যেমন Payment) আলাদাভাবে scale করা যায়।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

মনোলিথে সব রুট একই অ্যাপ্লিকেশনে (Node.js উদাহরণ):

// monolith-app.js — সব ফিচার এক জায়গায়
const express = require('express');
const app = express();

// User module
app.get('/users/:id', (req, res) => {
  res.json({ id: req.params.id, name: 'Rahim' });
});

// Order module — একই অ্যাপ্লিকেশন, একই প্রসেস
app.post('/orders', (req, res) => {
  res.json({ orderId: 101, status: 'created' });
});

app.listen(3000); // একটিই ডিপ্লয়মেন্ট ইউনিট

মাইক্রোসার্ভিসে User Service আলাদা একটি স্বাধীন সার্ভিস:

// user-service.js — শুধু user নিয়ে কাজ, নিজস্ব পোর্ট, নিজস্ব ডিপ্লয়
const express = require('express');
const app = express();

app.get('/users/:id', (req, res) => {
  res.json({ id: req.params.id, name: 'Rahim' });
});

app.listen(4001); // আলাদাভাবে scale ও ডিপ্লয় করা যায়

ব্যাখ্যা: প্রথম উদাহরণে user ও order একই প্রসেসে চলে — একটি পরিবর্তন মানেই পুরোটা পুনরায় ডিপ্লয়। দ্বিতীয় উদাহরণে User Service স্বাধীন, ফলে Order টিমকে বিরক্ত না করেই এটি আপডেট ও scale করা যায়। সীমাবদ্ধতা: এখন সার্ভিসগুলোকে নেটওয়ার্কের মাধ্যমে কথা বলতে হয়, যা নতুন জটিলতা (latency, failure handling) যোগ করে।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Amazon: শুরুতে একটি বিশাল মনোলিথ ছিল। ২০০১-এর দিকে ডেভেলপমেন্ট গতি কমে যাওয়ায় তারা মাইক্রোসার্ভিসে রূপান্তরিত হয় — এটিই আধুনিক মাইক্রোসার্ভিস আন্দোলনের অন্যতম জনক।
  • Netflix: ২০০৮-এ একটি বড় ডাটাবেস ব্যর্থতার পর তারা সম্পূর্ণভাবে ক্লাউড-ভিত্তিক মাইক্রোসার্ভিসে স্থানান্তরিত হয়; বর্তমানে শত শত সার্ভিস চালায়।
  • Uber: শুরুতে মনোলিথ ছিল, পরে দ্রুত বৃদ্ধির কারণে হাজারো মাইক্রোসার্ভিসে ভাগ হয়।
  • শিক্ষণীয়: প্রায় সব বড় কোম্পানিই মনোলিথ দিয়ে শুরু করে, তারপর প্রয়োজন অনুযায়ী মাইক্রোসার্ভিসে যায়। শুরু থেকেই মাইক্রোসার্ভিস করা সাধারণত ভুল সিদ্ধান্ত।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- Functional আর Non-functional requirement গুলিয়ে ফেলা
- requirement না বুঝেই কোডিং শুরু করা

Intermediate Mistakes:
- ছোট প্রজেক্টে অপ্রয়োজনে মাইক্রোসার্ভিস ব্যবহার করা ("over-engineering")

Production Mistakes:
- মাইক্রোসার্ভিসে সার্ভিসগুলোর মধ্যে সঠিক ব্যর্থতা সামলানোর ব্যবস্থা না রাখা

Scalability Mistakes:
- Non-functional requirement (scalability, latency) আগে থেকে বিবেচনা না করা

Architecture Mistakes:
- ভুলভাবে সার্ভিস ভাগ করা — যেমন একটি কাজ করতে ৫টি সার্ভিসে কল করা লাগে (distributed monolith নামক anti-pattern)

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: সিস্টেম ডিজাইন কী?

সফটওয়্যার সিস্টেমের আর্কিটেকচার, কম্পোনেন্ট ও ডাটা প্রবাহ সংজ্ঞায়িত করার প্রক্রিয়া, যা নির্দিষ্ট কার্যগত ও অকার্যগত প্রয়োজন পূরণ করে।

Intermediate প্রশ্ন: Functional ও Non-functional requirement-এর পার্থক্য কী?

Functional বলে সিস্টেম কী করবে (ফিচার), Non-functional বলে কতটা ভালোভাবে করবে (scalability, availability, latency ইত্যাদি)।

Advanced প্রশ্ন: Monolith থেকে Microservices-এ কখন যাবেন?

যখন টিম বড় হয়, স্বাধীন ডিপ্লয়মেন্ট দরকার হয়, এবং নির্দিষ্ট অংশ আলাদাভাবে scale করার প্রয়োজন পড়ে। শুধু "ট্রেন্ড" বলে নয়।

System Design প্রশ্ন: একটি URL shortener-এর জন্য আপনি কোন আর্কিটেকচার বেছে নেবেন?

প্রথমে requirement স্পষ্ট করুন (functional: লিংক ছোট করা ও redirect; non-functional: উচ্চ availability, কম latency)। প্রাথমিকভাবে একটি সরল মনোলিথই যথেষ্ট, কারণ লজিক সরল — অপ্রয়োজনে মাইক্রোসার্ভিস এড়ানোই বুদ্ধিমানের কাজ।

১০. সেরা চর্চা (Best Practices)

  • আগে requirement, পরে আর্কিটেকচার — কোড লেখার আগে functional ও non-functional উভয়ই স্পষ্ট করুন।
  • মনোলিথ দিয়ে শুরু করুন (well-structured monolith), প্রয়োজন হলে পরে ভাঙুন।
  • জটিলতা যোগ করার আগে কারণ থাকতে হবে — প্রতিটি সার্ভিসের অস্তিত্বের যুক্তি থাকা চাই।
  • Non-functional requirement (security, reliability) শুরু থেকেই বিবেচনায় রাখুন, পরে যোগ করা কঠিন।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- সিস্টেম ডিজাইন = আর্কিটেকচার, কম্পোনেন্ট ও ডাটা প্রবাহ সংজ্ঞায়িত করা।
- Functional = সিস্টেম কী করে; Non-functional = কতটা ভালোভাবে করে।
- Monolith = এক অখণ্ড ইউনিট — সহজ, দ্রুত, কিন্তু বড় হলে scale ও maintain করা কঠিন।
- Microservices = স্বাধীন ছোট সার্ভিস — নমনীয় ও স্বাধীনভাবে scalable, কিন্তু জটিল।
- প্রায় সব বড় কোম্পানি মনোলিথ দিয়ে শুরু করে।

গুরুত্বপূর্ণ পরিভাষা: HLD, LLD, Scalability, Availability, Latency, API Gateway, Single Point of Failure, Distributed Monolith.
