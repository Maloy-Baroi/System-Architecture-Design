অধ্যায় ৬: CDN এবং Object, Block ও File Storage

১. অধ্যায় পরিচিতি (Chapter Introduction)

আগের অধ্যায়ে আমরা শিখেছি কীভাবে caching ডাটাবেসের লোড কমায়। কিন্তু একটি সমস্যা থেকে যায় — ভূগোল (geography)। আপনার সার্ভার যদি ঢাকায় থাকে, তবে নিউইয়র্কের ব্যবহারকারীর প্রতিটি অনুরোধকে অর্ধেক পৃথিবী পাড়ি দিতে হয়। আলোর গতিরও একটি সীমা আছে — এই দূরত্ব মানেই অনিবার্য latency। একটি ছবি বা ভিডিও যদি প্রতিবার এত দূর থেকে আনতে হয়, ব্যবহারকারীর অভিজ্ঞতা ধীর হয়ে যায়।

এর সমাধান হলো CDN (Content Delivery Network) — ব্যবহারকারীর কাছাকাছি কনটেন্ট রেখে দেওয়া। এই অধ্যায়ের প্রথম অংশে আমরা CDN-এর গভীরে যাব।

দ্বিতীয় অংশে আমরা শিখব ডাটা কোথায় ও কীভাবে সংরক্ষণ করা হয় — কারণ ফাইল, ছবি, ভিডিও, ব্যাকআপ — এগুলো ডাটাবেসে রাখা হয় না। তিন ধরনের স্টোরেজ আছে: Object Storage, Block Storage, ও File Storage। প্রতিটির আলাদা ব্যবহার, সুবিধা ও ট্রেড-অফ আছে। ক্লাউড আর্কিটেকচারে কোন স্টোরেজ কোথায় ব্যবহার করবেন — এই জ্ঞান অপরিহার্য।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • CDN কী, কেন দরকার, এবং ভেতরে কীভাবে কাজ করে
  • Edge Server, PoP (Point of Presence), Origin Server-এর ধারণা
  • Push CDN ও Pull CDN-এর পার্থক্য
  • Edge-এ caching, TTL, Cache-Control, এবং Cache Purge/Invalidation
  • CDN-এর নিরাপত্তা ভূমিকা (TLS, DDoS, WAF)
  • Object, Block, ও File Storage — গঠন, পার্থক্য ও ব্যবহার
  • কোন পরিস্থিতিতে কোন স্টোরেজ বেছে নিতে হয়

৩. মূল ধারণা (Core Concepts)

অংশ ক: CDN (Content Delivery Network)

৩.১ CDN কী?

CDN (Content Delivery Network) হলো বিশ্বজুড়ে ছড়িয়ে থাকা সার্ভারের একটি নেটওয়ার্ক, যা ব্যবহারকারীর ভৌগোলিকভাবে কাছাকাছি অবস্থান থেকে কনটেন্ট (বিশেষত স্ট্যাটিক ফাইল — ছবি, ভিডিও, CSS, JS) পরিবেশন করে। লক্ষ্য — latency কমানো, গতি বাড়ানো, এবং মূল সার্ভারের (origin) লোড কমানো।

মূল ধারণা সহজ: কনটেন্টকে ব্যবহারকারীর কাছে নিয়ে আসো, ব্যবহারকারীকে দূরের সার্ভারে পাঠিও না।

৩.২ CDN-এর মূল উপাদান

  • Origin Server (অরিজিন সার্ভার): আপনার মূল সার্ভার যেখানে কনটেন্টের আসল উৎস (source of truth) থাকে।
  • Edge Server (এজ সার্ভার): ব্যবহারকারীর কাছাকাছি অবস্থিত CDN সার্ভার, যা কনটেন্টের অনুলিপি (cached copy) রাখে এবং পরিবেশন করে।
  • PoP (Point of Presence): একটি ভৌগোলিক অবস্থান (যেমন ঢাকা, সিঙ্গাপুর, লন্ডন) যেখানে একাধিক edge server থাকে। বিশ্বজুড়ে শত শত PoP থাকে।
  • Origin Shield: একটি অতিরিক্ত মধ্যবর্তী caching স্তর, যা origin-কে অনেক edge-এর সরাসরি অনুরোধ থেকে রক্ষা করে (একটিমাত্র shield origin-এ যায়, বহু edge নয়)।

৩.৩ CDN কীভাবে কাজ করে (Request Flow)

  1. ব্যবহারকারী একটি ফাইল চায় (যেমন image.jpg)।
  2. DNS / Anycast Routing ব্যবহারকারীকে সবচেয়ে কাছের PoP-এ পাঠায়।
  3. Edge server দেখে কনটেন্ট তার কাছে আছে কি না —
    - Edge Cache Hit: আছে → সরাসরি ব্যবহারকারীকে দেয় (অত্যন্ত দ্রুত)।
    - Edge Cache Miss: নেই → origin (বা origin shield) থেকে আনে, edge-এ ক্যাশ করে রাখে, তারপর ব্যবহারকারীকে দেয়। পরের ব্যবহারকারী আর miss পাবে না।

Anycast: একই IP ঠিকানা বহু সার্ভারে বরাদ্দ; নেটওয়ার্ক রাউটিং স্বয়ংক্রিয়ভাবে নিকটতম সার্ভারে অনুরোধ পাঠায়। এটিই CDN-এর "কাছের সার্ভার খুঁজে দেওয়ার" মূল কৌশল।

৩.৪ Push CDN vs Pull CDN

CDN-এ কনটেন্ট কীভাবে পৌঁছায়, তার দুটি মডেল:

Pull CDN (সবচেয়ে প্রচলিত):
কনটেন্ট edge-এ থাকে না; প্রথম ব্যবহারকারী চাইলে (cache miss) CDN নিজে origin থেকে "টেনে আনে" (pull) ও ক্যাশ করে।
- সুবিধা: কম রক্ষণাবেক্ষণ; শুধু চাহিদা অনুযায়ী কনটেন্ট ক্যাশ হয়; স্টোরেজ সাশ্রয়ী।
- অসুবিধা: প্রথম অনুরোধে miss (ধীর); জনপ্রিয় নয় এমন কনটেন্টে বারবার origin হিট।
- ব্যবহার: সাধারণ ওয়েবসাইট, যেখানে কনটেন্ট প্রায়ই বদলায় বা বিশাল।

Push CDN:
আপনি আগে থেকেই কনটেন্ট edge সার্ভারে "ঠেলে দেন" (push/upload)। ব্যবহারকারী আসার আগেই কনটেন্ট সেখানে থাকে।
- সুবিধা: কখনো প্রথম-অনুরোধ miss নেই; বড় ফাইল (যেমন সফটওয়্যার রিলিজ, ভিডিও) আগাম বিতরণে আদর্শ।
- অসুবিধা: আপনাকেই কনটেন্ট আপলোড ও আপডেট পরিচালনা করতে হয়; বেশি স্টোরেজ খরচ।
- ব্যবহার: কম-পরিবর্তনশীল, বড়, পূর্বানুমেয় জনপ্রিয় কনটেন্ট।

৩.৫ Edge Caching: TTL, Cache-Control ও Purge

  • TTL (Time To Live): edge-এ কনটেন্ট কতক্ষণ ক্যাশ থাকবে। মেয়াদ শেষে edge আবার origin থেকে যাচাই/আনয় করে।
  • Cache-Control Headers: origin HTTP header দিয়ে CDN-কে নির্দেশ দেয় — Cache-Control: max-age=3600 (১ ঘণ্টা ক্যাশ), no-cache, private ইত্যাদি।
  • ETag / Last-Modified: edge origin-কে জিজ্ঞেস করে "কনটেন্ট কি বদলেছে?"; না বদলালে origin 304 Not Modified দেয় (ব্যান্ডউইথ সাশ্রয়)।
  • Cache Purge / Invalidation: কনটেন্ট আপডেট হলে পুরোনো edge-ক্যাশ সরাতে হয় —
  • Purge by URL: নির্দিষ্ট ফাইল মুছে ফেলা।
  • Purge by Tag/Wildcard: একদল কনটেন্ট একসাথে মুছে ফেলা।
  • Cache Busting (versioned URL): ফাইলের নামে version দেওয়া (style.v2.css বা style.css?v=2) — নতুন নাম মানে নতুন ক্যাশ; purge-এর প্রয়োজন নেই। এটিই সবচেয়ে নিরাপদ কৌশল।

৩.৬ Static vs Dynamic Content

  • Static Content: সব ব্যবহারকারীর জন্য একই (ছবি, ভিডিও, CSS, JS, ফন্ট) — CDN ক্যাশিংয়ের জন্য আদর্শ।
  • Dynamic Content: প্রতি ব্যবহারকারী/অনুরোধে ভিন্ন (ব্যক্তিগত ড্যাশবোর্ড, API উত্তর) — সরাসরি ক্যাশ করা কঠিন। আধুনিক CDN এর জন্য Dynamic Content Acceleration (অপ্টিমাইজড রাউটিং, persistent connection) এবং Edge Computing (edge-এ কোড চালানো, যেমন Cloudflare Workers) ব্যবহার করে।

৩.৭ CDN-এর নিরাপত্তা ও অন্যান্য সুবিধা

CDN শুধু গতি নয়, নিরাপত্তা ও নির্ভরযোগ্যতাও দেয়:
- DDoS Protection: বিশাল distributed নেটওয়ার্ক আক্রমণ শোষণ করে origin রক্ষা করে।
- TLS/SSL Termination: edge-এ এনক্রিপশন সামলানো হয় — origin-এর কাজ কমে।
- WAF (Web Application Firewall): ক্ষতিকর অনুরোধ edge-এই ফিল্টার করা।
- Bandwidth Offload: বেশিরভাগ ট্র্যাফিক edge সামলায়, তাই origin-এর ব্যান্ডউইথ ও খরচ কমে।
- High Availability: একটি PoP ডাউন হলে অন্য PoP কাজ চালিয়ে নেয়।

জনপ্রিয় CDN: Cloudflare, Akamai, Amazon CloudFront, Fastly, Google Cloud CDN।

অংশ খ: Storage Types (স্টোরেজের ধরন)

ক্লাউডে ডাটা তিনভাবে সংরক্ষণ করা যায়। প্রতিটির ভিন্ন বিমূর্ততা (abstraction) ও ব্যবহার আছে।

৩.৮ Object Storage (অবজেক্ট স্টোরেজ)

Object Storage হলো এমন স্টোরেজ যেখানে ডাটা "object" হিসেবে রাখা হয় — প্রতিটি object-এ থাকে: ডাটা (file) + Metadata (মেটাডাটা) + একটি অনন্য ID (key)। কোনো ফোল্ডার-শ্রেণিবিন্যাস (hierarchy) নেই — একটি সমতল (flat) namespace, যেখানে object গুলো "bucket"-এ থাকে।

উদাহরণ: Amazon S3, Google Cloud Storage, Azure Blob Storage।

বৈশিষ্ট্য:
- REST API-ভিত্তিক: HTTP (GET/PUT) দিয়ে অ্যাক্সেস — ফাইল সিস্টেম mount করতে হয় না।
- প্রায় অসীম scalability: পেটাবাইট পর্যন্ত সহজে বাড়ে।
- উচ্চ Durability (স্থায়িত্ব): ডাটা একাধিক স্থানে প্রতিলিপি (replicated); S3 প্রায় "eleven nines" (99.999999999%) durability দাবি করে।
- Metadata সমৃদ্ধ: প্রতিটি object-এ কাস্টম মেটাডাটা যুক্ত করা যায়।
- সাধারণত immutable-ish: object সম্পূর্ণ প্রতিস্থাপন হয়, আংশিক edit সাধারণত নয়।
- দুর্বলতা: ফাইলের ভেতরের ছোট অংশ দ্রুত edit করার জন্য নয়; latency block storage-এর চেয়ে বেশি।

ব্যবহার: ছবি/ভিডিও, ব্যাকআপ, লগ, স্ট্যাটিক ওয়েবসাইট হোস্টিং, big data ও data lake, CDN-এর origin।

৩.৯ Block Storage (ব্লক স্টোরেজ)

Block Storage হলো এমন স্টোরেজ যেখানে ডাটা সমান আকারের "block"-এ ভাগ করে রাখা হয়, এবং এটি একটি কম্পিউটার/সার্ভারে একটি কাঁচা (raw) ভার্চুয়াল হার্ডডিস্কের মতো যুক্ত (attach) হয়। অপারেটিং সিস্টেম এর ওপর ফাইল সিস্টেম তৈরি করে।

উদাহরণ: Amazon EBS (Elastic Block Store), Google Persistent Disk, SAN।

বৈশিষ্ট্য:
- অত্যন্ত কম latency ও উচ্চ IOPS: দ্রুত random read/write।
- আংশিক পরিবর্তন সহজ: ফাইলের নির্দিষ্ট অংশ দ্রুত আপডেট করা যায় (database-এর জন্য আদর্শ)।
- সাধারণত একটিমাত্র instance-এ attach হয় (এক সময়ে এক সার্ভার)।
- দুর্বলতা: object storage-এর মতো সহজে বিশাল scale বা শেয়ার করা যায় না; খরচ বেশি।

ব্যবহার: ডাটাবেস (MySQL, PostgreSQL), boot volume (OS ডিস্ক), transaction-ভারী অ্যাপ্লিকেশন, যেখানে দ্রুত random access দরকার।

৩.১০ File Storage (ফাইল স্টোরেজ)

File Storage হলো ঐতিহ্যবাহী শ্রেণিবদ্ধ (hierarchical) ফাইল সিস্টেম — ফোল্ডার ও সাব-ফোল্ডারে ফাইল সাজানো, এবং নেটওয়ার্কের মাধ্যমে একাধিক সার্ভার একসাথে এটি শেয়ার ও mount করতে পারে।

উদাহরণ: Amazon EFS, Google Filestore, NFS, SMB/CIFS।

বৈশিষ্ট্য:
- শ্রেণিবদ্ধ গঠন: পরিচিত ফোল্ডার/পাথ (/home/user/docs/file.txt)।
- শেয়ারড অ্যাক্সেস: একাধিক সার্ভার একসাথে পড়া/লেখা করতে পারে (POSIX-সম্মত)।
- সহজ ব্যবহার: অ্যাপ্লিকেশন একে সাধারণ ফাইল সিস্টেমের মতোই দেখে।
- দুর্বলতা: object storage-এর মতো অসীম scale নয়; বিশাল হলে খরচ ও জটিলতা বাড়ে।

ব্যবহার: শেয়ারড ফাইল (টিমের নথি), legacy অ্যাপ্লিকেশন যা ফাইল সিস্টেম আশা করে, content management, একাধিক সার্ভারের মধ্যে শেয়ারড ডাটা।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনি একটি ভিডিও স্ট্রিমিং প্ল্যাটফর্ম বানাচ্ছেন (যেমন একটি ছোট YouTube)। সমস্যা দুটি:

সমস্যা ১ — স্টোরেজ: লক্ষ লক্ষ ভিডিও ফাইল কোথায় রাখবেন? ডাটাবেসে? — কখনো না। ভিডিও বিশাল, immutable, এবং URL দিয়ে অ্যাক্সেস করতে হয়। সমাধান: Object Storage (S3)। ভিডিও মেটাডাটা (শিরোনাম, ভিউ) ডাটাবেসে, কিন্তু আসল ফাইল object storage-এ।

সমস্যা ২ — বিতরণ: ভারতের একজন ব্যবহারকারী যদি প্রতিবার USA-র সার্ভার থেকে ভিডিও আনে, তবে buffering হবে, খরচ বাড়বে, origin চাপে পড়বে। সমাধান: CDN। ভিডিও edge সার্ভারে ক্যাশ হয়; ভারতের ব্যবহারকারী ভারতের PoP থেকেই পায় — দ্রুত, সস্তা, মসৃণ।

এই দুই প্রযুক্তি একসাথে ব্যবহার করেই Netflix, YouTube-এর মতো প্ল্যাটফর্ম বিশ্বজুড়ে কাজ করে। CDN বা সঠিক স্টোরেজ ছাড়া এই স্কেল অসম্ভব।

ডায়াগ্রাম ব্যাখ্যা:
- Components: ব্যবহারকারী → নিকটতম PoP/Edge → (miss হলে) Origin Shield → Origin।
- Request Flow: Edge-এ hit হলে সরাসরি দ্রুত পরিবেশন; miss হলে origin থেকে এনে edge-এ ক্যাশ করে ফেরত।
- Failure Points: একটি PoP ডাউন হলে রাউটিং অন্য PoP-এ যায়; Origin Shield origin-কে বিপুল edge অনুরোধ থেকে রক্ষা করে।
- Scaling: বেশিরভাগ ট্র্যাফিক edge সামলায়, তাই origin সামান্য লোডেই বিশ্বজুড়ে কোটি ব্যবহারকারীকে সেবা দিতে পারে।

ব্যাখ্যা: ডাটার প্রকৃতি অনুযায়ী নির্বাচন — মিডিয়া/ব্যাকআপ → Object; database/OS → Block; শেয়ারড ফোল্ডার → File। বড় সিস্টেমে তিনটিই একসাথে ব্যবহৃত হতে পারে।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

Object Storage-এ আপলোড (Python + AWS S3)

import boto3

s3 = boto3.client('s3')

# একটি ফাইল object হিসেবে আপলোড
s3.upload_file(
    Filename='video.mp4',          # লোকাল ফাইল
    Bucket='my-video-bucket',      # bucket (flat namespace)
    Key='videos/2024/video.mp4'    # object key (এটি "ফোল্ডার" নয়, শুধু নাম)
)

# পাবলিক/প্রি-সাইনড URL তৈরি (অস্থায়ী অ্যাক্সেস)
url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-video-bucket', 'Key': 'videos/2024/video.mp4'},
    ExpiresIn=3600                 # ১ ঘণ্টা বৈধ
)
print(url)

ব্যাখ্যা:
- upload_file ফাইলটিকে একটি object হিসেবে bucket-এ রাখে; Key হলো অনন্য শনাক্তকারী (videos/2024/ দেখতে ফোল্ডারের মতো হলেও আসলে flat namespace-এর একটি প্রিফিক্স মাত্র)।
- generate_presigned_url একটি অস্থায়ী, সময়সীমিত URL দেয় — যা দিয়ে নিরাপদে ফাইল শেয়ার করা যায় bucket পাবলিক না করেই।
- বাস্তবে এই S3 bucket-কেই CDN-এর (CloudFront) origin হিসেবে যুক্ত করা হয়।

origin-এ CDN-বান্ধব Cache Header সেট করা (Node.js)

app.get('/static/:file', (req, res) => {
  // CDN ও ব্রাউজারকে বলা: ১ দিন ক্যাশ করো
  res.set('Cache-Control', 'public, max-age=86400');
  res.sendFile(`/assets/${req.params.file}`);
});

ব্যাখ্যা: Cache-Control: public, max-age=86400 header CDN edge-কে নির্দেশ দেয় ফাইলটি ১ দিন (৮৬,৪০০ সেকেন্ড) ক্যাশ রাখতে — ফলে origin বারবার হিট হয় না। আপডেট করতে চাইলে cache busting (?v=2) ব্যবহার করুন, যাতে purge ছাড়াই নতুন সংস্করণ পৌঁছায়।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Netflix (Open Connect): নিজস্ব CDN তৈরি করেছে — ISP-দের ভেতরেই edge সার্ভার বসিয়ে; বিশ্বের ইন্টারনেট ট্র্যাফিকের একটি বিশাল অংশ এর মাধ্যমে যায়। আসল ভিডিও ফাইল object storage-এ, edge-এ আগাম push করা।
  • YouTube / Google: Google-এর global CDN ও object storage মিলে কোটি কোটি ভিডিও বিশ্বজুড়ে কম latency-তে পরিবেশন করে।
  • Amazon (S3 + CloudFront): অসংখ্য কোম্পানি স্ট্যাটিক ওয়েবসাইট ও মিডিয়া S3-তে রেখে CloudFront দিয়ে বিতরণ করে — একটি ইন্ডাস্ট্রি-স্ট্যান্ডার্ড প্যাটার্ন।
  • Cloudflare: বিশ্বজুড়ে শত শত PoP দিয়ে CDN + নিরাপত্তা (DDoS, WAF) + edge computing (Workers) প্রদান করে — dynamic content acceleration-এর অগ্রদূত।
  • Dropbox: শুরুতে S3-এ ফাইল রাখত, পরে নিজস্ব object storage ("Magic Pocket") তৈরি করে খরচ ও নিয়ন্ত্রণের জন্য।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- ছবি/ভিডিও ডাটাবেসে রাখা (object storage-এর বদলে) — ডাটাবেস ফুলে যায় ও ধীর হয়।
- সব কনটেন্টকে dynamic ধরে নিয়ে CDN ব্যবহার না করা।

Intermediate Mistakes:
- কনটেন্ট আপডেটের পর CDN cache purge না করা — ব্যবহারকারী পুরোনো সংস্করণ দেখে।
- ভুল Cache-Control সেট করা (ব্যক্তিগত ডাটায় public, বা স্ট্যাটিক ফাইলে no-cache)।

Production Mistakes:
- ভুল স্টোরেজ নির্বাচন — যেমন ডাটাবেস object storage-এ চালানোর চেষ্টা (block লাগত), বা শেয়ারড ফাইলের জন্য একটিমাত্র block volume।
- ব্যক্তিগত/সংবেদনশীল object পাবলিক bucket-এ রাখা — বড় নিরাপত্তা ছিদ্র (data leak)।

Scalability Mistakes:
- origin shield না রাখা — cache miss-এ বহু edge একসাথে origin-এ হিট করে (origin overload)।
- সব edge-এ একই সময়ে TTL শেষ হওয়া (CDN-স্তরের avalanche)।

Architecture Mistakes:
- dynamic, ব্যক্তিগত API উত্তরকে আক্রমণাত্মকভাবে ক্যাশ করা — এক ব্যবহারকারীর ডাটা অন্যকে দেখানোর ঝুঁকি।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: CDN কী এবং কেন ব্যবহার করা হয়?

CDN হলো বিশ্বজুড়ে ছড়ানো edge সার্ভারের নেটওয়ার্ক যা ব্যবহারকারীর কাছাকাছি থেকে কনটেন্ট পরিবেশন করে — latency কমায়, গতি বাড়ায়, origin-এর লোড ও ব্যান্ডউইথ খরচ কমায়, এবং নিরাপত্তা (DDoS protection) দেয়।

Intermediate প্রশ্ন: Push CDN আর Pull CDN-এর পার্থক্য কী?

Pull CDN চাহিদা অনুযায়ী origin থেকে কনটেন্ট টেনে আনে (প্রথম অনুরোধে miss); Push CDN-এ আপনি আগে থেকেই কনটেন্ট edge-এ আপলোড করেন (কখনো প্রথম-অনুরোধ miss নেই, কিন্তু বেশি ব্যবস্থাপনা ও স্টোরেজ লাগে)।

Intermediate প্রশ্ন: Object, Block ও File Storage-এর মূল পার্থক্য কী?

Object = flat namespace, REST API, অসীম scale (মিডিয়া/ব্যাকআপ)। Block = কাঁচা ডিস্ক, কম latency, একটি instance (database/OS)। File = শ্রেণিবদ্ধ ফোল্ডার, বহু সার্ভারে শেয়ারড (NFS)।

Advanced প্রশ্ন: CDN-এ কনটেন্ট আপডেট হলে পুরোনো ক্যাশ কীভাবে সামলাবেন?

দুটি উপায় — (১) Cache Purge/Invalidation দিয়ে নির্দিষ্ট URL বা tag মুছে ফেলা; (২) আরও নিরাপদ — Cache Busting: ফাইলের নামে version যোগ করা (app.v2.js), যাতে নতুন URL স্বয়ংক্রিয়ভাবে নতুন ক্যাশ তৈরি করে এবং purge-এর দরকারই হয় না।

System Design প্রশ্ন: একটি ছবি শেয়ারিং অ্যাপের (যেমন Instagram) স্টোরেজ ও বিতরণ আর্কিটেকচার ডিজাইন করুন।

আসল ছবি Object Storage (S3)-এ রাখুন; মেটাডাটা (user, caption, likes) ডাটাবেসে; ছবির বিভিন্ন রেজোলিউশন আগাম তৈরি করে object storage-এ রাখুন; বিতরণের জন্য CDN ব্যবহার করুন যাতে ছবি ব্যবহারকারীর কাছাকাছি edge থেকে দ্রুত আসে; দীর্ঘ TTL ও cache busting দিয়ে দক্ষতা নিশ্চিত করুন।

১০. সেরা চর্চা (Best Practices)

  • স্ট্যাটিক কনটেন্ট সবসময় CDN দিয়ে পরিবেশন করুন এবং দীর্ঘ TTL দিন।
  • Cache Busting (versioned URL) ব্যবহার করুন — purge-এর ঝামেলা এড়াতে।
  • সঠিক স্টোরেজ নির্বাচন করুন — মিডিয়া→Object, DB→Block, শেয়ারড→File।
  • ছবি/ভিডিও ডাটাবেসে নয়, object storage-এ রাখুন; ডাটাবেসে শুধু মেটাডাটা ও URL।
  • Object storage-এ সঠিক অ্যাক্সেস নিয়ন্ত্রণ — সংবেদনশীল object কখনো পাবলিক করবেন না; presigned URL ব্যবহার করুন।
  • Origin Shield ব্যবহার করুন বড় CDN স্থাপনায় — origin রক্ষায়।
  • TLS edge-এ সক্ষম করুন এবং WAF দিয়ে অনুরোধ ফিল্টার করুন।
  • dynamic ও ব্যক্তিগত কনটেন্ট সাবধানে — হয় ক্যাশ করবেন না, নয়তো ব্যবহারকারী-নির্দিষ্ট key দিয়ে।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- CDN = বিশ্বজুড়ে edge সার্ভারের নেটওয়ার্ক; latency কমায়, origin রক্ষা করে, নিরাপত্তা দেয়।
- উপাদান: Origin, Edge, PoP, Origin Shield; রাউটিং Anycast/DNS দিয়ে।
- Pull CDN (on-demand, প্রচলিত) vs Push CDN (আগাম আপলোড)।
- Edge caching: TTL, Cache-Control, ETag; আপডেটে Purge বা Cache Busting।
- নিরাপত্তা: DDoS protection, TLS termination, WAF, bandwidth offload।
- Object Storage = flat, REST API, অসীম scale, উচ্চ durability (S3) → মিডিয়া/ব্যাকআপ।
- Block Storage = কাঁচা ডিস্ক, কম latency, এক instance (EBS) → database/OS।
- File Storage = শ্রেণিবদ্ধ, শেয়ারড, POSIX (EFS/NFS) → শেয়ারড ফাইল।

গুরুত্বপূর্ণ পরিভাষা: CDN, Edge Server, PoP, Origin, Origin Shield, Anycast, Pull/Push CDN, TTL, Cache-Control, ETag, Purge, Cache Busting, WAF, Object/Block/File Storage, Bucket, Durability, IOPS, Presigned URL, S3, EBS, EFS।

১২. অনুশীলন (Practice Exercises)

Conceptual:
1. Pull CDN ও Push CDN-এর পার্থক্য ও কখন কোনটি উপযুক্ত — ব্যাখ্যা করুন।
2. Object, Block ও File Storage-এর প্রতিটির একটি করে আদর্শ ব্যবহার লিখুন এবং কেন তা ব্যাখ্যা করুন।

Practical:
3. একটি স্ট্যাটিক CSS ফাইলের জন্য উপযুক্ত Cache-Control header লিখুন এবং কীভাবে নিরাপদে আপডেট করবেন তা বর্ণনা করুন।
4. উপরের S3 কোডে একটি ফাংশন যোগ করুন যা একটি object-এর জন্য ১০ মিনিটের presigned URL তৈরি করে।

Architecture Design:
5. একটি বিশ্বব্যাপী ই-লার্নিং প্ল্যাটফর্মের (ভিডিও কোর্স) জন্য সম্পূর্ণ স্টোরেজ + CDN আর্কিটেকচার ডিজাইন করুন — ভিডিও, মেটাডাটা, ও ব্যবহারকারীর আপলোড আলাদাভাবে বিবেচনা করে।

Scenario-Based:
6. আপনি একটি লোগো ফাইল আপডেট করলেন, কিন্তু ব্যবহারকারীরা এখনো পুরোনোটি দেখছে। কারণ কী এবং দুটি ভিন্ন সমাধান দিন।

Interview Challenge:
7. একজন ইন্টারভিউয়ারকে বোঝান কেন একটি প্রোডাকশন ডাটাবেস object storage-এ চালানো উচিত নয়, এবং block storage কেন উপযুক্ত।
