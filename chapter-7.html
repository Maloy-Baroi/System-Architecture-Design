অধ্যায় ৭: REST vs gRPC vs WebSockets ও Event-Driven Architecture

১. অধ্যায় পরিচিতি (Chapter Introduction)

এখন পর্যন্ত আমরা শিখেছি কীভাবে ডাটা সংরক্ষণ, ক্যাশ ও বিতরণ করা হয়। কিন্তু একটি প্রশ্ন থেকে যায় — সিস্টেমের বিভিন্ন অংশ একে অপরের সাথে কীভাবে কথা বলে? একটি মোবাইল অ্যাপ কীভাবে সার্ভারের সাথে যোগাযোগ করে? দুটি মাইক্রোসার্ভিস কীভাবে তথ্য বিনিময় করে? একটি চ্যাট অ্যাপে মেসেজ কীভাবে তাৎক্ষণিকভাবে পৌঁছায়?

এই অধ্যায়ের প্রথম অংশে আমরা তিনটি প্রধান যোগাযোগ পদ্ধতি গভীরভাবে তুলনা করব: REST, gRPC, ও WebSockets — সাথে real-time যোগাযোগের অন্যান্য কৌশল (Polling, Long Polling, SSE)। প্রতিটির শক্তি, দুর্বলতা এবং কখন কোনটি ব্যবহার করতে হয়, তা জানা একজন আর্কিটেক্টের জন্য অপরিহার্য।

দ্বিতীয় অংশে আমরা শিখব একটি ভিন্ন দর্শন — Event-Driven Architecture (EDA)। এখানে সার্ভিসগুলো সরাসরি একে অপরকে না ডেকে "ঘটনা (event)"-এর মাধ্যমে যোগাযোগ করে। এটি আধুনিক distributed system ও microservices-এর মেরুদণ্ড।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • Synchronous vs Asynchronous এবং Request-Response vs Event-Driven যোগাযোগ
  • REST-এর শক্তি ও সীমাবদ্ধতা গভীরভাবে
  • gRPC কী — Protocol Buffers, HTTP/2, এবং চার ধরনের streaming
  • WebSockets কী — full-duplex, persistent connection, real-time
  • real-time-এর বিকল্প: Polling, Long Polling, SSE (Server-Sent Events)
  • কখন REST, কখন gRPC, কখন WebSocket বেছে নিতে হয়
  • Event-Driven Architecture — event, producer, consumer, broker, Pub/Sub
  • EDA-এর সুবিধা, চ্যালেঞ্জ ও প্যাটার্ন

৩. মূল ধারণা (Core Concepts)

৩.১ যোগাযোগের দুই মাত্রা

যেকোনো যোগাযোগ বোঝার আগে দুটি মৌলিক ধারণা:

Synchronous (সিঙ্ক্রোনাস): অনুরোধকারী উত্তরের জন্য অপেক্ষা করে (blocking)। যেমন একটি ফোন কল — কথা বলে উত্তর না পাওয়া পর্যন্ত লাইনে থাকেন।

Asynchronous (অ্যাসিঙ্ক্রোনাস): অনুরোধকারী অপেক্ষা করে না, পরে উত্তর/ফলাফল আসে (non-blocking)। যেমন একটি SMS — পাঠিয়ে নিজের কাজে ফিরে যান।

এর সাথে যুক্ত:
- Request-Response: একটি পক্ষ চায়, অন্যটি দেয় (REST, gRPC)।
- Event-Driven: কিছু ঘটলে "ঘটনা" প্রকাশিত হয়, আগ্রহীরা প্রতিক্রিয়া জানায় (EDA)।

অংশ ক: যোগাযোগ প্রোটোকল

৩.২ REST (Representational State Transfer)

আমরা অধ্যায় ৩-এ REST শিখেছি। সংক্ষেপে — HTTP-এর ওপর resource-ভিত্তিক, stateless, সাধারণত JSON-ভিত্তিক request-response API।

শক্তি:
- সরল, সর্বজনীন, যেকোনো ভাষা/প্ল্যাটফর্মে সমর্থিত।
- HTTP-নেটিভ — ব্রাউজার, ক্যাশ, CDN-এর সাথে সহজে কাজ করে।
- মানুষ-পাঠযোগ্য (JSON), ডিবাগ করা সহজ।

সীমাবদ্ধতা:
- Over-fetching / Under-fetching: একটি endpoint হয় বেশি ডাটা দেয়, নয় কম — প্রায়ই একাধিক কল লাগে।
- JSON ভারী ও ধীর (text-based, parse করতে হয়)।
- কোনো নেটিভ streaming নেই; কঠোর contract/type নেই।
- সার্ভিস-টু-সার্ভিস উচ্চ-পারফরম্যান্স যোগাযোগে অদক্ষ।

পার্শ্ব-উল্লেখ: REST-এর over/under-fetching সমস্যার জন্য GraphQL একটি জনপ্রিয় বিকল্প — যেখানে client ঠিক যা চায় তাই query করে। তবে এই অধ্যায়ের মূল ফোকাস REST, gRPC ও WebSocket।

৩.৩ gRPC

gRPC (gRPC Remote Procedure Call) হলো Google-এর তৈরি একটি উচ্চ-পারফরম্যান্স RPC ফ্রেমওয়ার্ক, যা মূলত সার্ভিস-টু-সার্ভিস যোগাযোগের জন্য। RPC মানে — দূরের সার্ভারের একটি ফাংশনকে এমনভাবে ডাকা যেন সেটি লোকাল ফাংশন।

মূল স্তম্ভ:

  • Protocol Buffers (Protobuf): ডাটা সংজ্ঞায়িত ও বিনিময়ের জন্য একটি বাইনারি, দৃঢ়-টাইপড (strongly-typed) ফরম্যাট। JSON-এর চেয়ে অনেক ছোট ও দ্রুত। একটি .proto ফাইলে contract লেখা হয়।
  • HTTP/2: এর ওপর চলে — multiplexing (একই connection-এ বহু অনুরোধ), header compression, ও streaming সমর্থন করে।
  • Code Generation: .proto থেকে স্বয়ংক্রিয়ভাবে client ও server কোড তৈরি হয় (বহু ভাষায়) — type-safe ও কম ভুল।

gRPC-এর চার ধরনের যোগাযোগ:
1. Unary: একটি অনুরোধ → একটি উত্তর (সাধারণ REST-এর মতো)।
2. Server Streaming: একটি অনুরোধ → উত্তরের একটি ধারা (stream) (যেমন লাইভ ফিড)।
3. Client Streaming: অনুরোধের একটি ধারা → একটি উত্তর (যেমন বড় ফাইল আপলোড)।
4. Bidirectional Streaming: উভয় দিকে একসাথে ধারা (যেমন রিয়েল-টাইম চ্যাট)।

শক্তি: অত্যন্ত দ্রুত ও দক্ষ (binary + HTTP/2); দৃঢ় contract; streaming সমর্থন; polyglot (বহু ভাষা)।
সীমাবদ্ধতা: ব্রাউজারে সরাসরি সীমিত সমর্থন (gRPC-Web লাগে); মানুষ-পাঠযোগ্য নয় (ডিবাগ কঠিন); শেখার বক্ররেখা বেশি।
ব্যবহার: internal microservices যোগাযোগ, কম-latency ও উচ্চ-throughput প্রয়োজন যেখানে।

৩.৪ WebSockets

WebSocket হলো একটি প্রোটোকল যা client ও server-এর মধ্যে একটি স্থায়ী (persistent), full-duplex (দ্বিমুখী) সংযোগ স্থাপন করে — যেখানে উভয় পক্ষ যেকোনো সময় একে অপরকে মেসেজ পাঠাতে পারে, বারবার নতুন অনুরোধ ছাড়াই।

কীভাবে কাজ করে:
- শুরু হয় একটি সাধারণ HTTP অনুরোধ দিয়ে, তারপর "Upgrade" handshake-এর মাধ্যমে সংযোগটি WebSocket-এ রূপান্তরিত হয়।
- একবার স্থাপিত হলে সংযোগ খোলা থাকে; server push করতে পারে (client-কে অনুরোধ করতে হয় না)।

শক্তি: সত্যিকারের real-time ও দ্বিমুখী; কম overhead (একবার connect, বারবার নয়); server থেকে instant push।
সীমাবদ্ধতা: স্থায়ী সংযোগ মানে সার্ভারে বেশি রিসোর্স (প্রতিটি client-এ একটি খোলা সংযোগ); scaling জটিল (sticky session/connection management); stateful।
ব্যবহার: চ্যাট, লাইভ নোটিফিকেশন, multiplayer গেম, লাইভ স্টক/স্কোর, collaborative editing (Google Docs)।

৩.৫ Real-Time-এর অন্যান্য কৌশল

WebSocket-ই একমাত্র উপায় নয়; এর আগে ও পাশাপাশি কিছু কৌশল গুরুত্বপূর্ণ:

  • Short Polling: client নিয়মিত (যেমন প্রতি ২ সেকেন্ডে) সার্ভারকে "নতুন কিছু আছে?" জিজ্ঞেস করে। সরল, কিন্তু অপচয়মূলক — বেশিরভাগ উত্তর খালি।
  • Long Polling: client অনুরোধ পাঠায়, সার্ভার নতুন ডাটা না আসা পর্যন্ত উত্তর ধরে রাখে, তারপর উত্তর দেয়; client সঙ্গে সঙ্গে আবার অনুরোধ করে। Polling-এর চেয়ে দক্ষ, WebSocket-পূর্ব যুগের জনপ্রিয় সমাধান।
  • SSE (Server-Sent Events): একটি একমুখী (server → client) স্থায়ী সংযোগ, HTTP-এর ওপর। সার্ভার একতরফাভাবে ডাটা push করতে পারে। লাইভ ফিড/নোটিফিকেশনে চমৎকার, কিন্তু client সার্ভারে পাঠাতে পারে না (একমুখী)।

নির্বাচন: শুধু সার্ভার→ক্লায়েন্ট আপডেট দরকার → SSE। উভয়-দিকে real-time দরকার → WebSocket। পুরোনো/সরল সিস্টেমে → Long Polling।

৩.৬ REST vs gRPC vs WebSocket — তুলনা

বৈশিষ্ট্য REST gRPC WebSocket
প্রোটোকল HTTP/1.1 HTTP/2 WS (HTTP upgrade)
ডাটা ফরম্যাট JSON (text) Protobuf (binary) যেকোনো (text/binary)
যোগাযোগ Request-Response Unary + Streaming Full-duplex
গতি/দক্ষতা মাঝারি উচ্চ উচ্চ (real-time)
ব্রাউজার সমর্থন চমৎকার সীমিত (gRPC-Web) চমৎকার
Streaming না হ্যাঁ (৪ ধরন) হ্যাঁ
State Stateless Stateless Stateful
সেরা যেখানে পাবলিক API internal microservices real-time অ্যাপ

অংশ খ: Event-Driven Architecture (EDA)

৩.৭ EDA কী?

Event-Driven Architecture হলো এমন একটি স্থাপত্য যেখানে সিস্টেমের উপাদানগুলো সরাসরি একে অপরকে না ডেকে, ঘটনা (event) তৈরি ও গ্রহণের মাধ্যমে যোগাযোগ করে। একটি event হলো অতীতে ঘটে যাওয়া কোনো গুরুত্বপূর্ণ ঘটনার তথ্য — যেমন "OrderPlaced", "PaymentReceived", "UserRegistered"।

মূল ধারণা: একটি সার্ভিস কিছু ঘটলে শুধু ঘোষণা করে ("একটি অর্ডার হয়েছে"); কে কে এতে আগ্রহী এবং তারা কী করবে — তা সে জানেও না, পরোয়াও করে না।

৩.৮ EDA-এর উপাদান

  • Producer / Publisher (উৎপাদক): যে event তৈরি ও প্রকাশ করে (যেমন Order Service)।
  • Event (ঘটনা): ঘটে যাওয়া কিছুর বার্তা (data সহ)।
  • Event Broker / Message Bus (মধ্যস্থ): event গ্রহণ করে ও আগ্রহী consumer-দের কাছে পৌঁছায় (যেমন Kafka, RabbitMQ — অধ্যায় ৮)।
  • Consumer / Subscriber (গ্রাহক): যে event গ্রহণ করে ও প্রতিক্রিয়া জানায় (যেমন Email Service, Inventory Service)।

৩.৯ Pub/Sub প্যাটার্ন

Publish/Subscribe (Pub/Sub) হলো EDA-এর কেন্দ্রীয় প্যাটার্ন: producer একটি event "publish" করে একটি topic-এ; যত consumer সেই topic-এ "subscribe" করেছে, প্রত্যেকে event-টির একটি অনুলিপি পায়। producer ও consumer একে অপরকে চেনে না — সম্পূর্ণ decoupled (বিযুক্ত)।

৩.১০ Event-Driven-এর তিন শৈলী

  1. Event Notification: event শুধু জানায় "কিছু ঘটেছে" (ন্যূনতম ডাটা); consumer প্রয়োজনে বিস্তারিত জিজ্ঞেস করে।
  2. Event-Carried State Transfer: event-এর সাথেই প্রয়োজনীয় সব ডাটা থাকে (consumer-কে আর কোথাও জিজ্ঞেস করতে হয় না)।
  3. Event Sourcing: সিস্টেমের সব পরিবর্তনকে event-এর ক্রম হিসেবে সংরক্ষণ করা হয় (বিস্তারিত অধ্যায় ১৬-এ)।

৩.১১ Choreography vs Orchestration

সার্ভিসগুলোর মধ্যে কাজের সমন্বয় দুইভাবে হয়:

  • Choreography (কোরিওগ্রাফি): কোনো কেন্দ্রীয় নিয়ন্ত্রক নেই; প্রতিটি সার্ভিস event শোনে ও নিজে সিদ্ধান্ত নেয় (নাচের মতো — সবাই জানে কখন কী করতে হয়)। বিযুক্ত, কিন্তু পুরো প্রবাহ বোঝা কঠিন।
  • Orchestration (অর্কেস্ট্রেশন): একটি কেন্দ্রীয় "orchestrator" সার্ভিস ধাপে ধাপে অন্যদের নির্দেশ দেয় (অর্কেস্ট্রার কন্ডাক্টরের মতো)। নিয়ন্ত্রণ স্পষ্ট, কিন্তু কেন্দ্রীয় নির্ভরতা। (SAGA প্যাটার্নে বিস্তারিত — অধ্যায় ১৫)

৩.১২ EDA-এর সুবিধা ও চ্যালেঞ্জ

সুবিধা:
- Loose Coupling (শিথিল সংযুক্তি): সার্ভিসগুলো স্বাধীন; একটি বদলালে অন্যে প্রভাব কম।
- Scalability: consumer স্বাধীনভাবে scale করা যায়; broker peak load শোষণ করে (buffering)।
- Resilience: একটি consumer ডাউন থাকলেও event broker-এ থাকে, পরে প্রক্রিয়া হয়।
- Extensibility: নতুন consumer যোগ করা সহজ — producer-কে বদলাতে হয় না।

চ্যালেঞ্জ:
- Eventual Consistency: তাৎক্ষণিক সামঞ্জস্য নেই; ডাটা সিঙ্ক হতে সময় লাগে।
- ডিবাগিং কঠিন: প্রবাহ অনেক সার্ভিসে ছড়িয়ে; ট্রেস করা জটিল (distributed tracing লাগে)।
- Event Ordering ও Duplicates: event ক্রম রক্ষা ও একই event দুবার আসা সামলানো কঠিন (idempotency লাগে — অধ্যায় ১৪)।
- জটিলতা: সরল request-response-এর চেয়ে বেশি অবকাঠামো ও মনিটরিং দরকার।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন একটি ই-কমার্স সাইটে একটি অর্ডার হলো। এর সাথে অনেক কাজ জড়িত: পেমেন্ট প্রক্রিয়া, ইনভেন্টরি কমানো, ইমেল পাঠানো, ইনভয়েস তৈরি, রিকমেন্ডেশন আপডেট, লয়ালটি পয়েন্ট যোগ করা।

Request-Response (synchronous) দিয়ে: Order Service একে একে সব সার্ভিসকে ডাকবে ও অপেক্ষা করবে। সমস্যা — ধীর (সব শেষ না হলে ব্যবহারকারী অপেক্ষায়); একটি সার্ভিস (যেমন Email) ডাউন হলে পুরো অর্ডার আটকে যায়; নতুন কাজ যোগ করলে Order Service-এর কোড বদলাতে হয়।

Event-Driven দিয়ে: Order Service শুধু একটি OrderPlaced event publish করে এবং সঙ্গে সঙ্গে ব্যবহারকারীকে "অর্ডার গৃহীত" দেখায়। Payment, Inventory, Email, Loyalty — প্রতিটি সার্ভিস স্বাধীনভাবে event-টি শুনে নিজের কাজ করে। ফল: দ্রুত প্রতিক্রিয়া, একটি সার্ভিস ডাউন হলেও বাকিরা চলে, এবং নতুন কাজ = শুধু নতুন একটি consumer যোগ করা (Order Service অপরিবর্তিত)।

এটিই EDA-এর শক্তি — এবং কেন প্রায় সব বড় microservices সিস্টেম এটি ব্যবহার করে।

৫. ভিজ্যুয়াল আর্কিটেকচার ডায়াগ্রাম (Visual Architecture Diagrams)

Request-Response vs Event-Driven

REQUEST-RESPONSE (synchronous, coupled):
Order ── ডাকে → Payment ── ডাকে → Email ── ডাকে → Inventory
(একটি ব্যর্থ হলে পুরো শৃঙ্খল আটকে যায়)

EVENT-DRIVEN (asynchronous, decoupled):
                     +-----------------+
Order ──publish──▶  | Event Broker    |
 "OrderPlaced"      | (Kafka)         |
                     +-----------------+
                       |     |      |
                       v     v      v
                  Payment  Email  Inventory
                  (প্রত্যেকে স্বাধীনভাবে)

Mermaid: Pub/Sub প্রবাহ

graph LR P[Order Service
Producer] -->|OrderPlaced event| B[Event Broker
Topic: orders] B --> C1[Payment Service] B --> C2[Email Service] B --> C3[Inventory Service]

ডায়াগ্রাম ব্যাখ্যা:
- Components: এক Producer, একটি Broker (topic), একাধিক স্বাধীন Consumer।
- Flow: Producer event publish করে → Broker সব subscriber-কে অনুলিপি দেয় → প্রত্যেকে স্বাধীনভাবে প্রক্রিয়া করে।
- Failure Points: একটি consumer ডাউন হলে event broker-এ অপেক্ষা করে (হারায় না); broker নিজে redundant রাখা হয়।
- Scaling: প্রতিটি consumer আলাদাভাবে scale করা যায়; broker spike শোষণ করে।

gRPC Streaming ধরন

graph TD A[Unary: 1 req → 1 res] B[Server Streaming: 1 req → stream res] C[Client Streaming: stream req → 1 res] D[Bidirectional: stream ↔ stream]

ব্যাখ্যা: gRPC-এর চার ধরন বিভিন্ন প্রয়োজনে — সাধারণ কল (unary), লাইভ ফিড (server stream), বড় আপলোড (client stream), real-time চ্যাট (bidirectional)।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

gRPC: Protobuf contract সংজ্ঞা

// user.proto — দৃঢ়-টাইপড contract
syntax = "proto3";

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);          // Unary
  rpc ListUsers (Empty) returns (stream UserResponse);       // Server streaming
}

message UserRequest { int32 id = 1; }
message UserResponse { int32 id = 1; string name = 2; }
message Empty {}

ব্যাখ্যা: .proto ফাইলে service ও message সংজ্ঞায়িত। এখান থেকে client/server কোড স্বয়ংক্রিয়ভাবে তৈরি হয় (যেকোনো ভাষায়) — type-safe। stream কীওয়ার্ড server streaming নির্দেশ করে। প্রতিটি ফিল্ডের নম্বর (= 1) binary encoding-এ ব্যবহৃত হয়।

WebSocket: real-time সার্ভার (Node.js)

const WebSocket = require('ws');
const server = new WebSocket.Server({ port: 8080 });

server.on('connection', (socket) => {
  // ক্লায়েন্ট থেকে মেসেজ এলে
  socket.on('message', (msg) => {
    // সব সংযুক্ত ক্লায়েন্টে broadcast (real-time chat)
    server.clients.forEach((client) => {
      if (client.readyState === WebSocket.OPEN) {
        client.send(msg.toString());
      }
    });
  });
});

ব্যাখ্যা: connection event-এ প্রতিটি নতুন client-এর জন্য একটি persistent socket তৈরি হয়। একজন মেসেজ পাঠালে সার্ভার সব খোলা সংযোগে তা push করে — এটিই real-time broadcast। লক্ষ্য করুন: সার্ভারকে প্রতিটি সংযোগ মনে রাখতে হয় (stateful), যা scaling জটিল করে।

Event Publish (Python, pseudo-broker)

def place_order(order):
    save_to_db(order)
    # event publish — কে শুনবে তা Order Service জানে না
    broker.publish("orders", {
        "type": "OrderPlaced",
        "order_id": order.id,
        "user_id": order.user_id
    })
    return "Order accepted"   # সঙ্গে সঙ্গে ফেরত, অন্যদের অপেক্ষা ছাড়াই

ব্যাখ্যা: place_order শুধু DB-তে সংরক্ষণ করে একটি event publish করে এবং তৎক্ষণাৎ ফেরত দেয়। Payment/Email/Inventory সার্ভিস স্বাধীনভাবে এই event শুনে কাজ করবে — সম্পূর্ণ decoupled ও দ্রুত।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Google: তাদের অভ্যন্তরীণ হাজারো microservice gRPC দিয়ে যোগাযোগ করে — কম latency ও দৃঢ় contract-এর জন্য (gRPC-ই Google-এর Stubby থেকে উদ্ভূত)।
  • Netflix: ব্যাপকভাবে Event-Driven ও Kafka ব্যবহার করে — ভিউয়িং ইভেন্ট, রিকমেন্ডেশন, মনিটরিং সব event-চালিত।
  • WhatsApp / Slack / Discord: real-time মেসেজিংয়ের জন্য persistent connection (WebSocket-জাতীয়) ব্যবহার করে।
  • Uber: gRPC ও Event-Driven উভয়ই — সার্ভিস যোগাযোগে gRPC, এবং ট্রিপ/লোকেশন ইভেন্টে Kafka।
  • Stock/Trading প্ল্যাটফর্ম: লাইভ মূল্য আপডেটে WebSocket বা SSE ব্যবহার করে।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- real-time আপডেটের জন্য short polling ব্যবহার (অপচয়মূলক) যখন WebSocket/SSE উপযুক্ত।
- সব কিছুতে REST ব্যবহার, এমনকি উচ্চ-পারফরম্যান্স internal যোগাযোগেও।

Intermediate Mistakes:
- ব্রাউজার-ভিত্তিক পাবলিক API-তে সরাসরি gRPC ব্যবহার (সীমিত সমর্থন; gRPC-Web বা REST gateway লাগে)।
- Event-driven-এ idempotency না রাখা — ফলে duplicate event-এ দুবার প্রক্রিয়া (যেমন দুবার চার্জ)।

Production Mistakes:
- WebSocket scaling-এ connection state সামলানোর পরিকল্পনা না করা (sticky session/shared registry লাগে)।
- EDA-তে event ordering ধরে নেওয়া যা broker গ্যারান্টি দেয় না।
- distributed tracing ছাড়া EDA চালানো — ডিবাগিং দুঃস্বপ্ন হয়।

Scalability Mistakes:
- প্রতিটি client-এ খোলা WebSocket সংযোগের রিসোর্স খরচ বিবেচনা না করা।
- synchronous chain (একটি সার্ভিস আরেকটিকে ডাকে, সেটি আরেকটিকে) তৈরি করা — যা cascading failure ঘটায়।

Architecture Mistakes:
- যেখানে সরল request-response যথেষ্ট, সেখানে অপ্রয়োজনে EDA-এর জটিলতা যোগ করা (over-engineering)।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: Synchronous আর Asynchronous যোগাযোগের পার্থক্য কী?

Synchronous-এ অনুরোধকারী উত্তরের জন্য অপেক্ষা করে (blocking); Asynchronous-এ অপেক্ষা করে না, পরে ফলাফল আসে (non-blocking) — যেমন EDA।

Intermediate প্রশ্ন: REST আর gRPC-এর মধ্যে কখন কোনটি বেছে নেবেন?

পাবলিক, ব্রাউজার-বান্ধব, সরল API-তে REST। internal microservices-এ উচ্চ পারফরম্যান্স, streaming ও দৃঢ় contract দরকার হলে gRPC (binary Protobuf + HTTP/2)।

Intermediate প্রশ্ন: WebSocket আর SSE-এর পার্থক্য কী?

WebSocket full-duplex (উভয় দিকে); SSE একমুখী (শুধু server→client)। শুধু সার্ভার আপডেট push করলে SSE যথেষ্ট ও সরল; দ্বিমুখী real-time দরকার হলে WebSocket।

Advanced প্রশ্ন: Event-Driven Architecture-এর প্রধান ট্রেড-অফ কী?

এটি loose coupling, scalability ও resilience দেয়, কিন্তু বিনিময়ে আসে eventual consistency, কঠিন ডিবাগিং, event ordering/duplicate সমস্যা, এবং বাড়তি অবকাঠামোগত জটিলতা।

System Design প্রশ্ন: একটি real-time চ্যাট অ্যাপ ডিজাইন করুন — কোন যোগাযোগ পদ্ধতি ও কেন?

ক্লায়েন্ট-সার্ভার real-time মেসেজিংয়ে WebSocket (full-duplex, instant push)। পেছনে মেসেজ বিতরণ ও persistence-এ Event-Driven + message broker (Kafka) যাতে একাধিক সার্ভার ও অফলাইন ডেলিভারি সামলানো যায়। connection scaling-এ shared session registry/sticky routing; idempotency দিয়ে duplicate রোধ।

১০. সেরা চর্চা (Best Practices)

  • সঠিক টুল সঠিক কাজে: পাবলিক API → REST; internal উচ্চ-পারফরম্যান্স → gRPC; real-time দ্বিমুখী → WebSocket; একমুখী লাইভ → SSE।
  • প্রয়োজন না হলে real-time push এড়ান — short polling-এর অপচয় ও WebSocket-এর জটিলতা দুটোই বুঝে ব্যবহার করুন।
  • EDA-তে idempotent consumer লিখুন — duplicate event নিরাপদে সামলাতে।
  • event-এ স্পষ্ট schema/version রাখুন (যেমন Avro/Protobuf) — যাতে producer/consumer স্বাধীনভাবে বিকশিত হতে পারে।
  • distributed tracing ও monitoring যুক্ত করুন EDA-তে — দৃশ্যমানতার জন্য।
  • WebSocket scaling পরিকল্পনা করুন — connection state, heartbeat/ping, reconnect কৌশল।
  • synchronous chain এড়িয়ে asynchronous event ব্যবহার করুন cascading failure রোধে।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- যোগাযোগ: Synchronous (অপেক্ষা) vs Asynchronous (অপেক্ষা নেই); Request-Response vs Event-Driven।
- REST = সরল, HTTP/JSON, পাবলিক API; কিন্তু over/under-fetching ও streaming-হীন।
- gRPC = Protobuf (binary) + HTTP/2; দ্রুত, দৃঢ়-টাইপড, ৪ ধরনের streaming; internal microservices-এ আদর্শ।
- WebSocket = persistent, full-duplex, real-time; চ্যাট/গেম/লাইভে আদর্শ; কিন্তু stateful ও scaling জটিল।
- বিকল্প: Short Polling (অপচয়), Long Polling, SSE (একমুখী server→client)।
- EDA = event-এর মাধ্যমে decoupled যোগাযোগ; Producer → Broker → Consumer; Pub/Sub।
- শৈলী: Event Notification, Event-Carried State Transfer, Event Sourcing; Choreography vs Orchestration।
- EDA ট্রেড-অফ: loose coupling/scalability/resilience ↔ eventual consistency/ডিবাগিং/ordering জটিলতা।

গুরুত্বপূর্ণ পরিভাষা: Synchronous, Asynchronous, RPC, Protocol Buffers, HTTP/2, Unary/Streaming, Full-duplex, Handshake, Polling, Long Polling, SSE, Event, Producer, Consumer, Broker, Pub/Sub, Topic, Choreography, Orchestration, Eventual Consistency, Idempotency, Loose Coupling।
