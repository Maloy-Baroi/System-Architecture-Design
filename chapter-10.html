অধ্যায় ১০: Load Balancer Deep Dive, Database Partitioning ও Sharding

১. অধ্যায় পরিচিতি (Chapter Introduction)

অধ্যায় ৯-এ আমরা শিখেছি horizontal scaling-এ আরও সার্ভার যোগ করা হয়। কিন্তু একটি গুরুত্বপূর্ণ প্রশ্ন থেকে যায় — কোটি কোটি অনুরোধ এই সার্ভারগুলোর মধ্যে কীভাবে ন্যায্যভাবে ভাগ হবে? এর উত্তর হলো Load Balancer, যা আমরা অধ্যায় ২-এ সংক্ষেপে দেখেছি। এই অধ্যায়ে আমরা এর গভীরে যাব — L4 vs L7, বিভিন্ন অ্যালগরিদম, consistent hashing, এবং Load Balancer নিজে কীভাবে নির্ভরযোগ্য থাকে।

কিন্তু অ্যাপ সার্ভার scale করা সহজ অংশ। আসল চ্যালেঞ্জ হলো ডাটাবেস। আপনি ১০০০টি stateless সার্ভার বসাতে পারেন, কিন্তু যদি সবাই একটিই ডাটাবেসে আঘাত করে, সেই ডাটাবেসই bottleneck হয়ে যায়। ডাটা যখন এক মেশিনে আঁটে না বা এক মেশিন সব query সামলাতে পারে না, তখন ডাটাকে ভাগ করতে হয় — এটিই Partitioning ও Sharding।

এই অধ্যায়টি internet-scale সিস্টেম ডিজাইনের মেরুদণ্ড, এবং System Design ইন্টারভিউয়ের সবচেয়ে গুরুত্বপূর্ণ অধ্যায়গুলোর একটি।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • L4 (Transport) vs L7 (Application) load balancing
  • সব প্রধান load balancing অ্যালগরিদম (Round Robin থেকে Consistent Hashing)
  • Health Check (active/passive), SSL termination, reverse proxy ভূমিকা
  • Load Balancer-এর High Availability (active-passive, active-active)
  • GSLB / DNS load balancing (global scale)
  • Partitioning কী — Vertical vs Horizontal
  • Sharding কী, এবং sharding কৌশল (Range, Hash, Consistent Hash, Directory)
  • Shard Key নির্বাচন ও চ্যালেঞ্জ (hotspot, rebalancing, cross-shard query)

৩. মূল ধারণা (Core Concepts)

অংশ ক: Load Balancer Deep Dive

৩.১ Load Balancer পুনঃপরিচয়

Load Balancer (LB) হলো একটি উপাদান যা আগত ট্র্যাফিক একাধিক backend সার্ভারে বণ্টন করে। এটি সাধারণত একটি reverse proxy হিসেবে কাজ করে — client সরাসরি সার্ভার চেনে না, শুধু LB-কে চেনে; LB পেছনে অনুরোধ রুট করে। এতে scaling, availability ও নিরাপত্তা সবই উন্নত হয়।

৩.২ L4 vs L7 Load Balancing

OSI মডেলের কোন স্তরে কাজ করে, তার ভিত্তিতে দুই ধরন:

L4 (Layer 4 — Transport Layer):
TCP/UDP স্তরে কাজ করে; শুধু IP ঠিকানা ও পোর্ট দেখে রুট করে — অনুরোধের ভেতরের কনটেন্ট দেখে না।
- সুবিধা: অত্যন্ত দ্রুত ও কম overhead (প্যাকেট না খুলেই রুট)।
- সীমা: কনটেন্ট-ভিত্তিক বুদ্ধিমান রাউটিং করতে পারে না।
- উদাহরণ: AWS NLB (Network Load Balancer)।

L7 (Layer 7 — Application Layer):
HTTP স্তরে কাজ করে; URL, header, cookie, content দেখে রুট করতে পারে — যেমন /api/* এক গ্রুপে, /images/* আরেক গ্রুপে।
- সুবিধা: বুদ্ধিমান, কনটেন্ট-ভিত্তিক রাউটিং; SSL termination; sticky session সহজ।
- সীমা: L4-এর চেয়ে ধীর (প্যাকেট খুলে পড়তে হয়)।
- উদাহরণ: AWS ALB (Application Load Balancer), NGINX, HAProxy।

সংক্ষেপে: কাঁচা গতি ও সরল রাউটিং → L4; বুদ্ধিমান, কনটেন্ট-সচেতন রাউটিং → L7 (আধুনিক ওয়েব অ্যাপে বেশি ব্যবহৃত)।

৩.৩ Load Balancing অ্যালগরিদম (বিস্তারিত)

  • Round Robin: পালাক্রমে প্রতিটি সার্ভারে একটি করে। সরল, কিন্তু সার্ভারের ক্ষমতা/লোড বিবেচনা করে না।
  • Weighted Round Robin: শক্তিশালী সার্ভারকে বেশি ওজন (weight) দিয়ে বেশি অনুরোধ।
  • Least Connections: যে সার্ভারে এই মুহূর্তে সবচেয়ে কম সক্রিয় সংযোগ, সেখানে পাঠানো। দীর্ঘস্থায়ী সংযোগে ভালো।
  • Weighted Least Connections: least connections + সার্ভার ক্ষমতার ওজন।
  • Least Response Time: যে সার্ভার দ্রুততম উত্তর দিচ্ছে সেখানে — latency-সচেতন।
  • IP Hash: client IP-এর hash দিয়ে সার্ভার নির্ধারণ — একই client সবসময় একই সার্ভারে (sticky-র মতো)।
  • Random (with Two Choices): এলোমেলো দুটি সার্ভার বেছে কম-লোডেরটি নেওয়া — সরল অথচ কার্যকর।
  • Consistent Hashing: (নিচে বিস্তারিত) — সার্ভার যোগ/সরালে ন্যূনতম পুনর্বণ্টন।

৩.৪ Consistent Hashing (গুরুত্বপূর্ণ)

সাধারণ hashing-এ (server = hash(key) % N) সমস্যা: সার্ভার সংখ্যা N বদলালে (যোগ/সরানো) প্রায় সব key-এর mapping বদলে যায় — ফলে বিশাল পুনর্বণ্টন ও cache miss।

Consistent Hashing এই সমস্যা সমাধান করে: সার্ভার ও key উভয়কে একটি কাল্পনিক বৃত্তাকার "hash ring"-এ বসানো হয়; প্রতিটি key তার ঘড়ির কাঁটার দিকে নিকটতম সার্ভারে যায়। একটি সার্ভার যোগ/সরালে শুধু তার প্রতিবেশী অংশের key গুলো সরে — বাকি সব অপরিবর্তিত।
- Virtual Nodes (vnodes): প্রতিটি ভৌত সার্ভারকে ring-এ একাধিক ভার্চুয়াল বিন্দু হিসেবে রাখা হয় — যাতে লোড আরও সমানভাবে বণ্টিত হয়।
- ব্যবহার: distributed cache (যেমন Redis cluster, Memcached), distributed database (Cassandra, DynamoDB), এবং sharding।

৩.৫ Health Check (স্বাস্থ্য পরীক্ষা)

LB শুধু সুস্থ সার্ভারেই ট্র্যাফিক পাঠায়:
- Active Health Check: LB নিয়মিত সার্ভারকে ping/HTTP অনুরোধ পাঠায় (যেমন /health); ব্যর্থ হলে সরিয়ে রাখে।
- Passive Health Check: চলমান অনুরোধের ব্যর্থতা পর্যবেক্ষণ করে সিদ্ধান্ত নেওয়া।

৩.৬ অন্যান্য LB ভূমিকা

  • SSL/TLS Termination: LB-তে এনক্রিপশন সামলানো হয় — backend সার্ভারের কাজ কমে।
  • Session Persistence (Sticky Session): একই client-কে একই সার্ভারে রাখা (stateful অ্যাপে; অধ্যায় ৯ দ্রষ্টব্য)।
  • Reverse Proxy ও নিরাপত্তা: backend লুকানো, DDoS শোষণ, rate limiting।

৩.৭ Load Balancer-এর High Availability

LB নিজেই Single Point of Failure হতে পারে — তাই LB-কেও redundant করতে হয়:
- Active-Passive: একটি সক্রিয় LB, একটি standby; সক্রিয়টি ব্যর্থ হলে standby দায়িত্ব নেয় (failover), প্রায়ই একটি floating/virtual IP দিয়ে।
- Active-Active: একাধিক LB একসাথে ট্র্যাফিক সামলায় — বেশি ক্ষমতা ও redundancy।

৩.৮ GSLB / DNS Load Balancing (Global Scale)

একটি অঞ্চলেই নয়, বিশ্বজুড়ে ট্র্যাফিক বণ্টনে:
- DNS-based Load Balancing: একটি ডোমেইনের জন্য DNS বিভিন্ন IP ফেরত দেয় (ভৌগোলিক/round-robin ভিত্তিতে) — ব্যবহারকারীকে নিকটতম/উপযুক্ত region-এ পাঠায়।
- GSLB (Global Server Load Balancing): একাধিক datacenter/region-এর মধ্যে latency, geography ও স্বাস্থ্য বিবেচনা করে রুট করে। (CDN-এর Anycast-এর সাথে সম্পর্কিত — অধ্যায় ৬)।

অংশ খ: Partitioning ও Sharding

৩.৯ Partitioning কী?

Partitioning হলো একটি বড় ডাটাবেস/টেবিলকে ছোট ছোট, আরও ব্যবস্থাপনাযোগ্য অংশে (partition) ভাগ করা — যাতে পারফরম্যান্স, scalability ও ব্যবস্থাপনা উন্নত হয়। দুই প্রধান ধরন:

Vertical Partitioning (উল্লম্ব বিভাজন):
টেবিলকে কলাম অনুযায়ী ভাগ করা — কিছু কলাম এক জায়গায়, কিছু অন্য জায়গায়। যেমন users টেবিলের ঘন-ব্যবহৃত কলাম (id, name) এক partition-এ, বড়/কম-ব্যবহৃত কলাম (bio, profile_pic) আরেকটিতে।
- সুবিধা: ঘন-ব্যবহৃত ডাটা ছোট ও দ্রুত; সম্পর্কহীন ডাটা আলাদা।

Horizontal Partitioning (অনুভূমিক বিভাজন) = Sharding:
টেবিলকে সারি (row) অনুযায়ী ভাগ করা — একই গঠন, কিন্তু ভিন্ন সারি ভিন্ন partition-এ। যেমন user 1–10 লক্ষ এক shard-এ, 10–20 লক্ষ আরেকটিতে। যখন এই partition গুলো ভিন্ন মেশিনে থাকে, তখন একে Sharding বলে।

Partitioning ≠ Replication: Partitioning ডাটাকে ভাগ করে (প্রতিটি অংশ ভিন্ন)। Replication ডাটার অনুলিপি রাখে (একই ডাটা একাধিক জায়গায়, redundancy ও read scaling-এর জন্য — অধ্যায় ১২/১৩)। বড় সিস্টেমে দুটোই একসাথে ব্যবহৃত হয়।

৩.১০ Sharding বিস্তারিত

Sharding হলো horizontal partitioning যেখানে ডাটা একাধিক স্বাধীন ডাটাবেস সার্ভারে (shard) বিতরণ করা হয়। কোন সারি কোন shard-এ যাবে তা নির্ধারণ করে Shard Key (partition key)।

Sharding কৌশল:

  1. Range-Based Sharding: key-এর পরিসর অনুযায়ী (যেমন A–M এক shard, N–Z আরেকটি; বা তারিখ অনুযায়ী)।
    - সুবিধা: range query সহজ; বাস্তবায়ন সরল।
    - অসুবিধা: অসম বণ্টন ও hotspot (যেমন সাম্প্রতিক তারিখে সব লেখা একটি shard-এ)।

  2. Hash-Based Sharding: shard key-এর hash দিয়ে shard নির্ধারণ (shard = hash(key) % N)।
    - সুবিধা: সমান বণ্টন; hotspot কম।
    - অসুবিধা: range query কঠিন; shard সংখ্যা বদলালে বিশাল পুনর্বণ্টন (এজন্য consistent hashing)।

  3. Consistent Hashing: (উপরে দেখুন) — shard যোগ/সরালে ন্যূনতম পুনর্বণ্টন। আধুনিক distributed DB-তে জনপ্রিয়।

  4. Directory / Lookup-Based Sharding: একটি আলাদা lookup টেবিল রাখে কোন key কোন shard-এ আছে।
    - সুবিধা: সর্বোচ্চ নমনীয়তা; sharding scheme সহজে বদলানো যায়।
    - অসুবিধা: lookup টেবিল নিজে bottleneck ও single point of failure হতে পারে।

  5. Geo-Based Sharding: ভৌগোলিক অবস্থান অনুযায়ী (ইউরোপের ডাটা ইউরোপের shard-এ) — latency ও আইনি (data residency) কারণে।

৩.১১ Shard Key নির্বাচন ও চ্যালেঞ্জ

ভালো Shard Key-এর গুণ: উচ্চ cardinality (অনেক ভিন্ন মান), সমান বণ্টন, এবং বেশিরভাগ query-তে উপস্থিত (যাতে cross-shard এড়ানো যায়)।

Sharding-এর প্রধান চ্যালেঞ্জ:
- Hotspot / Celebrity Problem: এক shard-এ অসম লোড — যেমন একজন বিখ্যাত ব্যবহারকারীর (celebrity) সব ডাটা এক shard-এ, যা overload হয়।
- Resharding / Rebalancing: shard যোগ/সরানোর সময় ডাটা পুনর্বণ্টন — জটিল ও ঝুঁকিপূর্ণ (consistent hashing সাহায্য করে)।
- Cross-Shard Query / Join: একাধিক shard-জুড়ে query/join ব্যয়বহুল ও ধীর; প্রায়ই অ্যাপ্লিকেশন-স্তরে জোড়া লাগাতে হয়।
- Distributed Transactions: একাধিক shard জুড়ে ACID লেনদেন কঠিন (two-phase commit/SAGA — অধ্যায় ১৪/১৫)।
- জটিলতা ও অপারেশন: ব্যাকআপ, monitoring, schema পরিবর্তন সব shard-জুড়ে কঠিন।

নিয়ম: sharding একটি শেষ অস্ত্র — আগে vertical scaling, read replica, caching চেষ্টা করুন; ডাটা সত্যিই এক মেশিনে না আঁটলে তবেই shard করুন, কারণ এটি বিশাল জটিলতা যোগ করে।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনার সোশ্যাল অ্যাপে ৫০ কোটি ব্যবহারকারী এবং একটি posts টেবিলে ১০০ কোটি পোস্ট। সমস্যা:

  • একটি ডাটাবেস সার্ভারে এত ডাটা আঁটে না (স্টোরেজ সীমা)।
  • এত write/read একটি মেশিন সামলাতে পারে না (throughput সীমা)।
  • Index এত বড় যে query ধীর।

Vertical scaling / caching যথেষ্ট নয় — কারণ এটি মৌলিকভাবে আকারের সমস্যা।

সমাধান — Sharding:
- user_id-কে shard key ধরে hash-based sharding: প্রতিটি ব্যবহারকারীর পোস্ট তার hash(user_id) অনুযায়ী shard-এ যায়।
- ১০টি shard হলে প্রতিটিতে ~১০ কোটি পোস্ট — যা ব্যবস্থাপনাযোগ্য।
- ট্র্যাফিক ১০টি মেশিনে ভাগ হয়ে throughput ১০ গুণ।
- সামনে একটি Load Balancer অ্যাপ সার্ভার scale করে; প্রতিটি অ্যাপ সার্ভার shard key দেখে সঠিক shard-এ যায়।

কিন্তু সাবধানতা — "একজন celebrity-র টাইমলাইন" বা "সব shard জুড়ে সার্চ" এখন কঠিন। এই ট্রেড-অফগুলো জেনেই sharding করতে হয়। Instagram, Twitter ঠিক এভাবেই scale করেছে।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

Consistent Hashing (Python — সরলীকৃত)

import hashlib, bisect

class ConsistentHash:
    def __init__(self, servers, vnodes=100):
        self.ring = {}                 # hash → server
        self.sorted_keys = []
        for s in servers:
            for i in range(vnodes):    # virtual nodes — সমান বণ্টন
                h = self._hash(f"{s}:{i}")
                self.ring[h] = s
                bisect.insort(self.sorted_keys, h)

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_server(self, key):
        h = self._hash(key)
        # ঘড়ির কাঁটার দিকে নিকটতম server
        idx = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)
        return self.ring[self.sorted_keys[idx]]

ch = ConsistentHash(["shard0", "shard1", "shard2"])
print(ch.get_server("user_42"))   # সবসময় একই shard দেবে

ব্যাখ্যা: প্রতিটি server-কে vnodes সংখ্যক ভার্চুয়াল বিন্দু হিসেবে ring-এ বসানো হয় (সমান বণ্টনের জন্য)। get_server একটি key-এর hash থেকে ঘড়ির কাঁটার দিকে নিকটতম server খুঁজে দেয় (bisect দিয়ে দ্রুত)। একটি server সরালে শুধু তার অংশের key পুনর্বণ্টিত হয় — বাকি সব অপরিবর্তিত।

NGINX Load Balancer কনফিগ (L7)

upstream backend {
    least_conn;                       # least connections অ্যালগরিদম
    server app1.example.com weight=3; # শক্তিশালী সার্ভার, বেশি weight

ব্যাখ্যা: NGINX একটি L7 reverse proxy/load balancer হিসেবে কাজ করছে — least_conn অ্যালগরিদম, weight দিয়ে অসম ক্ষমতা সামলানো, /api/ path-ভিত্তিক রাউটিং (L7-এর সুবিধা), SSL এখানেই terminate, এবং active health_check।

  • Google (Maglev) ও Netflix: নিজস্ব বিশাল-স্কেল software load balancer ব্যবহার করে কোটি কোটি সংযোগ বণ্টন করতে।
  • Discord: Cassandra-তে message sharding করে ট্রিলিয়ন মেসেজ সামলায়; hotspot ও large-partition সমস্যা সমাধানের কেস স্টাডি বিখ্যাত।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- Load Balancer-কে single point of failure রেখে দেওয়া (redundant না করা)।
- ভুল ভেবে নেওয়া যে sharding শুধু "আরও মেশিন" — এর বিশাল জটিলতা উপেক্ষা করা।

Intermediate Mistakes:
- খারাপ shard key বাছা (কম cardinality বা অসম বণ্টন) → hotspot।
- সাধারণ hash % N ব্যবহার, যা shard যোগে বিশাল পুনর্বণ্টন ঘটায় (consistent hashing দরকার)।

Production Mistakes:
- Celebrity/hotspot সমস্যা পরিকল্পনা না করা — এক shard overload।
- cross-shard query/join-এর খরচ আগে থেকে বিবেচনা না করা।
- প্রতিটি shard আলাদাভাবে replicate না করা — shard ডাউন মানে ঐ ডাটা পুরোপুরি অনুপলব্ধ।

Scalability Mistakes:
- প্রয়োজনের আগেই sharding (premature) — যখন caching/replica যথেষ্ট ছিল।
- resharding কৌশল ছাড়াই shard করা — পরে বাড়াতে গিয়ে আটকে যাওয়া।

Architecture Mistakes:
- L4 ব্যবহার যেখানে content-ভিত্তিক রাউটিং (L7) দরকার ছিল, বা উল্টোটা।
- partitioning ও replication গুলিয়ে ফেলা — দুটি ভিন্ন উদ্দেশ্যের কৌশল।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: L4 আর L7 load balancer-এর পার্থক্য কী?

L4 transport স্তরে (IP/পোর্ট) কাজ করে — দ্রুত কিন্তু কনটেন্ট দেখে না। L7 application স্তরে (HTTP, URL, header) কাজ করে — বুদ্ধিমান কনটেন্ট-ভিত্তিক রাউটিং ও SSL termination দিতে পারে, তবে ধীর।

Intermediate প্রশ্ন: Consistent Hashing কেন দরকার?

সাধারণ hash % N-এ সার্ভার সংখ্যা বদলালে প্রায় সব key পুনর্বণ্টিত হয় (বিশাল cache miss/ডাটা সরানো)। Consistent hashing-এ সার্ভার যোগ/সরালে শুধু প্রতিবেশী অংশের key সরে — পুনর্বণ্টন ন্যূনতম।

Intermediate প্রশ্ন: Vertical আর Horizontal partitioning-এর পার্থক্য কী?

Vertical — টেবিলকে কলাম অনুযায়ী ভাগ (কিছু কলাম এক জায়গায়)। Horizontal (sharding) — সারি অনুযায়ী ভাগ (ভিন্ন সারি ভিন্ন মেশিনে)।

Advanced প্রশ্ন: Sharding-এ "celebrity/hotspot" সমস্যা কী এবং কীভাবে সামলাবেন?

একটি shard-এ অসম লোড — যেমন একজন বিখ্যাত ব্যবহারকারীর বিপুল ট্র্যাফিক এক shard-এ পড়ে সেটি overload করে। সমাধান: ভালো shard key (উচ্চ cardinality), hot key-কে আলাদা/একাধিক shard-এ ছড়ানো, ঐ ডাটা caching, বা celebrity-দের জন্য আলাদা ব্যবস্থা।

System Design প্রশ্ন: একটি বিশ্বব্যাপী চ্যাট অ্যাপের ডাটাবেস স্তর ডিজাইন করুন (ট্রিলিয়ন মেসেজ)।

মেসেজ channel_id বা chat_id-ভিত্তিক sharding (একই চ্যাটের মেসেজ একসাথে); consistent hashing দিয়ে shard বণ্টন ও সহজ rebalancing; প্রতিটি shard replicated (HA); সামনে L7 load balancer + stateless সার্ভার; cross-shard query এড়াতে query প্যাটার্ন অনুযায়ী shard key বাছা; hot channel-এর জন্য caching। বিশ্বব্যাপী latency-তে GSLB/geo-sharding বিবেচনা।

১০. সেরা চর্চা (Best Practices)

  • Load Balancer-কে redundant করুন (active-passive/active-active) — single point of failure এড়াতে।
  • L7 ব্যবহার করুন আধুনিক ওয়েব অ্যাপে (content-ভিত্তিক রাউটিং, SSL termination); কাঁচা গতিতে L4।
  • distributed cache/sharding-এ consistent hashing ব্যবহার করুন।
  • Sharding-এর আগে caching, read replica, vertical scaling চেষ্টা করুন — sharding শেষ অস্ত্র।
  • ভালো shard key বাছুন — উচ্চ cardinality, সমান বণ্টন, query-বান্ধব।
  • প্রতিটি shard আলাদাভাবে replicate করুন — HA নিশ্চিত করতে।
  • hotspot ও resharding আগে থেকে পরিকল্পনা করুন; query প্যাটার্ন বুঝে shard key স্থির করুন।
  • partitioning ও replication আলাদা করে ভাবুন — একটি ভাগ করে, অন্যটি অনুলিপি রাখে।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Load Balancer = reverse proxy যা ট্র্যাফিক বণ্টন করে; L4 (দ্রুত, IP/পোর্ট) vs L7 (বুদ্ধিমান, HTTP)।
- অ্যালগরিদম: Round Robin, Weighted, Least Connections, Least Response Time, IP Hash, Consistent Hashing।
- Consistent Hashing = সার্ভার যোগ/সরালে ন্যূনতম পুনর্বণ্টন; virtual nodes দিয়ে সমান বণ্টন।
- Health Check (active/passive), SSL termination, HA (active-passive/active-active), GSLB (global)।
- Partitioning = ডাটা ভাগ করা; Vertical (কলাম) vs Horizontal/Sharding (সারি)।
- Sharding কৌশল: Range, Hash, Consistent Hash, Directory, Geo।
- চ্যালেঞ্জ: hotspot/celebrity, resharding, cross-shard query, distributed transaction।
- Partitioning ≠ Replication — ভাগ vs অনুলিপি।

গুরুত্বপূর্ণ পরিভাষা: L4/L7, Reverse Proxy, Round Robin, Least Connections, IP Hash, Consistent Hashing, Virtual Nodes, Health Check, SSL Termination, Active-Passive/Active-Active, Floating IP, GSLB, Partitioning (Vertical/Horizontal), Sharding, Shard Key, Range/Hash/Directory Sharding, Hotspot, Resharding, Cross-Shard Query।
