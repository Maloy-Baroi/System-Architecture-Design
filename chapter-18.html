অধ্যায় ১৮: AWS Fundamentals, Core AWS Services ও Deploying Applications on AWS

১. অধ্যায় পরিচিতি (Chapter Introduction)

এতদিন আমরা সিস্টেম ডিজাইনের তাত্ত্বিক ও স্থাপত্যগত ধারণা শিখেছি — scaling, load balancing, caching, sharding, queue, redundancy। কিন্তু এই সব ধারণা বাস্তবে কোথায় চলে? কোনো একটি ভৌত datacenter-এ আপনি নিজে সার্ভার কিনে, নেটওয়ার্ক বসিয়ে, ঠান্ডা রেখে এগুলো চালাতে পারেন — অথবা একটি cloud platform ব্যবহার করতে পারেন, যেখানে এই সব রিসোর্স কয়েক ক্লিকে, ব্যবহার-অনুযায়ী-ভাড়ায় পাওয়া যায়।

AWS (Amazon Web Services) হলো বিশ্বের বৃহত্তম ও সবচেয়ে পরিণত cloud platform। আগের অধ্যায়গুলোর প্রায় প্রতিটি ধারণার একটি সরাসরি AWS সেবা আছে — load balancer (ELB), object storage (S3), CDN (CloudFront), managed database (RDS/DynamoDB), message queue (SQS), auto-scaling, এবং আরও অনেক কিছু। এই অধ্যায়ে আমরা শিখব AWS-এর মৌলিক কাঠামো, সবচেয়ে গুরুত্বপূর্ণ সেবাগুলো, এবং কীভাবে একটি বাস্তব অ্যাপ্লিকেশন AWS-এ ডিপ্লয় ও scale করা হয়।

আমি এই অধ্যায়টি ব্যবহারিক রেখেছি — কোন সেবা কী কাজে, কোনটি কখন বাছবেন, এবং কীভাবে একসাথে জুড়ে একটি প্রোডাকশন আর্কিটেকচার গড়বেন — যাতে আপনি সরাসরি কাজে লাগাতে পারেন। (লক্ষ্য করুন: AWS ক্রমাগত নতুন সেবা ও মূল্য যোগ করে; এখানে মূল, স্থিতিশীল ধারণা ও সেবার ভূমিকা শেখানো হয়েছে — নির্দিষ্ট মূল্য/সীমা সবসময় AWS-এর অফিসিয়াল ডকুমেন্টেশনে যাচাই করবেন।)

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি গভীরভাবে বুঝতে ও প্রয়োগ করতে পারবেন:

  • Cloud-এর মডেল (IaaS, PaaS, SaaS) এবং AWS-এর Global Infrastructure (Region, AZ, Edge)
  • Shared Responsibility Model — নিরাপত্তায় কার দায়িত্ব কী
  • IAM — user, role, policy, least privilege
  • VPC — subnet, security group, NAT, internet gateway (cloud networking)
  • বিভাগ অনুযায়ী Core AWS Services — Compute, Storage, Database, Networking, Messaging, Monitoring, Security
  • কোন সেবা কখন বাছবেন (EC2 vs Lambda vs ECS; RDS vs DynamoDB ইত্যাদি)
  • বাস্তব deployment আর্কিটেকচার — 3-tier, serverless, container, এবং CI/CD ও IaC

৩. মূল ধারণা (Core Concepts)

অংশ ক: AWS Fundamentals

৩.১ Cloud মডেল — IaaS, PaaS, SaaS

Cloud সেবা তিনটি স্তরে আসে, নিয়ন্ত্রণ ও ব্যবস্থাপনার ভিন্ন মাত্রায়:
- IaaS (Infrastructure as a Service): কাঁচা অবকাঠামো — ভার্চুয়াল সার্ভার, স্টোরেজ, নেটওয়ার্ক। আপনি OS থেকে শুরু করে সব নিয়ন্ত্রণ করেন। উদাহরণ: EC2। সর্বোচ্চ নমনীয়তা, সর্বোচ্চ দায়িত্ব।
- PaaS (Platform as a Service): প্ল্যাটফর্ম দেওয়া হয়; আপনি শুধু কোড ডিপ্লয় করেন, অবকাঠামো AWS সামলায়। উদাহরণ: Elastic Beanstalk, Lambda। কম নিয়ন্ত্রণ, কম ঝামেলা।
- SaaS (Software as a Service): সম্পূর্ণ তৈরি সফটওয়্যার, শুধু ব্যবহার করেন। উদাহরণ: Gmail, একটি AWS-হোস্টেড managed অ্যাপ।

মনে রাখুন: যত উপরে (IaaS → SaaS), তত কম নিয়ন্ত্রণ কিন্তু তত কম operational বোঝা। সঠিক স্তর বাছা একটি গুরুত্বপূর্ণ সিদ্ধান্ত।

৩.২ AWS Global Infrastructure — Region, AZ, Edge

AWS-এর ভৌত অবকাঠামো একটি স্তরবিন্যাসে সাজানো — এটি বোঝা HA ও latency ডিজাইনের (অধ্যায় ১২, ৬) ভিত্তি:

  • Region (অঞ্চল): একটি বৃহৎ ভৌগোলিক এলাকা (যেমন us-east-1, ap-south-1 মুম্বাই)। প্রতিটি region ভৌতভাবে আলাদা ও স্বাধীন। আপনি ব্যবহারকারীর কাছাকাছি region বাছেন (কম latency, ও data residency আইনের জন্য)।
  • Availability Zone (AZ): একটি region-এর ভেতরে এক বা একাধিক স্বতন্ত্র datacenter (পৃথক পাওয়ার, কুলিং, নেটওয়ার্ক), কিন্তু একে অপরের কাছাকাছি ও দ্রুত সংযুক্ত। একাধিক AZ-তে ছড়িয়ে ডিপ্লয় করলে একটি AZ-এর বিপর্যয়েও অ্যাপ চলে — এটিই Multi-AZ (অধ্যায় ১২)।
  • Edge Location: CDN (CloudFront)-এর জন্য বিশ্বজুড়ে শত শত ছোট পয়েন্ট, যা ব্যবহারকারীর কাছাকাছি কনটেন্ট ক্যাশ করে (অধ্যায় ৬)।

ব্যবহারিক নিয়ম: প্রোডাকশনে সবসময় অন্তত দুটি AZ-তে ডিপ্লয় করুন (HA); ভৌগোলিকভাবে বিতরিত ব্যবহারকারী বা DR-এর জন্য Multi-Region বিবেচনা করুন।

৩.৩ Shared Responsibility Model

AWS-এ নিরাপত্তা একটি ভাগ করা দায়িত্ব:
- AWS দায়ী "of the cloud" (cloud-এর নিরাপত্তা): ভৌত datacenter, হার্ডওয়্যার, নেটওয়ার্ক অবকাঠামো, হাইপারভাইজার।
- আপনি দায়ী "in the cloud" (cloud-এর ভেতরে নিরাপত্তা): আপনার ডাটা, OS প্যাচিং (EC2-তে), নেটওয়ার্ক কনফিগ (security group), IAM, এনক্রিপশন, অ্যাপ্লিকেশন নিরাপত্তা।

এটি বোঝা গুরুত্বপূর্ণ — অনেক নিরাপত্তা ঘটনা ঘটে কারণ ব্যবহারকারী ভাবে AWS সব সামলাচ্ছে, কিন্তু আসলে কনফিগারেশন (যেমন একটি পাবলিক S3 bucket) তাদেরই দায়িত্ব।

৩.৪ IAM — Identity and Access Management

IAM হলো AWS-এ কে কী করতে পারবে তা নিয়ন্ত্রণের সেবা — নিরাপত্তার ভিত্তি। মূল উপাদান:
- User: একজন ব্যক্তি বা অ্যাপ্লিকেশনের পরিচয় (দীর্ঘমেয়াদি credential)।
- Group: user-দের একটি সংগ্রহ (একসাথে permission দেওয়ার জন্য)।
- Role: একটি অস্থায়ী পরিচয় যা assume করা যায় — বিশেষত গুরুত্বপূর্ণ: একটি EC2 instance বা Lambda-কে role দিলে, তার ভেতরের কোড নিরাপদে অন্য AWS সেবা (যেমন S3) অ্যাক্সেস করতে পারে — হার্ডকোডেড credential ছাড়াই। এটিই প্রস্তাবিত পদ্ধতি।
- Policy: JSON ডকুমেন্টে লেখা অনুমতির নিয়ম (কোন action, কোন resource-এ, allow/deny)।

সবচেয়ে গুরুত্বপূর্ণ নীতি — Least Privilege: প্রতিটি পরিচয়কে শুধু ততটুকু অনুমতি দিন যতটুকু তার কাজে দরকার, এর বেশি নয়। অতিরিক্ত অনুমতি নিরাপত্তা ছিদ্র। কখনো credential কোডে হার্ডকোড করবেন না — role ব্যবহার করুন।

৩.৫ VPC — Cloud Networking

VPC (Virtual Private Cloud) হলো AWS-এর ভেতরে আপনার নিজস্ব, বিচ্ছিন্ন ভার্চুয়াল নেটওয়ার্ক — যেখানে আপনি সম্পূর্ণ নিয়ন্ত্রণে নিজের IP পরিসর, subnet ও রাউটিং সাজান। প্রোডাকশন আর্কিটেকচারে এটি অপরিহার্য। মূল উপাদান:
- Subnet: VPC-কে ছোট নেটওয়ার্ক খণ্ডে ভাগ করা, প্রায়ই প্রতি AZ-তে একটি করে।
- Public Subnet: ইন্টারনেট থেকে সরাসরি পৌঁছানো যায় (যেমন load balancer, bastion host এখানে)।
- Private Subnet: ইন্টারনেট থেকে সরাসরি পৌঁছানো যায় না (যেমন অ্যাপ সার্ভার, ডাটাবেস — নিরাপত্তার জন্য এখানে)।
- Internet Gateway (IGW): VPC-কে ইন্টারনেটের সাথে যুক্ত করে (public subnet-এর জন্য)।
- NAT Gateway: private subnet-এর রিসোর্সকে বাইরে যেতে দেয় (যেমন প্যাকেজ ডাউনলোড) কিন্তু বাইরে থেকে ভেতরে আসতে দেয় না — নিরাপত্তা রক্ষা করে।
- Security Group: instance-স্তরের একটি stateful ফায়ারওয়াল — কোন পোর্টে কোন ট্র্যাফিক ঢুকবে/বের হবে (যেমন "শুধু পোর্ট 443 খোলা")।
- NACL (Network ACL): subnet-স্তরের একটি stateless ফায়ারওয়াল (অতিরিক্ত স্তর)।

প্রস্তাবিত প্যাটার্ন: load balancer public subnet-এ; অ্যাপ সার্ভার ও ডাটাবেস private subnet-এ; security group দিয়ে কঠোরভাবে শুধু প্রয়োজনীয় ট্র্যাফিক অনুমোদন। ডাটাবেস কখনো সরাসরি ইন্টারনেট-এক্সপোজড নয়।

অংশ খ: Core AWS Services (বিভাগ অনুযায়ী)

৩.৬ Compute (গণনা)

  • EC2 (Elastic Compute Cloud): ভার্চুয়াল সার্ভার (IaaS)। সম্পূর্ণ নিয়ন্ত্রণ (OS, কনফিগ)। বিভিন্ন instance type (compute/memory/GPU-অপ্টিমাইজড)। Pricing: On-Demand (নমনীয়), Reserved/Savings Plan (দীর্ঘমেয়াদে সস্তা), Spot (অব্যবহৃত ক্ষমতা, খুব সস্তা কিন্তু যেকোনো সময় বন্ধ হতে পারে)।
  • Lambda (Serverless): কোনো সার্ভার ব্যবস্থাপনা নেই — শুধু একটি ফাংশন লেখেন, এটি event-এ (HTTP, queue message, file upload) চলে এবং শুধু চলার সময়টুকুর জন্য পেমেন্ট। auto-scale স্বয়ংক্রিয়। আদর্শ: event-driven, sporadic, বা অপ্রত্যাশিত workload।
  • ECS / EKS (Containers): container অর্কেস্ট্রেশন — ECS (AWS-এর নিজস্ব), EKS (managed Kubernetes)। Fargate = serverless container (instance ব্যবস্থাপনা ছাড়াই container চালানো)।
  • Elastic Beanstalk (PaaS): কোড আপলোড করলে AWS স্বয়ংক্রিয়ভাবে EC2, load balancer, scaling সব সেট করে — সরল ডিপ্লয়মেন্ট।

কখন কোনটি: পূর্ণ নিয়ন্ত্রণ/legacy → EC2; event-driven/সরল API → Lambda; container-ভিত্তিক microservices → ECS/EKS (+Fargate); দ্রুত সরল ডিপ্লয় → Beanstalk।

৩.৭ Storage (স্টোরেজ — অধ্যায় ৬-এর সাথে)

  • S3 (Simple Storage Service): Object storage — ছবি, ভিডিও, ব্যাকআপ, স্ট্যাটিক ওয়েবসাইট, data lake। প্রায় অসীম, উচ্চ durability। বিভিন্ন storage class (Standard, Infrequent Access, Glacier — কম-ব্যবহৃত ডাটার জন্য সস্তা archival)।
  • EBS (Elastic Block Store): Block storage — EC2-তে যুক্ত করা ভার্চুয়াল ডিস্ক (database, OS volume)। কম latency, একটি instance-এ attach।
  • EFS (Elastic File System): File storage — একাধিক EC2-তে শেয়ারড নেটওয়ার্ক ফাইল সিস্টেম (NFS)।

৩.৮ Database (ডাটাবেস — অধ্যায় ৪-এর সাথে)

  • RDS (Relational Database Service): managed SQL ডাটাবেস (MySQL, PostgreSQL, etc.) — AWS প্যাচিং, ব্যাকআপ, Multi-AZ failover সামলায় (অধ্যায় ১২)। Aurora = AWS-এর নিজস্ব উচ্চ-পারফরম্যান্স, MySQL/PostgreSQL-সঙ্গতিপূর্ণ ডাটাবেস (দ্রুত failover, auto-scaling storage)।
  • DynamoDB: managed NoSQL (key-value/document) — প্রায় অসীম scale, single-digit millisecond latency, serverless (অধ্যায় ৪, ১৩-এর AP/eventual consistency, tunable)। আদর্শ: বিশাল scale, সরল অ্যাক্সেস প্যাটার্ন।
  • ElastiCache: managed Redis/Memcached (অধ্যায় ৫) — caching ও session স্টোর।
  • Redshift: managed data warehouse — বিশাল analytics query (OLAP)।

কখন কোনটি: জটিল সম্পর্ক/লেনদেন → RDS/Aurora; বিশাল scale + সরল প্যাটার্ন → DynamoDB; caching → ElastiCache; analytics → Redshift।

৩.৯ Networking & Content Delivery

  • Route 53: managed DNS + health-check-ভিত্তিক DNS failover ও geo-routing (অধ্যায় ১২)।
  • CloudFront: CDN — edge location থেকে কনটেন্ট বিতরণ (অধ্যায় ৬); প্রায়ই S3-এর সামনে।
  • ELB (Elastic Load Balancing): ALB (Application LB — L7, HTTP, path/host routing), NLB (Network LB — L4, অতি-উচ্চ পারফরম্যান্স), CLB (পুরোনো)। অধ্যায় ১০-এর L4/L7 সরাসরি এখানে।
  • API Gateway: managed API Gateway (অধ্যায় ১৫) — routing, auth, rate limiting, প্রায়ই Lambda-র সামনে।

৩.১০ Messaging (অধ্যায় ৮-এর সাথে)

  • SQS: managed message queue (Standard/FIFO) — decoupling ও async।
  • SNS: managed Pub/Sub notification — fan-out (SNS→multiple SQS প্যাটার্ন)।
  • Kinesis: real-time streaming (Kafka-র মতো) — বিশাল ডাটা স্ট্রিম, analytics।
  • EventBridge: event bus — সার্ভিস ও SaaS-এর মধ্যে event-driven integration।

৩.১১ Monitoring, Security ও IaC

  • CloudWatch: metrics, logs, alarms, dashboards — auto-scaling trigger ও observability (অধ্যায় ৯, ১২)।
  • CloudTrail: সব AWS API কল-এর audit log (কে কী করল)।
  • Security: KMS (এনক্রিপশন কী ব্যবস্থাপনা), Secrets Manager (password/API key নিরাপদে সংরক্ষণ — কখনো কোডে নয়), WAF (web application firewall — অধ্যায় ৬), Shield (DDoS protection)।
  • IaC (Infrastructure as Code): CloudFormation (YAML/JSON-এ পুরো অবকাঠামো সংজ্ঞায়িত), CDK (কোড দিয়ে অবকাঠামো — Python/TS)। Terraform (তৃতীয় পক্ষ) ব্যাপকভাবে ব্যবহৃত। গুরুত্ব: অবকাঠামো ম্যানুয়ালি ক্লিক করে নয়, কোডে সংজ্ঞায়িত করলে তা reproducible, version-controlled ও নিরাপদ।

অংশ গ: Deploying Applications on AWS

৩.১২ তিনটি সাধারণ deployment মডেল

১. ক্লাসিক 3-Tier (EC2-ভিত্তিক):
সবচেয়ে প্রচলিত প্রথাগত আর্কিটেকচার (অধ্যায় ৩-এর 3-tier, AWS-এ):
- Route 53 (DNS) → CloudFront (CDN) → ALB (public subnet)
- ALB → Auto Scaling Group-এর EC2 instance (private subnet, একাধিক AZ — অধ্যায় ৯, ১২)
- EC2 → RDS Multi-AZ (private subnet) + ElastiCache (caching)
- স্ট্যাটিক asset → S3 + CloudFront

২. Serverless:
কোনো সার্ভার ব্যবস্থাপনা নেই, ব্যবহার-অনুযায়ী খরচ:
- CloudFront → API Gateway → Lambda → DynamoDB
- স্ট্যাটিক frontend → S3 + CloudFront
- আদর্শ: পরিবর্তনশীল/অপ্রত্যাশিত traffic, দ্রুত শুরু, কম operational বোঝা; কিন্তু cold start ও vendor lock-in বিবেচনা।

৩. Container-based (microservices):
- ECR (container registry)-এ image; ECS/EKS (+Fargate) container চালায়; ALB ট্র্যাফিক বণ্টন; service discovery; CloudWatch monitoring — অধ্যায় ১৫/১৬-এর microservices প্যাটার্ন AWS-এ।

৩.১৩ CI/CD ও Deployment কৌশল

কোড থেকে প্রোডাকশনে স্বয়ংক্রিয়ভাবে পৌঁছানোর pipeline:
- CodeCommit/GitHub (source) → CodeBuild (build/test) → CodeDeploy (deploy) → CodePipeline (পুরো প্রবাহ অর্কেস্ট্রেট)।
- Deployment কৌশল: Rolling (ধীরে ধীরে instance আপডেট), Blue-Green (পুরোনো ও নতুন পরিবেশ পাশাপাশি, এক ঝটকায় switch — দ্রুত rollback), Canary (অল্প ট্র্যাফিক নতুন সংস্করণে আগে — অধ্যায় ১৬)।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনাকে একটি ই-কমার্স অ্যাপ AWS-এ ডিপ্লয় করতে বলা হলো, যা সাধারণ দিনে কম traffic কিন্তু সেল-এ ২০ গুণ traffic পায়, এবং HA ও নিরাপত্তা অপরিহার্য।

আগের সব অধ্যায়ের ধারণা AWS সেবায় ম্যাপ করে একটি সম্পূর্ণ সমাধান দাঁড়ায়:
- ব্যবহারকারী → Route 53 (DNS) → CloudFront (CDN — স্ট্যাটিক asset ও ছবি দ্রুত, অধ্যায় ৬)।
- ডাইনামিক অনুরোধ → ALB (L7 load balancer, public subnet, অধ্যায় ১০)।
- ALB → Auto Scaling Group-এর EC2 (private subnet, ২+ AZ) — সেল-এ CPU বাড়লে স্বয়ংক্রিয়ভাবে আরও instance (অধ্যায় ৯), সার্ভার stateless (session ElastiCache/Redis-এ, অধ্যায় ৯)।
- ডাটা → RDS Multi-AZ (primary + standby, automatic failover, অধ্যায় ১২) জটিল/transaction ডাটার জন্য; DynamoDB কার্ট/সেশনের জন্য (অধ্যায় ৪)।
- ছবি/ভিডিও → S3 (object storage) + CloudFront।
- ভারী কাজ (ইমেল, অর্ডার প্রক্রিয়া) → SQS + Lambda/Worker (async, অধ্যায় ৮)।
- নিরাপত্তা → VPC (private subnet-এ DB/app), Security Group (কঠোর), IAM role (হার্ডকোডেড credential নয়), Secrets Manager (DB password), WAF + Shield (CloudFront-এ DDoS/আক্রমণ রোধ)।
- observability → CloudWatch (metrics, alarm, auto-scaling trigger)।
- পুরো অবকাঠামো → CloudFormation/Terraform (IaC — reproducible, version-controlled)।
- ডিপ্লয় → CodePipeline + blue-green/canary।

এই একটি আর্কিটেকচারে পুরো বইয়ের ধারণা একসাথে বাস্তব AWS সেবায় রূপ নেয় — এবং এটিই একটি বাস্তব প্রোডাকশন ই-কমার্স ডিপ্লয়মেন্টের কাঠামো।

৫. ভিজ্যুয়াল আর্কিটেকচার ডায়াগ্রাম (Visual Architecture Diagrams)

ডায়াগ্রাম ব্যাখ্যা:
- Components: DNS, CDN+WAF, ALB (public), EC2 ASG (private, ২ AZ), RDS Multi-AZ, ElastiCache, SQS+Worker।
- Flow: ব্যবহারকারী → DNS → CDN (স্ট্যাটিক) বা → ALB → EC2 → DB/cache; ভারী কাজ SQS-এ async।
- Failure Points: একটি AZ মারা গেলে অন্য AZ-এর EC2 ও RDS standby কাজ চালায় (HA)। ALB ও CloudFront নিজে redundant।
- Scaling: ASG traffic অনুযায়ী EC2 যোগ/সরায়; stateless সার্ভার (session ElastiCache-এ) এটি সম্ভব করে।

Serverless আর্কিটেকচার

graph LR U[Client] --> CF[CloudFront] CF --> S3[(S3 - frontend)] CF --> AG[API Gateway] AG --> L[Lambda functions] L --> D[(DynamoDB)] L --> SNS[SNS/SQS - async]

ব্যাখ্যা: কোনো সার্ভার ব্যবস্থাপনা নেই — API Gateway অনুরোধ Lambda-তে রুট করে, Lambda DynamoDB-তে কাজ করে ও auto-scale করে; ব্যবহার-অনুযায়ী খরচ। পরিবর্তনশীল traffic ও দ্রুত শুরুর জন্য আদর্শ।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples — প্রোডাকশনে ব্যবহারযোগ্য)

IAM Least-Privilege Policy (JSON)

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::my-app-bucket/*"
  }]
}

ব্যাখ্যা: এই policy শুধু একটি নির্দিষ্ট bucket-এ object পড়া/লেখার অনুমতি দেয় — আর কিছুই নয় (least privilege)। এটি একটি IAM role-এ যুক্ত করে EC2/Lambda-তে দিলে, কোড হার্ডকোডেড credential ছাড়াই S3 অ্যাক্সেস করতে পারে। কখনো "Action": "*" বা "Resource": "*" দেবেন না যদি না সত্যিই দরকার।

Lambda ফাংশন (Python — serverless)

import json, boto3

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('Orders')

def handler(event, context):
    # API Gateway থেকে আসা অনুরোধ
    body = json.loads(event['body'])
    table.put_item(Item={                  # DynamoDB-তে লেখা
        'order_id': body['order_id'],
        'user_id': body['user_id'],
        'amount': body['amount']
    })
    return {
        'statusCode': 201,
        'body': json.dumps({'status': 'created'})
    }
    # কোনো সার্ভার নেই — AWS স্বয়ংক্রিয়ভাবে scale করে, শুধু execution-এর খরচ

ব্যাখ্যা: এই Lambda একটি API Gateway অনুরোধে চলে, DynamoDB-তে অর্ডার লেখে, ও উত্তর দেয়। কোনো সার্ভার ব্যবস্থাপনা নেই; traffic বাড়লে AWS স্বয়ংক্রিয়ভাবে অনেক copy চালায়। DynamoDB অ্যাক্সেস হয় Lambda-র IAM role দিয়ে (credential ছাড়াই)। বিবেচনা: cold start (প্রথম invocation-এ সামান্য বিলম্ব)।

CloudFormation IaC (YAML — reproducible অবকাঠামো)

Resources:
  MyBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: my-app-static-assets
      PublicAccessBlockConfiguration:    # নিরাপত্তা: পাবলিক অ্যাক্সেস ব্লক
        BlockPublicAcls: true
        IgnorePublicAcls: true

  MyTable:
    Type: AWS::DynamoDB::Table
    Properties:
      TableName: Orders
      BillingMode: PAY_PER_REQUEST       # auto-scale, ব্যবহার-অনুযায়ী
      AttributeDefinitions:
        - { AttributeName: order_id, AttributeType: S }
      KeySchema:
        - { AttributeName: order_id, KeyType: HASH }

ব্যাখ্যা: এই YAML একটি S3 bucket ও একটি DynamoDB table সংজ্ঞায়িত করে — ম্যানুয়ালি console-এ ক্লিক না করে। সুবিধা: এটি version-controlled (Git-এ), reproducible (একই কনফিগ বারবার ডিপ্লয়), এবং নিরাপদ (যেমন PublicAccessBlock দিয়ে ভুলবশত পাবলিক bucket রোধ)। প্রোডাকশনে সব অবকাঠামো এভাবে IaC-তে রাখুন — ম্যানুয়াল পরিবর্তন এড়ান।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Netflix: সম্পূর্ণভাবে AWS-এ চলে — EC2, S3, auto-scaling, ও বিশাল microservices fleet; AWS-এর সবচেয়ে বিখ্যাত বড় গ্রাহক।
  • Airbnb, Lyft, Pinterest: AWS-এ scale করেছে — RDS/Aurora, DynamoDB, S3, ElastiCache, ও container/serverless মিশ্রণ ব্যবহার করে।
  • Serverless adoption: অনেক স্টার্টআপ ও এন্টারপ্রাইজ Lambda + API Gateway + DynamoDB দিয়ে দ্রুত, কম-operational অ্যাপ বানায় (যেমন event-driven পাইপলাইন)।
  • Capital One (ব্যাংকিং): AWS-এ বড় আকারে স্থানান্তরিত — দেখায় নিয়ন্ত্রিত শিল্পেও cloud নিরাপদে ব্যবহার সম্ভব (IAM, KMS, VPC, compliance সহ)।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- credential কোডে হার্ডকোড করা — IAM role ব্যবহার না করা।
- ডাটাবেস public subnet-এ বা সরাসরি ইন্টারনেট-এক্সপোজড রাখা।
- S3 bucket ভুলবশত পাবলিক রাখা — ডাটা ফাঁস।

Intermediate Mistakes:
- শুধু একটি AZ-তে ডিপ্লয় — HA ছাড়া (একটি AZ মারা গেলে পুরো অ্যাপ ডাউন)।
- least privilege উপেক্ষা করে অতিরিক্ত wide IAM permission (*)।
- ভুল সেবা পছন্দ — যেমন সরল API-তে EC2 fleet (যেখানে Lambda যথেষ্ট), বা বিশাল scale-এ ভুল ডাটাবেস।

Production Mistakes:
- অবকাঠামো ম্যানুয়ালি console-এ তৈরি (IaC ছাড়া) — অ-reproducible, ভুলপ্রবণ, drift।
- secret/password Secrets Manager-এর বদলে environment/কোডে রাখা।
- খরচ মনিটরিং না করা — Spot/Reserved না ব্যবহার করে অপ্রয়োজনে বিল বৃদ্ধি; runaway auto-scaling-এ MaxSize না রাখা।
- CloudWatch alarm/monitoring সেট না করা — সমস্যা নীরবে।

Scalability Mistakes:
- EC2 stateful রেখে auto-scaling (session ElastiCache-এ না রাখা — অধ্যায় ৯)।
- DynamoDB-তে খারাপ partition key — hot partition (অধ্যায় ১০)।
- ডাটাবেসকে scaling পরিকল্পনায় না আনা (অ্যাপ scale হয় কিন্তু RDS bottleneck)।

Architecture Mistakes:
- Serverless-এর cold start ও vendor lock-in বিবেচনা না করা।
- সবকিছু একটি সেবায় চাপানো — সঠিক কাজে সঠিক সেবা (polyglot) না বাছা।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: Region আর Availability Zone-এর পার্থক্য কী?

Region একটি বৃহৎ ভৌগোলিক এলাকা (যেমন মুম্বাই); প্রতিটি region-এ একাধিক Availability Zone (AZ) — পৃথক পাওয়ার/কুলিং/নেটওয়ার্কের স্বতন্ত্র datacenter, কিন্তু দ্রুত সংযুক্ত। একাধিক AZ-তে ডিপ্লয় করলে একটি AZ-এর বিপর্যয়েও অ্যাপ চলে (HA)।

Intermediate প্রশ্ন: EC2, Lambda আর ECS-এর মধ্যে কখন কোনটি বাছবেন?

EC2 — পূর্ণ নিয়ন্ত্রণ, legacy, স্থিতিশীল workload। Lambda — event-driven, sporadic/অপ্রত্যাশিত traffic, কম operational বোঝা (কিন্তু cold start)। ECS/EKS — container-ভিত্তিক microservices, যেখানে orchestration ও portability দরকার।

Intermediate প্রশ্ন: Public আর Private subnet-এ কী রাখবেন এবং কেন?

Public subnet-এ ইন্টারনেট-মুখী রিসোর্স (load balancer, bastion); Private subnet-এ অ্যাপ সার্ভার ও ডাটাবেস (সরাসরি ইন্টারনেট থেকে অপৌঁছানো — নিরাপত্তা)। Private subnet বাইরে যেতে NAT Gateway ব্যবহার করে। ডাটাবেস কখনো public নয়।

Advanced প্রশ্ন: AWS-এ একটি অ্যাপের নিরাপত্তা কীভাবে নিশ্চিত করবেন?

Shared Responsibility বুঝে — VPC + private subnet-এ DB/app; কঠোর Security Group; IAM least privilege + role (হার্ডকোডেড credential নয়); Secrets Manager-এ secret; KMS দিয়ে এনক্রিপশন (at-rest ও in-transit); CloudFront-এ WAF + Shield; CloudTrail-এ audit; এবং S3 public access block।

System Design প্রশ্ন: একটি scalable, HA ই-কমার্স অ্যাপ AWS-এ ডিজাইন করুন।

Route 53 → CloudFront (CDN+WAF) → ALB (public, multi-AZ) → Auto Scaling Group-এর stateless EC2 (private, ২+ AZ; session ElastiCache-এ) → RDS Multi-AZ (transaction) + DynamoDB (cart) → S3 (media) → SQS+Lambda (async); IAM role, Secrets Manager, VPC নিরাপত্তা; CloudWatch monitoring + auto-scaling; CloudFormation IaC; CodePipeline + blue-green deploy।

১০. সেরা চর্চা (Best Practices — সরাসরি প্রয়োগযোগ্য)

  • IAM role + least privilege — কখনো credential হার্ডকোড করবেন না; শুধু প্রয়োজনীয় অনুমতি।
  • অন্তত ২ AZ-তে ডিপ্লয় (HA); DB-তে Multi-AZ; গুরুত্বপূর্ণ হলে Multi-Region।
  • DB/app private subnet-এ; LB public-এ; security group কঠোর; S3 public access block।
  • secret সবসময় Secrets Manager/Parameter Store-এ — কোড/env-এ নয়।
  • সব অবকাঠামো IaC-তে (CloudFormation/CDK/Terraform) — reproducible ও version-controlled।
  • সঠিক কাজে সঠিক সেবা — EC2/Lambda/ECS, RDS/DynamoDB; polyglot।
  • stateless app + ElastiCache session — মসৃণ auto-scaling (অধ্যায় ৯)।
  • CloudWatch alarm + খরচ মনিটরিং; Spot/Reserved দিয়ে খরচ অপ্টিমাইজ; auto-scaling-এ MaxSize।
  • CI/CD pipeline + blue-green/canary — নিরাপদ, স্বয়ংক্রিয় ডিপ্লয়।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Cloud মডেল: IaaS (EC2) → PaaS (Beanstalk/Lambda) → SaaS; যত উপরে তত কম নিয়ন্ত্রণ ও বোঝা।
- Global Infra: Region > AZ > Edge; HA-তে Multi-AZ অপরিহার্য।
- Shared Responsibility: AWS "of the cloud", আপনি "in the cloud"।
- IAM: user/group/role/policy; least privilege ও role (credential নয়)।
- VPC: public/private subnet, IGW, NAT, Security Group; DB private-এ।
- Core Services: Compute (EC2/Lambda/ECS), Storage (S3/EBS/EFS), Database (RDS/Aurora/DynamoDB/ElastiCache/Redshift), Networking (Route53/CloudFront/ELB/API GW), Messaging (SQS/SNS/Kinesis/EventBridge), Ops (CloudWatch/CloudTrail), Security (KMS/Secrets Manager/WAF), IaC (CloudFormation/CDK)।
- Deployment: 3-tier (EC2+ASG+ALB+RDS), Serverless (Lambda+API GW+DynamoDB), Container (ECS/EKS); CI/CD (CodePipeline) + blue-green/canary।

গুরুত্বপূর্ণ পরিভাষা: IaaS/PaaS/SaaS, Region, AZ, Edge Location, Multi-AZ, Shared Responsibility, IAM, Role, Policy, Least Privilege, VPC, Public/Private Subnet, Internet Gateway, NAT Gateway, Security Group, EC2, Lambda, ECS/EKS/Fargate, S3/EBS/EFS, RDS/Aurora/DynamoDB/ElastiCache, Route 53, CloudFront, ALB/NLB, API Gateway, SQS/SNS/Kinesis, CloudWatch, KMS, Secrets Manager, WAF, CloudFormation/IaC, CI/CD, Blue-Green, Canary।

১২. অনুশীলন (Practice Exercises)

Conceptual:
1. IaaS, PaaS ও SaaS-এর পার্থক্য AWS উদাহরণসহ লিখুন।
2. কেন ডাটাবেস public subnet-এ রাখা একটি নিরাপত্তা ঝুঁকি?

Practical:
3. একটি IAM policy লিখুন যা শুধু একটি নির্দিষ্ট DynamoDB table-এ read অনুমতি দেয় (least privilege)।
4. EC2-ভিত্তিক বনাম Lambda-ভিত্তিক একটি API-র খরচ ও scaling আচরণের তুলনা করুন।

Architecture Design:
5. একটি ফটো-শেয়ারিং অ্যাপের জন্য সম্পূর্ণ AWS আর্কিটেকচার ডিজাইন করুন (compute, storage, DB, CDN, async, নিরাপত্তা সহ) — প্রতিটি সেবা পছন্দের কারণসহ।

Scenario-Based:
6. আপনার auto-scaled EC2 অ্যাপে কিছু ব্যবহারকারী মাঝে মাঝে logout হয়ে যাচ্ছেন। AWS-এর প্রেক্ষাপটে কারণ ও সমাধান কী?

Interview Challenge:
7. একজন ইন্টারভিউয়ারকে একটি HA, secure, scalable অ্যাপের সম্পূর্ণ AWS ডিপ্লয়মেন্ট বোঝান — প্রতিটি স্তরে কোন সেবা ও কেন।
