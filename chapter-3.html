অধ্যায় ৩: Client-Server Model, 3-Tier Architecture, HTTP ও REST API

১. অধ্যায় পরিচিতি (Chapter Introduction)

আগের অধ্যায়ে আমরা সিস্টেমের গুণাগুণ (scalability, latency ইত্যাদি) শিখেছি। কিন্তু একটি সিস্টেম আসলে কীভাবে যোগাযোগ করে? আপনি যখন ব্রাউজারে একটি ওয়েবসাইট খোলেন, তখন আপনার কম্পিউটার আর দূরের সার্ভারের মধ্যে ঠিক কী ঘটে?

এই অধ্যায়ে আমরা ইন্টারনেটের সবচেয়ে মৌলিক যোগাযোগ মডেল — Client-Server Model (ক্লায়েন্ট-সার্ভার মডেল) শিখব। এরপর দেখব কীভাবে বড় অ্যাপ্লিকেশনকে স্তরে স্তরে সাজানো হয় (3-Tier Architecture)। তারপর শিখব ওয়েবের ভাষা HTTP, এবং সবশেষে আধুনিক API ডিজাইনের মান REST।

এগুলো এমন ভিত্তি, যা ছাড়া পরবর্তী অধ্যায়ের কোনো উন্নত ধারণা (microservices, API Gateway, caching) বোঝা সম্ভব নয়।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি বুঝতে পারবেন:

  • Client-Server Model কীভাবে কাজ করে এবং কেন এটি ইন্টারনেটের ভিত্তি
  • 3-Tier Architecture-এর তিনটি স্তর এবং তাদের দায়িত্ব
  • HTTP কী, এর Request/Response গঠন, Method ও Status Code
  • REST কী এবং একটি ভালো REST API Endpoint কীভাবে ডিজাইন করতে হয়
  • Stateless যোগাযোগ কেন গুরুত্বপূর্ণ

৩. মূল ধারণা (Core Concepts)

৩.১ Client-Server Model (ক্লায়েন্ট-সার্ভার মডেল)

এটি একটি যোগাযোগ মডেল যেখানে দুটি পক্ষ থাকে:

  • Client (ক্লায়েন্ট): যে অনুরোধ (request) পাঠায় — যেমন আপনার ব্রাউজার, মোবাইল অ্যাপ।
  • Server (সার্ভার): যে অনুরোধ গ্রহণ করে, প্রক্রিয়া করে এবং উত্তর (response) ফেরত দেয়।

মৌলিক প্রবাহ: Client একটি অনুরোধ পাঠায় → Server সেটি প্রক্রিয়া করে (ডাটাবেস থেকে তথ্য আনে) → Server উত্তর ফেরত পাঠায়।

এই মডেলের মূল বৈশিষ্ট্য হলো দায়িত্ব বিভাজন — Client শুধু চায়, Server দেয়। একটি Server একসাথে হাজারো Client-কে সেবা দিতে পারে।

৩.২ 3-Tier Architecture (থ্রি-টিয়ার আর্কিটেকচার)

বড় অ্যাপ্লিকেশনকে তিনটি যৌক্তিক স্তরে (tier/layer) ভাগ করা হয়, যাতে প্রতিটি স্তর স্বাধীনভাবে পরিবর্তন ও scale করা যায়।

  1. Presentation Tier (উপস্থাপন স্তর): ব্যবহারকারী যা দেখে — UI, ওয়েব পেজ, মোবাইল স্ক্রিন। (Frontend)
  2. Application/Logic Tier (যুক্তি স্তর): ব্যবসায়িক যুক্তি (business logic) — হিসাব, নিয়ম, প্রক্রিয়াকরণ। (Backend)
  3. Data Tier (ডাটা স্তর): তথ্য সংরক্ষণ — Database, file storage।

সুবিধা: একটি স্তরে পরিবর্তন আনলে অন্য স্তরে প্রভাব পড়ে না। যেমন UI বদলালেও ডাটাবেস স্পর্শ করতে হয় না। প্রতিটি স্তর আলাদাভাবে scale করা যায়।

৩.৩ HTTP Basics (এইচটিটিপি)

HTTP (HyperText Transfer Protocol) হলো সেই প্রোটোকল যার মাধ্যমে Client ও Server ওয়েবে কথা বলে। এটি একটি request-response প্রোটোকল এবং stateless — অর্থাৎ প্রতিটি অনুরোধ স্বাধীন, Server আগের অনুরোধ মনে রাখে না।

HTTP Methods (গুরুত্বপূর্ণ):

Method কাজ উদাহরণ
GET তথ্য পড়া (read) ব্যবহারকারীর প্রোফাইল আনা
POST নতুন তথ্য তৈরি (create) নতুন অ্যাকাউন্ট খোলা
PUT সম্পূর্ণ আপডেট (replace) পুরো প্রোফাইল বদলানো
PATCH আংশিক আপডেট শুধু ইমেইল বদলানো
DELETE মুছে ফেলা অ্যাকাউন্ট মুছে ফেলা

HTTP Status Code (গুরুত্বপূর্ণ শ্রেণি):

  • 2xx — সফল: 200 OK, 201 Created
  • 3xx — রিডাইরেক্ট: 301 Moved Permanently, 304 Not Modified
  • 4xx — Client-এর ভুল: 400 Bad Request, 401 Unauthorized, 404 Not Found
  • 5xx — Server-এর ভুল: 500 Internal Server Error, 503 Service Unavailable

একটি HTTP Request-এর গঠন:
- Method + URL (যেমন GET /users/123)
- Headers (যেমন Authorization, Content-Type)
- Body (POST/PUT-এ ডাটা থাকে)

৩.৪ REST API (রেস্ট এপিআই)

REST (Representational State Transfer) হলো API ডিজাইনের একটি স্থাপত্য শৈলী, যা HTTP-এর ওপর ভিত্তি করে গড়া। REST অনুসরণকারী API-কে বলা হয় RESTful API।

REST-এর মূল নীতি:

  • Resource-ভিত্তিক: সবকিছুকে "resource" হিসেবে দেখা হয় (user, order, product) এবং প্রতিটির একটি URL থাকে।
  • HTTP Method ব্যবহার: কাজের ধরন বোঝাতে method ব্যবহার (GET পড়া, POST তৈরি)।
  • Stateless: প্রতিটি অনুরোধ সম্পূর্ণ তথ্য বহন করে; Server সেশন মনে রাখে না।
  • JSON ফরম্যাট: সাধারণত ডাটা আদান-প্রদান হয় JSON-এ।

ভালো REST Endpoint ডিজাইন:

GET    /users          → সব ব্যবহারকারীর তালিকা
GET    /users/123      → নির্দিষ্ট ব্যবহারকারী
POST   /users          → নতুন ব্যবহারকারী তৈরি
PUT    /users/123      → ব্যবহারকারী আপডেট
DELETE /users/123      → ব্যবহারকারী মুছে ফেলা
GET    /users/123/orders → ঐ ব্যবহারকারীর অর্ডার

নিয়ম: URL-এ noun (বিশেষ্য) ব্যবহার করুন, verb (ক্রিয়া) নয়। /getUser খারাপ; GET /users/123 ভালো — কারণ কাজটি method-ই বলে দেয়।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনি একটি মোবাইল অ্যাপ আর একটি ওয়েবসাইট একসাথে বানাচ্ছেন — দুটোই একই ব্যবহারকারীর ডাটা দেখাবে। আপনি কি দুটোতে আলাদাভাবে ডাটাবেস লজিক লিখবেন?

না। আপনি একটি REST API বানাবেন যা ব্যবসায়িক যুক্তি ও ডাটা সামলায়, আর ওয়েব ও মোবাইল উভয়ই সেই একই API-কে অনুরোধ পাঠাবে। এটিই 3-Tier ও Client-Server-এর বাস্তব শক্তি:

  • একবার লিখুন, সবখানে ব্যবহার করুন — একই API ওয়েব, মোবাইল, এমনকি তৃতীয় পক্ষের জন্যও।
  • স্বাধীন পরিবর্তন — Backend বদলালেও Frontend অপরিবর্তিত থাকে যদি API চুক্তি (contract) একই থাকে।

API ছাড়া প্রতিটি প্ল্যাটফর্মে আলাদা কোড লিখতে হতো — যা রক্ষণাবেক্ষণ দুঃস্বপ্নে পরিণত হতো।

৫. ভিজ্যুয়াল আর্কিটেকচার ডায়াগ্রাম (Visual Architecture Diagrams)

Mermaid: একটি REST অনুরোধের জীবনচক্র

sequenceDiagram participant C as Client (Browser) participant S as Server (API) participant DB as Database C->>S: GET /users/123 (HTTP Request) S->>DB: SELECT * FROM users WHERE id=123 DB-->>S: User Data S-->>C: 200 OK + JSON Body

ডায়াগ্রাম ব্যাখ্যা:

  • Components: Client (Presentation), API Server (Application), Database (Data) — তিনটি স্তর।
  • Request Flow: Client GET /users/123 পাঠায় → Server ডাটাবেসে query করে → ডাটা পেয়ে JSON হিসেবে ফেরত দেয় → 200 OK।
  • Failure Points: ব্যবহারকারী না থাকলে Server 404 Not Found; ডাটাবেস ডাউন থাকলে 503।
  • Scaling: প্রতিটি স্তর আলাদাভাবে scale করা যায় — যেমন একাধিক API Server-এর সামনে Load Balancer বসানো (অধ্যায় ২)।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples)

একটি REST API (Node.js / Express)

const express = require('express');
const app = express();
app.use(express.json());  // JSON body পড়ার জন্য

// GET — ব্যবহারকারী পড়া (read)
app.get('/users/:id', (req, res) => {
  const user = { id: req.params.id, name: 'Karim' };
  res.status(200).json(user);   // 200 OK + JSON
});

// POST — নতুন ব্যবহারকারী তৈরি (create)
app.post('/users', (req, res) => {
  const newUser = req.body;     // Client-এর পাঠানো ডাটা
  // ... ডাটাবেসে সংরক্ষণ ...
  res.status(201).json(newUser); // 201 Created
});

// DELETE — মুছে ফেলা
app.delete('/users/:id', (req, res) => {
  // ... ডাটাবেস থেকে মুছুন ...
  res.status(204).send();        // 204 No Content
});

app.listen(3000);

ব্যাখ্যা:
- প্রতিটি route একটি resource (/users) ও একটি HTTP method-এর সমন্বয়।
- res.status(...) দিয়ে সঠিক status code পাঠানো হচ্ছে — 201 তৈরি, 204 মুছে ফেলা।
- API stateless — প্রতিটি অনুরোধে প্রয়োজনীয় সব তথ্য (যেমন :id) থাকে।

সীমাবদ্ধতা: এখানে authentication নেই; প্রোডাকশনে প্রতিটি অনুরোধে Authorization header যাচাই করতে হবে এবং ভুল ইনপুটে 400 ফেরত দিতে হবে।

সরল HTTP Client (Python)

import requests

# Server-এ GET অনুরোধ পাঠানো
response = requests.get("https://api.example.com/users/123")

print(response.status_code)   # 200
print(response.json())        # {'id': 123, 'name': 'Karim'}

ব্যাখ্যা: এটি Client-এর ভূমিকা দেখায় — অনুরোধ পাঠানো ও উত্তর গ্রহণ করা। status_code দিয়ে সফলতা যাচাই করা হয়।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Twitter/X: তাদের পাবলিক REST API তৃতীয় পক্ষের ডেভেলপারদের টুইট পড়া/পোস্ট করার সুযোগ দেয় — একই backend, বহু Client।
  • Stripe (পেমেন্ট): ইন্ডাস্ট্রির সবচেয়ে প্রশংসিত REST API-এর একটি; পরিষ্কার resource-ভিত্তিক endpoint ও নির্ভরযোগ্য status code-এর জন্য বিখ্যাত।
  • Amazon: তাদের প্রতিটি অভ্যন্তরীণ টিম API-এর মাধ্যমে যোগাযোগ করে (বিখ্যাত "Bezos API Mandate") — এটিই পরে microservices সংস্কৃতির ভিত্তি হয়।
  • GitHub: সম্পূর্ণ প্ল্যাটফর্ম একটি well-documented REST (ও পরে GraphQL) API-এর ওপর দাঁড়িয়ে।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- URL-এ verb ব্যবহার (/createUser) — REST নীতির বিরুদ্ধে।
- সব ক্ষেত্রে 200 OK ফেরত দেওয়া, এমনকি ত্রুটিতেও।

Intermediate Mistakes:
- GET অনুরোধে ডাটা পরিবর্তন করা (GET হওয়া উচিত শুধু read, side-effect ছাড়া)।
- ভুল status code (ব্যবহারকারী না পেয়েও 200 দেওয়া, 404-এর বদলে)।

Production Mistakes:
- Stateless নীতি ভেঙে Server-এ সেশন স্টেট রাখা — যা horizontal scaling কঠিন করে।
- API versioning না রাখা (/v1/users) — ফলে পরিবর্তনে পুরোনো Client ভেঙে পড়ে।

Scalability Mistakes:
- Server-side session ব্যবহার করা, যা একাধিক সার্ভারে ভাগ করা কঠিন করে।

Architecture Mistakes:
- Presentation Tier-এ business logic মিশিয়ে ফেলা — স্তর বিভাজনের উদ্দেশ্য নষ্ট হয়।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: HTTP-তে GET আর POST-এর পার্থক্য কী?

GET তথ্য পড়ে এবং side-effect থাকে না; POST নতুন তথ্য তৈরি করে এবং body-তে ডাটা বহন করে।

Intermediate প্রশ্ন: REST API "stateless" বলতে কী বোঝায়?

প্রতিটি অনুরোধ স্বাধীন ও সম্পূর্ণ — Server আগের অনুরোধের কোনো অবস্থা মনে রাখে না। এটি horizontal scaling সহজ করে, কারণ যেকোনো সার্ভার যেকোনো অনুরোধ সামলাতে পারে।

Advanced প্রশ্ন: PUT আর PATCH-এর পার্থক্য কী?

PUT সম্পূর্ণ resource প্রতিস্থাপন করে (idempotent); PATCH শুধু নির্দিষ্ট অংশ আপডেট করে। যেমন শুধু ইমেইল বদলাতে PATCH উপযুক্ত।

System Design প্রশ্ন: একটি ব্লগ প্ল্যাটফর্মের জন্য REST API endpoint ডিজাইন করুন।

Resource-ভিত্তিক: GET /posts, POST /posts, GET /posts/{id}, PUT /posts/{id}, DELETE /posts/{id}, এবং নেস্টেড সম্পর্কের জন্য GET /posts/{id}/comments, POST /posts/{id}/comments। সঠিক status code ও /v1/ versioning যুক্ত করুন।

১০. সেরা চর্চা (Best Practices)

  • Resource-ভিত্তিক URL ব্যবহার করুন — noun, verb নয়; বহুবচন (/users)।
  • সঠিক HTTP method ও status code ব্যবহার করুন।
  • API versioning রাখুন (/v1/) যাতে ভবিষ্যৎ পরিবর্তনে পুরোনো Client না ভাঙে।
  • Stateless রাখুন — সেশন স্টেট Server-এ নয়, token (যেমন JWT) বা Client-এ রাখুন।
  • নিরাপত্তা: প্রতিটি অনুরোধে authentication যাচাই করুন; HTTPS ব্যবহার করুন।
  • পরিষ্কার error response দিন — ত্রুটির কারণসহ JSON বার্তা।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Client-Server Model = Client অনুরোধ পাঠায়, Server প্রক্রিয়া করে উত্তর দেয়।
- 3-Tier Architecture = Presentation, Application (Logic), Data — তিনটি স্বাধীন স্তর।
- HTTP = ওয়েবের stateless request-response প্রোটোকল; Method (GET/POST/PUT/DELETE) ও Status Code (2xx/4xx/5xx)।
- REST API = resource-ভিত্তিক, stateless, HTTP method-নির্ভর API ডিজাইন শৈলী; সাধারণত JSON।

গুরুত্বপূর্ণ পরিভাষা: Client, Server, Tier, HTTP, Stateless, Method, Status Code, Resource, REST, Endpoint, JSON, Idempotent, Versioning।
