অধ্যায় ২০: Scaling to Millions, AWS Auto Scaling ও Load Balancers at Internet Scale

১. অধ্যায় পরিচিতি (Chapter Introduction)

এই অধ্যায়টি পুরো বইয়ের একটি বাস্তব সংশ্লেষণ (synthesis)। আমরা এখন পর্যন্ত প্রতিটি ধারণা আলাদাভাবে এবং কেস স্টাডিতে দেখেছি। এই অধ্যায়ে আমরা একটি ভিন্ন দৃষ্টিকোণ নেব — একটি অ্যাপ্লিকেশনের যাত্রা: একটি একক সার্ভার থেকে শুরু করে কীভাবে ধাপে ধাপে কোটি ব্যবহারকারী পর্যন্ত পৌঁছানো যায়।

বাস্তবে কেউ প্রথম দিনেই একটি ১০০-সার্ভারের distributed system বানায় না — সেটি হবে over-engineering। বরং আপনি একটি সরল সিস্টেম দিয়ে শুরু করেন, এবং প্রতিটি bottleneck আসার সাথে সাথে নির্দিষ্ট কৌশল প্রয়োগ করেন। এই অধ্যায়ে আমরা সেই বিবর্তনের পথটি ধাপে ধাপে দেখব — প্রতিটি ধাপে "কোন সমস্যা এল, এবং কোন সমাধান প্রয়োগ করলাম" — যা বইয়ের সব ধারণাকে একটি ব্যবহারিক ক্রমে সাজায়।

এরপর আমরা গভীরে যাব AWS Auto Scaling-এর বাস্তব কাজ (অধ্যায় ৯-এর তত্ত্বের প্রায়োগিক রূপ), এবং সবশেষে internet-scale load balancing — কীভাবে কোটি কোটি অনুরোধ বিশ্বজুড়ে বণ্টন করা হয় (DNS, Anycast, multi-tier load balancing)। এই অধ্যায় শেষে আপনি একটি অ্যাপকে শূন্য থেকে internet-scale পর্যন্ত নিয়ে যাওয়ার সম্পূর্ণ মানচিত্র পাবেন।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি গভীরভাবে বুঝতে ও প্রয়োগ করতে পারবেন:

  • একটি অ্যাপের scaling যাত্রা — এক সার্ভার থেকে কোটি ব্যবহারকারী পর্যন্ত, ধাপে ধাপে
  • প্রতিটি ধাপে কোন bottleneck আসে এবং কোন কৌশল তা সমাধান করে
  • Database scaling গভীরভাবে — read replica, caching, sharding-এর ক্রম
  • AWS Auto Scaling-এর বাস্তব কাজ — ASG, launch template, scaling policy, lifecycle
  • Internet-scale Load Balancing — DNS, Anycast, GSLB, multi-tier LB
  • কখন কোন কৌশল প্রয়োগ করতে হয় (এবং কখন নয় — premature optimization এড়ানো)

৩. মূল ধারণা (Core Concepts)

অংশ ক: Scaling Journey — এক সার্ভার থেকে কোটি ব্যবহারকারী

নিচে একটি অ্যাপের বিবর্তন ধাপে ধাপে। প্রতিটি ধাপ একটি নির্দিষ্ট bottleneck-এর প্রতিক্রিয়া — এটিই scaling-এর আসল চিন্তাপদ্ধতি।

৩.১ ধাপ ০: একক সার্ভার (Single Server)

শুরুতে — সব কিছু একটি মেশিনে: web server, application, এবং database একসাথে। কয়েকশ থেকে কয়েক হাজার ব্যবহারকারীর জন্য এটি একদম ঠিক, এবং সবচেয়ে সরল।
- bottleneck আসবে যখন: CPU/RAM সীমায় পৌঁছায়, বা এই একটি সার্ভার ডাউন হলে পুরো অ্যাপ ডাউন (SPOF)।

৩.২ ধাপ ১: স্তর পৃথকীকরণ ও Vertical Scaling

প্রথম পদক্ষেপ — application ও database আলাদা সার্ভারে রাখা (অধ্যায় ৩-এর tier পৃথকীকরণ)। এতে প্রতিটি স্তর স্বাধীনভাবে রিসোর্স পায়। সাথে প্রাথমিক vertical scaling — সার্ভারগুলোকে আরও শক্তিশালী করা (অধ্যায় ৯)।
- সহজ ও কার্যকর, কিন্তু: vertical scaling-এর কঠিন সীমা আছে, এবং এখনো SPOF আছে।

৩.৩ ধাপ ২: Horizontal Scaling + Load Balancer

vertical scaling সীমায় পৌঁছালে — একাধিক application server এবং সামনে একটি Load Balancer (অধ্যায় ২, ১০)। এখন bottleneck app স্তরে কমে। কিন্তু এর পূর্বশর্ত — অ্যাপ stateless হতে হবে, এবং session বাইরে (Redis) রাখতে হবে (অধ্যায় ৯), যাতে যেকোনো সার্ভার যেকোনো অনুরোধ সামলাতে পারে।
- এখন bottleneck সরে যায়: সাধারণত database-এ — কারণ সব app server একটি DB-তে আঘাত করছে।

৩.৪ ধাপ ৩: Caching (সবচেয়ে বেশি লাভজনক পদক্ষেপ)

DB-তে চাপ কমাতে প্রথম ও সবচেয়ে কার্যকর পদক্ষেপ — caching (অধ্যায় ৫)। ঘন-পঠিত ডাটা Redis/Memcached-এ ক্যাশ করা; স্ট্যাটিক asset CDN-এ (অধ্যায় ৬)। একটি ভালো cache hit ratio DB লোড ৮০-৯৫%+ কমাতে পারে — অপেক্ষাকৃত কম খরচে বিশাল লাভ।
- এরপরও bottleneck: DB-তে read চাপ (যা cache miss-এ যায়) এবং write চাপ।

৩.৫ ধাপ ৪: Database Read Replicas

read চাপ কমাতে — read replica (অধ্যায় ১৩-এর single-leader replication)। একটি primary (write) এবং একাধিক replica (read)। read query-গুলো replica-তে বণ্টন করা হয়, primary শুধু write সামলায়। বেশিরভাগ অ্যাপ read-heavy, তাই এটি বিশাল সাহায্য করে।
- বিবেচনা: replication lag (replica সামান্য পিছিয়ে — eventual consistency); read-your-writes দরকার হলে সাবধানতা (অধ্যায় ১৩)।
- এরপরও bottleneck: write চাপ — সব write এখনো একটি primary-তে।

৩.৬ ধাপ ৫: Async Processing ও Queue

ভারী/ধীর কাজ (ইমেল, রিপোর্ট, মিডিয়া প্রক্রিয়া) সরাসরি না করে message queue + worker দিয়ে async করা (অধ্যায় ৮)। এতে request চক্র দ্রুত থাকে, traffic spike queue-তে buffer হয়, এবং DB-তে তাৎক্ষণিক write চাপ কমে।
- এরপরও bottleneck: write throughput ও DB আকার যখন একটি মেশিনে আঁটে না।

৩.৭ ধাপ ৬: Database Sharding

যখন write চাপ ও ডাটার আকার একটি primary-তে আঁটে না — sharding (অধ্যায় ১০)। ডাটা একাধিক shard-এ ভাগ করা; প্রতিটি shard নিজের write সামলায়। এটি write scaling-এর চূড়ান্ত সমাধান, কিন্তু সবচেয়ে জটিল — তাই শেষ অস্ত্র (আগে caching, replica, async চেষ্টা করুন)।
- বিবেচনা: shard key নির্বাচন, hotspot, cross-shard query (অধ্যায় ১০)।

৩.৮ ধাপ ৭: Microservices, Multi-AZ ও Auto-Scaling

বড় টিম ও জটিলতায় — মনোলিথ ভেঙে microservices (অধ্যায় ১, ১৫); Multi-AZ/Multi-Region redundancy (অধ্যায় ১২); এবং auto-scaling (নিচে) যাতে চাহিদা অনুযায়ী স্বয়ংক্রিয়ভাবে scale হয়। সাথে resilience (circuit breaker, rate limiting — অধ্যায় ১১), observability (monitoring), ও CDN/edge optimization।
- এই ধাপে আপনি কার্যত internet-scale-এ পৌঁছান — অধ্যায় ১৭/১৯-এর সিস্টেমগুলোর মতো।

মূল চিন্তাপদ্ধতি: scaling একটি একবারের সিদ্ধান্ত নয়, একটি পুনরাবৃত্ত প্রক্রিয়া — মাপো (monitor), bottleneck খোঁজো, সবচেয়ে সস্তা কার্যকর সমাধান প্রয়োগ করো, আবার মাপো। কখনো প্রয়োজনের আগে scale করবেন না (premature optimization)।

অংশ খ: AWS Auto Scaling (বাস্তব কাজ)

৩.৯ Auto Scaling-এর উপাদান

অধ্যায় ৯-এ আমরা auto-scaling-এর তত্ত্ব শিখেছি; এখানে AWS-এর বাস্তব বাস্তবায়ন:

  • Launch Template: নতুন instance কীভাবে তৈরি হবে তার "ব্লুপ্রিন্ট" — কোন AMI (image), instance type, security group, user-data script ইত্যাদি।
  • Auto Scaling Group (ASG): instance-গুলোর একটি গোষ্ঠী যা স্বয়ংক্রিয়ভাবে পরিচালিত হয়; এর Min/Max/Desired capacity নির্ধারণ করে কতগুলো instance থাকবে (অধ্যায় ৯)।
  • Scaling Policy: কখন scale হবে তার নিয়ম —
  • Target Tracking: একটি metric (যেমন CPU)-কে একটি লক্ষ্যে (যেমন ৫০%) ধরে রাখা — সবচেয়ে সহজ ও প্রস্তাবিত।
  • Step Scaling: metric-এর মাত্রা অনুযায়ী ধাপে ধাপে যোগ (যেমন CPU ৭০%+ → ২টি, ৯০%+ → ৫টি)।
  • Scheduled Scaling: সময়-ভিত্তিক (পরিচিত traffic প্যাটার্নে)।
  • Predictive Scaling: ML দিয়ে ভবিষ্যৎ চাহিদা পূর্বাভাস (অধ্যায় ৯)।
  • Health Check ও Self-Healing: ASG অসুস্থ instance (EC2 বা ELB health check অনুযায়ী) সরিয়ে নতুন instance দিয়ে প্রতিস্থাপন করে (অধ্যায় ১২)।
  • Lifecycle Hooks: instance চালু/বন্ধ হওয়ার সময় কাস্টম কাজ (যেমন warm-up, graceful shutdown — অধ্যায় ১২)।

৩.১০ Auto Scaling + Load Balancer একসাথে

ASG সাধারণত একটি Load Balancer (ALB/NLB)-এর সাথে যুক্ত থাকে: ASG নতুন instance তৈরি করলে তা স্বয়ংক্রিয়ভাবে load balancer-এর target group-এ যুক্ত হয় (এবং health check পাস করলে ট্র্যাফিক পায়); instance সরানো হলে আগে graceful-ভাবে ট্র্যাফিক বন্ধ (connection draining) করে তবেই বন্ধ হয়। এই সমন্বয়ই elastic scaling সম্ভব করে — চাহিদা অনুযায়ী instance ও ট্র্যাফিক বণ্টন একসাথে সমন্বিত।

৩.১১ বাস্তব বিবেচনা (অধ্যায় ৯ থেকে)

  • Cooldown/Warm-up: scaling-এর পর অপেক্ষা (oscillation/thrashing রোধ); নতুন instance প্রস্তুত হওয়ার সময়।
  • সঠিক metric: শুধু CPU নয় — request/sec, queue depth, latency-ও বিবেচনা।
  • Min/Max সীমা: redundancy (min) ও খরচ নিয়ন্ত্রণ (max)।
  • ডাটাবেস scaling আলাদা: ASG শুধু stateless app স্তর scale করে; DB-কে আলাদাভাবে (read replica, Aurora auto-scaling, DynamoDB) scale করতে হয় — নইলে app scale হলেও DB bottleneck।

অংশ গ: Load Balancing at Internet Scale

৩.১২ একটি LB যথেষ্ট নয় — Multi-tier Load Balancing

একটি একক load balancer (এমনকি একটি ক্লাস্টার)-এরও সীমা আছে। internet-scale-এ (কোটি কোটি অনুরোধ, বিশ্বজুড়ে) load balancing একাধিক স্তরে হয়:

স্তর ১ — DNS-based Load Balancing (Global):
প্রথম বণ্টন ঘটে DNS-এ। একটি ডোমেইনের জন্য DNS একাধিক IP ফেরত দিতে পারে (round-robin), বা ভৌগোলিক/latency-ভিত্তিক রাউটিং করতে পারে — ব্যবহারকারীকে নিকটতম/সেরা region-এ পাঠায় (অধ্যায় ১০-এর GSLB; AWS Route 53)।
- সীমা: DNS caching ও TTL-এর কারণে পরিবর্তন ধীরে প্রচারিত হয়; তাই দ্রুত failover-এ একা নির্ভরযোগ্য নয়।

স্তর ২ — Anycast (Network-level):
একই IP ঠিকানা বিশ্বজুড়ে বহু লোকেশনে বরাদ্দ; নেটওয়ার্ক রাউটিং (BGP) স্বয়ংক্রিয়ভাবে অনুরোধকে নিকটতম লোকেশনে পাঠায় (অধ্যায় ৬-এর CDN Anycast)। CDN ও বড় edge নেটওয়ার্ক এটি ব্যবহার করে।

স্তর ৩ — Regional / L4-L7 Load Balancers:
একটি region-এ পৌঁছানোর পর, একাধিক স্তরের load balancer — প্রথমে হয়তো একটি L4 (NLB, কাঁচা গতি) যা একটি L7 LB ক্লাস্টারে বণ্টন করে, যা আবার app server-এ বণ্টন করে (অধ্যায় ১০)।

৩.১৩ LB নিজে scalable ও HA

internet-scale-এ load balancer নিজেও একটি bottleneck/SPOF হতে পারে — তাই:
- LB redundant (active-active, multiple instances — অধ্যায় ১২)।
- বড় কোম্পানি software load balancer (যেমন Google-এর Maglev, Netflix-এর সমাধান) ব্যবহার করে — যা commodity hardware-এ horizontally scale করা যায়, ঐতিহ্যবাহী hardware LB-এর সীমা ছাড়িয়ে।
- Connection draining/graceful — instance যোগ/সরানোর সময় চলমান অনুরোধ না হারিয়ে।

৩.১৪ সম্পূর্ণ চিত্র — সব স্তর একসাথে

internet-scale-এ একটি অনুরোধের যাত্রা: ব্যবহারকারী → DNS (নিকটতম region নির্বাচন) → Anycast/CDN edge (স্ট্যাটিক হলে এখানেই; নাহলে) → regional entry LB (L4) → L7 LB → app server (ASG-managed) → cache/DB। প্রতিটি স্তর redundant, scalable, ও health-checked — এই বহু-স্তরীয় বণ্টনই কোটি কোটি অনুরোধ মসৃণভাবে সামলানো সম্ভব করে।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনি একটি স্টার্টআপ শুরু করলেন। আপনার scaling যাত্রা বাস্তবে এমন হবে:

  • মাস ১ (১০০ ব্যবহারকারী): একটি $20/মাস সার্ভার — সব একসাথে। ঠিক আছে। distributed system বানানো এখন পাগলামি (over-engineering)।
  • মাস ৬ (১০,০০০ ব্যবহারকারী): DB ধীর হচ্ছে। DB আলাদা সার্ভারে সরালেন (ধাপ ১)।
  • বছর ১ (১ লক্ষ ব্যবহারকারী): একটি app server যথেষ্ট নয়। Load Balancer + একাধিক stateless app server, session Redis-এ (ধাপ ২)। তারপর caching যোগ করলেন — DB চাপ নাটকীয়ভাবে কমল (ধাপ ৩)।
  • বছর ২ (১০ লক্ষ ব্যবহারকারী): read চাপ বেশি — read replica যোগ (ধাপ ৪)। ভারী কাজ queue+worker-এ সরালেন (ধাপ ৫)। AWS Auto Scaling চালু করলেন — traffic spike স্বয়ংক্রিয়ভাবে সামলায়।
  • বছর ৩ (১ কোটি+ ব্যবহারকারী): write ও আকার একটি DB-তে আঁটে না — sharding (ধাপ ৬)। Multi-AZ HA, microservices, multi-tier load balancing, CDN — internet-scale (ধাপ ৭)।

মূল শিক্ষা: প্রতিটি ধাপ একটি প্রকৃত, পরিমাপিত bottleneck-এর প্রতিক্রিয়া — অনুমান নয়। আপনি যদি মাস ১-এ sharding করতেন, তা হতো বিশাল সময় ও জটিলতার অপচয়। আবার বছর ৩-এ এক সার্ভারে আটকে থাকলে ব্যবসা ধসে যেত। সঠিক সময়ে সঠিক কৌশল — এটিই scaling-এর শিল্প।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples — প্রোডাকশনে ব্যবহারযোগ্য)

Read/Write Split (read replica routing — Python)

class Database:
    def __init__(self, primary, replicas):
        self.primary = primary          # write এখানে
        self.replicas = replicas        # read এখানে (একাধিক)

    def write(self, query):
        return self.primary.execute(query)        # সব write primary-তে

    def read(self, query):
        # read replica-তে বণ্টন (load balance)
        replica = random.choice(self.replicas)
        return replica.execute(query)

    def read_after_write(self, query):
        # read-your-writes দরকার হলে primary থেকে পড়া
        # (replication lag এড়াতে — অধ্যায় ১৩)
        return self.primary.execute(query)

ব্যাখ্যা ও বাস্তব প্রয়োগ: সব write primary-তে, read replica-তে বণ্টন করা হয় — read scaling-এর সরল প্যাটার্ন। গুরুত্বপূর্ণ সূক্ষ্মতা: replica-তে replication lag থাকে, তাই ব্যবহারকারী নিজের সদ্য-লেখা ডাটা পড়তে চাইলে (read-your-writes) সেটি primary থেকে পড়তে হবে (read_after_write) — নইলে stale দেখাবে। প্রোডাকশনে এই রাউটিং প্রায়ই একটি proxy (যেমন ProxySQL, RDS Proxy) বা ORM স্তরে করা হয়।

AWS Auto Scaling Group (CloudFormation — সরাসরি ব্যবহারযোগ্য)

Resources:
  AppASG:
    Type: AWS::AutoScaling::AutoScalingGroup
    Properties:
      MinSize: 2                     # redundancy: কখনো ২-এর নিচে নয়
      MaxSize: 50                    # খরচ সীমা
      DesiredCapacity: 4
      LaunchTemplate:
        LaunchTemplateId: !Ref AppLaunchTemplate
        Version: !GetAtt AppLaunchTemplate.LatestVersionNumber
      VPCZoneIdentifier:             # একাধিক AZ-তে ছড়ানো (HA)
        - !Ref PrivateSubnetAZ1
        - !Ref PrivateSubnetAZ2
      TargetGroupARNs:               # LB-এর সাথে যুক্ত
        - !Ref AppTargetGroup
      HealthCheckType: ELB           # LB health check ব্যবহার
      HealthCheckGracePeriod: 60     # warm-up সময়

  CPUScalingPolicy:
    Type: AWS::AutoScaling::ScalingPolicy
    Properties:
      AutoScalingGroupName: !Ref AppASG
      PolicyType: TargetTrackingScaling
      TargetTrackingConfiguration:
        PredefinedMetricSpecification:
          PredefinedMetricType: ASGAverageCPUUtilization
        TargetValue: 50.0            # CPU ~৫০%-এ ধরে রাখো

ব্যাখ্যা: এই কনফিগ একটি production-grade ASG সংজ্ঞায়িত করে — দুই AZ-তে ছড়ানো (HA), LB target group-এর সাথে যুক্ত, ELB health check + grace period (warm-up), target tracking policy (CPU ~৫০%)। MinSize: 2 redundancy নিশ্চিত করে; MaxSize: 50 runaway খরচ রোধ করে। সবই IaC-তে (অধ্যায় ১৮) — reproducible।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • প্রায় প্রতিটি স্টার্টআপ: এই scaling যাত্রা অনুসরণ করে — সরল মনোলিথ → LB+caching → read replica → (প্রয়োজনে) sharding/microservices। অকালে scale করা স্টার্টআপ প্রায়ই সময় নষ্ট করে।
  • Amazon/Netflix: AWS Auto Scaling-এর ব্যাপক ব্যবহার — দৈনিক ও মৌসুমি traffic অনুযায়ী হাজারো instance স্বয়ংক্রিয়ভাবে scale।
  • Google (Maglev): software load balancer যা commodity hardware-এ horizontally scale করে — internet-scale LB-এর উদাহরণ।
  • Cloudflare/CDN: Anycast + global edge দিয়ে কোটি কোটি অনুরোধ বিশ্বজুড়ে বণ্টন।
  • Stack Overflow (বিপরীত শিক্ষা): তুলনামূলকভাবে কম সার্ভারে (আক্রমণাত্মক vertical scaling + caching) বিশাল traffic সামলেছে — দেখায় horizontal scaling-ই একমাত্র পথ নয়; প্রসঙ্গ গুরুত্বপূর্ণ।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- দিন ১-এ microservices/sharding/distributed system বানানো — premature, বিশাল অপচয় (over-engineering)।
- bottleneck না মেপে অনুমানের ভিত্তিতে scale করা।

Intermediate Mistakes:
- caching-এর আগেই sharding করা — সবচেয়ে সস্তা লাভজনক পদক্ষেপ (cache) এড়িয়ে সবচেয়ে জটিলটায় যাওয়া।
- app stateful রেখে horizontal scale করার চেষ্টা (session বাইরে না রাখা — অধ্যায় ৯)।
- read replica-তে read-your-writes ধরে নেওয়া (replication lag উপেক্ষা)।

Production Mistakes:
- app স্তর auto-scale করা কিন্তু DB-কে scaling পরিকল্পনায় না আনা — DB-ই bottleneck থেকে যায়।
- ASG-তে MaxSize না রাখা — spike/আক্রমণে runaway খরচ; cooldown না রাখা — thrashing।
- connection draining ছাড়া scale-in — চলমান অনুরোধ হারানো।
- LB-কে redundant না করা — internet-scale-এ SPOF।

Scalability Mistakes:
- DNS failover-এর ওপর দ্রুত failover-এর জন্য একা নির্ভর করা (TTL/caching বিলম্ব)।
- ভুল scaling metric (শুধু CPU, যখন আসল bottleneck queue/memory)।
- প্রতিটি স্তর আলাদাভাবে scale না করা — এক স্তর scale করলেও অন্যটি আটকায়।

Architecture Mistakes:
- "সব Netflix-এর মতো করতে হবে" — নিজের scale প্রয়োজন না বুঝে অন্ধ অনুকরণ।
- monitoring/observability ছাড়া scaling — অন্ধভাবে।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: আপনার অ্যাপ ধীর হয়ে যাচ্ছে কারণ DB-তে চাপ বেশি। প্রথম কী করবেন?

প্রথমে caching (Redis/Memcached) — ঘন-পঠিত ডাটা ক্যাশ করে DB লোড নাটকীয়ভাবে কমানো; স্ট্যাটিক asset CDN-এ। এটি সবচেয়ে কম খরচে সর্বোচ্চ লাভ। তারপর প্রয়োজনে read replica।

Intermediate প্রশ্ন: Read replica কীভাবে scaling-এ সাহায্য করে এবং এর সীমা কী?

read query-গুলো একাধিক replica-তে বণ্টন করে read scaling দেয় (বেশিরভাগ অ্যাপ read-heavy)। সীমা — replication lag (replica সামান্য পিছিয়ে, eventual consistency), এবং write এখনো একটি primary-তে সীমাবদ্ধ (write scaling-এ sharding লাগে)।

Intermediate প্রশ্ন: AWS Auto Scaling Group কীভাবে কাজ করে?

ASG একটি launch template থেকে instance তৈরি/পরিচালনা করে, Min/Max/Desired সীমার মধ্যে; scaling policy (যেমন target tracking — CPU ৫০%-এ রাখা) অনুযায়ী CloudWatch metric দেখে scale out/in করে; health check-এ অসুস্থ instance প্রতিস্থাপন করে (self-healing); LB-এর সাথে যুক্ত হয়ে নতুন instance-এ ট্র্যাফিক বণ্টন।

Advanced প্রশ্ন: Internet-scale-এ load balancing কীভাবে কাজ করে?

বহু-স্তরীয় — (১) DNS (Route 53) geo/latency-ভিত্তিক নিকটতম region নির্বাচন; (২) Anycast/CDN edge — স্ট্যাটিক কনটেন্ট ও নিকটতম entry; (৩) region-এ L4 LB (কাঁচা গতি) → L7 LB ক্লাস্টার → app server (ASG)। প্রতিটি স্তর redundant ও health-checked; বড় কোম্পানি software LB (Maglev) দিয়ে LB স্তরও horizontally scale করে।

System Design প্রশ্ন: একটি অ্যাপকে ১০০ ব্যবহারকারী থেকে ১ কোটিতে নেওয়ার পরিকল্পনা বলুন।

ধাপে ধাপে — single server → app/DB পৃথকীকরণ → LB + stateless app (session Redis) → caching + CDN → read replica → async queue+worker → sharding → Multi-AZ + microservices + auto-scaling + multi-tier LB। প্রতিটি ধাপ একটি পরিমাপিত bottleneck-এর প্রতিক্রিয়া; caching আগে, sharding শেষে; DB-কে সবসময় scaling পরিকল্পনায় রাখা; monitoring-ভিত্তিক সিদ্ধান্ত; premature optimization এড়ানো।

১০. সেরা চর্চা (Best Practices — সরাসরি প্রয়োগযোগ্য)

  • মাপো, তারপর scale করো — monitoring দিয়ে প্রকৃত bottleneck খুঁজে তবেই কৌশল প্রয়োগ; অনুমানে নয়।
  • সরল দিয়ে শুরু করো; premature optimization এড়াও — দিন ১-এ distributed system নয়।
  • সস্তা সমাধান আগে: caching ও CDN আগে, read replica তারপর, sharding শেষে।
  • app stateless রাখো (session বাইরে) — horizontal scaling ও auto-scaling-এর পূর্বশর্ত।
  • DB-কে সবসময় scaling পরিকল্পনায় রাখো — app scale হলেও DB bottleneck হতে পারে।
  • Auto Scaling-এ: Min (redundancy), Max (খরচ), cooldown (thrashing রোধ), সঠিক metric, multi-AZ, connection draining।
  • LB redundant ও multi-tier internet-scale-এ; DNS failover-এর একক নির্ভরতা এড়াও।
  • প্রতিটি স্তর স্বাধীনভাবে scale করো; সব কিছু observable রাখো।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Scaling যাত্রা: single server → app/DB পৃথকীকরণ → LB + stateless app → caching/CDN → read replica → async queue → sharding → microservices/multi-AZ/auto-scaling। প্রতিটি ধাপ একটি পরিমাপিত bottleneck-এর প্রতিক্রিয়া।
- ক্রম গুরুত্বপূর্ণ: caching আগে (সস্তা, সর্বোচ্চ লাভ), sharding শেষে (জটিল, শেষ অস্ত্র)।
- AWS Auto Scaling: Launch Template + ASG (Min/Max/Desired) + Scaling Policy (target/step/scheduled/predictive) + health check/self-healing + LB integration; cooldown/warm-up; DB আলাদাভাবে scale।
- Internet-scale LB: multi-tier — DNS (global geo/latency) → Anycast/CDN edge → regional L4 → L7 → ASG app; LB নিজে redundant ও scalable (software LB)।
- মূল নীতি: মাপো → bottleneck খোঁজো → সস্তা কার্যকর সমাধান → আবার মাপো; premature optimization এড়াও।

গুরুত্বপূর্ণ পরিভাষা: Scaling Journey, Bottleneck, Tier Separation, Stateless, Read Replica, Replication Lag, Read-Your-Writes, Async Queue, Sharding, Launch Template, Auto Scaling Group, Min/Max/Desired, Target/Step/Scheduled/Predictive Scaling, Connection Draining, Cooldown/Warm-up, Self-Healing, DNS Load Balancing, Anycast, GSLB, Multi-tier LB, L4/L7, Software Load Balancer, Premature Optimization।

১২. অনুশীলন (Practice Exercises)

Conceptual:
1. একটি অ্যাপের scaling যাত্রার ৭টি ধাপ ক্রমানুসারে লিখুন এবং প্রতিটিতে কোন bottleneck সমাধান হয়।
2. কেন caching সাধারণত sharding-এর আগে প্রয়োগ করা উচিত?

Practical:
3. একটি read/write split ডিজাইন করুন এবং read-your-writes কীভাবে সামলাবেন তা ব্যাখ্যা করুন।
4. একটি ASG-এর জন্য target tracking ও step scaling policy-র মধ্যে কখন কোনটি বাছবেন — উদাহরণসহ।

Architecture Design:
5. একটি সোশ্যাল অ্যাপকে ১০ লক্ষ ব্যবহারকারীতে scale করার সম্পূর্ণ পরিকল্পনা ডিজাইন করুন — প্রতিটি স্তর ও সিদ্ধান্তের কারণসহ।

Scenario-Based:
6. আপনি app server auto-scale করেছেন কিন্তু peak সময়ে এখনো অ্যাপ ধীর। সম্ভাব্য কারণ (ইঙ্গিত: DB) ও সমাধান কী?

Interview Challenge:
7. একজন ইন্টারভিউয়ারকে বোঝান কেন একটি প্রাথমিক স্টার্টআপের জন্য দিন ১-এ sharding/microservices করা একটি ভুল সিদ্ধান্ত — এবং সঠিক পদ্ধতি কী।
