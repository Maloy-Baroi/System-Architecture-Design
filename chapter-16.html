📖 অধ্যায় ১৬

অধ্যায় ১৬: Event Sourcing, Service Mesh, Istio ও Sidecar Proxy

১. অধ্যায় পরিচিতি (Chapter Introduction)

এই অধ্যায়ে আমরা দুটি উন্নত, শক্তিশালী ধারণা শিখব যা আধুনিক distributed system-এর দুটি ভিন্ন স্তরে কাজ করে — একটি ডাটা/স্টেট স্তরে, আরেকটি নেটওয়ার্ক/অবকাঠামো স্তরে।

প্রথম ধারণা — Event Sourcing। ঐতিহ্যগতভাবে আমরা একটি জিনিসের শুধু বর্তমান অবস্থা (current state) সংরক্ষণ করি — যেমন "অ্যাকাউন্ট ব্যালেন্স = ৫০০ টাকা"। কিন্তু আমরা জানি না কীভাবে সেখানে পৌঁছালাম — কোন কোন লেনদেন হয়েছিল, কখন। Event Sourcing এই দৃষ্টিভঙ্গি উল্টে দেয়: বর্তমান অবস্থা সংরক্ষণ না করে, সেই অবস্থায় পৌঁছানোর প্রতিটি ঘটনার (event) সম্পূর্ণ ইতিহাস সংরক্ষণ করে। এটি ব্যাংকিং, audit, ও জটিল ব্যবসায়িক সিস্টেমে অসাধারণ শক্তিশালী।

দ্বিতীয় ধারণা — Service Mesh (এবং এর বাস্তবায়ন Istio ও মূল উপাদান Sidecar Proxy)। আমরা অধ্যায় ১১-এ resilience pattern (retry, circuit breaker, timeout), অধ্যায় ১৫-এ service discovery শিখেছি। কিন্তু একটি সমস্যা — এই সব লজিক যদি প্রতিটি সার্ভিসের কোডে লিখতে হয় (এবং প্রতিটি ভাষায়), তা বিশাল পুনরাবৃত্তি ও অসামঞ্জস্য তৈরি করে। Service Mesh এই সব নেটওয়ার্ক-সম্পর্কিত দায়িত্ব অ্যাপ্লিকেশন কোড থেকে বের করে অবকাঠামো স্তরে নিয়ে যায় — যাতে ডেভেলপাররা শুধু ব্যবসায়িক লজিকে মনোযোগ দিতে পারেন।

এই দুটি ধারণা গভীরভাবে বুঝলে আপনি আরও পরিণত, রক্ষণাবেক্ষণযোগ্য ও পর্যবেক্ষণযোগ্য (observable) সিস্টেম ডিজাইন করতে পারবেন।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি গভীরভাবে বুঝতে ও প্রয়োগ করতে পারবেন:

  • Event Sourcing — মূল ধারণা, event store, state পুনর্গঠন (replay), snapshot
  • Event Sourcing-এর সুবিধা (audit, time travel, debugging) ও চ্যালেঞ্জ (event versioning, eventual consistency)
  • CQRS + Event Sourcing কীভাবে একসাথে কাজ করে
  • Sidecar Proxy প্যাটার্ন — কেন ও কীভাবে
  • Service Mesh — data plane vs control plane; এটি কোন সমস্যা সমাধান করে
  • Istio — আর্কিটেকচার ও মূল ক্ষমতা (traffic management, security, observability)
  • কখন service mesh ব্যবহার করবেন এবং কখন এটি অতিরিক্ত জটিলতা

৩. মূল ধারণা (Core Concepts)

অংশ ক: Event Sourcing

৩.১ মৌলিক ধারণা — state নয়, ঘটনা সংরক্ষণ

ঐতিহ্যগত পদ্ধতিতে (একে বলে "state-oriented") আমরা একটি entity-র শুধু সর্বশেষ অবস্থা একটি টেবিলের সারিতে রাখি, এবং প্রতিটি পরিবর্তনে সেই সারি overwrite করি। সমস্যা — পুরোনো অবস্থা ও পরিবর্তনের ইতিহাস চিরতরে হারিয়ে যায়।

Event Sourcing এর বিপরীত: একটি entity-র বর্তমান অবস্থা সরাসরি সংরক্ষণ না করে, তার ওপর ঘটে যাওয়া প্রতিটি ঘটনাকে (event) একটি অপরিবর্তনীয় (immutable), append-only ক্রমে সংরক্ষণ করা হয়। বর্তমান অবস্থা = এই সব event ক্রমানুসারে প্রয়োগ করে গণনা করা ফল।

ব্যাংক অ্যাকাউন্টের উদাহরণ দিয়ে স্পষ্ট করি:
- State-oriented: balance = 150 (শুধু এই একটি সংখ্যা)।
- Event-sourced: AccountOpened(0) → Deposited(100) → Deposited(100) → Withdrew(50)। এই চারটি event-ই হলো সত্য (source of truth); বর্তমান ব্যালেন্স (১৫০) এদের যোগফল হিসেবে গণনা করা হয়।

মূল অন্তর্দৃষ্টি: event-গুলোই source of truth, current state শুধু একটি derived (উদ্ভূত) ভিউ। এটি একটি ব্যাংকের লেজারের মতো — আপনি ব্যালেন্স মুছে ফেলেন না, প্রতিটি লেনদেন একটি নতুন লাইন হিসেবে যোগ করেন।

৩.২ Event Store ও State পুনর্গঠন

Event Store হলো সেই append-only ডাটাবেস যেখানে event-গুলো সংরক্ষিত হয় (কালানুক্রমিকভাবে, প্রতি entity/aggregate-এর জন্য একটি ক্রম)। event কখনো মুছে ফেলা বা পরিবর্তন করা হয় না — শুধু নতুন event যোগ হয়।

State পুনর্গঠন (Replay): কোনো entity-র বর্তমান (বা অতীতের যেকোনো) অবস্থা পেতে, তার সব event শুরু থেকে ক্রমানুসারে replay করা হয় — অর্থাৎ একটি খালি অবস্থা থেকে শুরু করে প্রতিটি event একে একে প্রয়োগ করে চূড়ান্ত অবস্থায় পৌঁছানো।

Snapshot (পারফরম্যান্স অপ্টিমাইজেশন): একটি entity-তে যদি লক্ষ লক্ষ event থাকে, তবে প্রতিবার শুরু থেকে replay করা ধীর। সমাধান — snapshot: পর্যায়ক্রমে (যেমন প্রতি ১০০ event পর) বর্তমান অবস্থার একটি ছবি সংরক্ষণ করা। তখন state পুনর্গঠনে সর্বশেষ snapshot থেকে শুরু করে তার পরের অল্প কিছু event replay করলেই চলে — অনেক দ্রুত।

৩.৩ Event Sourcing-এর সুবিধা

  • সম্পূর্ণ Audit Trail: প্রতিটি পরিবর্তনের পূর্ণ ইতিহাস স্বয়ংক্রিয়ভাবে থাকে — "কে, কখন, কী বদলেছে" — যা finance, healthcare, compliance-এ অপরিহার্য।
  • Time Travel / Temporal Query: অতীতের যেকোনো মুহূর্তের অবস্থা পুনর্গঠন করা যায় ("গত মাসের ১ তারিখে এই অ্যাকাউন্টের ব্যালেন্স কত ছিল?")।
  • Debugging ও Root Cause Analysis: একটি bug-এর কারণ খুঁজতে event ক্রম পুনরায় চালিয়ে দেখা যায় ঠিক কী ঘটেছিল।
  • নতুন read model/view সহজে তৈরি: ভবিষ্যতে নতুন কোনো প্রতিবেদন/view দরকার হলে, পুরোনো সব event replay করে সেটি তৈরি করা যায় — মূল ডাটা হারায়নি।
  • Business Insight: event-গুলো নিজেই মূল্যবান ব্যবসায়িক ডাটা (যেমন ব্যবহারকারীর প্রতিটি action)।

৩.৪ Event Sourcing-এর চ্যালেঞ্জ (বাস্তব সতর্কতা)

  • Event Versioning / Schema Evolution: event immutable, কিন্তু সময়ের সাথে event-এর গঠন বদলাতে পারে (নতুন ফিল্ড)। পুরোনো event-ও পড়তে হবে — তাই version ও upcasting (পুরোনো event-কে নতুন ফরম্যাটে রূপান্তর) কৌশল লাগে। এটি Event Sourcing-এর সবচেয়ে কঠিন বাস্তব সমস্যা।
  • Eventual Consistency: current state ও read model প্রায়ই event থেকে async-ভাবে তৈরি — তাই সামান্য বিলম্ব।
  • জটিলতা: state-oriented-এর চেয়ে অনেক জটিল; সরল CRUD অ্যাপে over-engineering।
  • Query কঠিন: "সব অ্যাকাউন্টের মধ্যে যাদের ব্যালেন্স > X" — এমন query সরাসরি event store-এ কঠিন; এজন্য CQRS read model দরকার।
  • বড় event store: event কখনো মুছে যায় না — তাই স্টোরেজ ক্রমাগত বাড়ে।

৩.৫ Event Sourcing + CQRS — স্বাভাবিক জুটি

অধ্যায় ১৫-এ শেখা CQRS এবং Event Sourcing একসাথে অসাধারণ কাজ করে, এবং প্রায়ই একসাথে ব্যবহৃত হয়:
- Write side: command আসে → ব্যবসায়িক নিয়ম যাচাই → একটি বা একাধিক event তৈরি করে event store-এ append (এটিই Event Sourcing)।
- Read side: এই event-গুলো শুনে এক বা একাধিক denormalized read model তৈরি/আপডেট করা হয় (এটিই CQRS-এর query side)।

এভাবে — event store হলো নির্ভরযোগ্য source of truth (audit, replay সহ), আর read model গুলো দ্রুত query-র জন্য অপ্টিমাইজড। নতুন read model দরকার হলে শুধু event replay করে তৈরি করা যায়। (লক্ষ্য করুন — CQRS Event Sourcing ছাড়াও ব্যবহার করা যায়, এবং উল্টোটাও; কিন্তু একসাথে এরা সবচেয়ে শক্তিশালী।)

অংশ খ: Sidecar, Service Mesh ও Istio

৩.৬ সমস্যা: cross-cutting concern প্রতিটি সার্ভিসে পুনরাবৃত্তি

আধুনিক microservices-এ প্রতিটি সার্ভিসকে কিছু সাধারণ নেটওয়ার্ক-কাজ করতে হয়: service discovery, load balancing, retry, timeout, circuit breaking (অধ্যায় ১১), mutual TLS (নিরাপদ সার্ভিস-টু-সার্ভিস যোগাযোগ), metrics সংগ্রহ, distributed tracing, ট্র্যাফিক রাউটিং।

সমস্যা — এই সব লজিক যদি প্রতিটি সার্ভিসের কোডে (এবং আপনার বিভিন্ন সার্ভিস বিভিন্ন ভাষায় — Java, Go, Python) আলাদাভাবে লিখতে হয়, তাহলে: বিশাল কোড পুনরাবৃত্তি; ভাষাভেদে অসামঞ্জস্যপূর্ণ আচরণ; একটি নিয়ম বদলাতে সব সার্ভিস আপডেট ও পুনঃডিপ্লয়; ডেভেলপাররা ব্যবসায়িক লজিকের বদলে অবকাঠামোগত কোডে সময় নষ্ট করে।

৩.৭ Sidecar Proxy প্যাটার্ন — সমাধানের ভিত্তি

Sidecar Proxy হলো একটি সহায়ক প্রক্সি যা প্রতিটি সার্ভিস instance-এর পাশে (একই pod/host-এ, কিন্তু আলাদা প্রসেস/container হিসেবে) চলে — অনেকটা মোটরসাইকেলের পাশে যুক্ত সাইডকারের মতো। সার্ভিসের সব ইনকামিং ও আউটগোয়িং নেটওয়ার্ক ট্র্যাফিক এই sidecar-এর মধ্য দিয়ে যায়।

মূল ধারণা: সার্ভিসটি সরাসরি অন্য সার্ভিসের সাথে কথা না বলে, শুধু তার নিজের sidecar-এর সাথে কথা বলে (localhost-এ); sidecar বাকি সব নেটওয়ার্ক-জটিলতা (discovery, retry, TLS, metrics) সামলায়।

  • সুবিধা: অবকাঠামোগত লজিক অ্যাপ কোড থেকে সম্পূর্ণ আলাদা; ভাষা-নিরপেক্ষ (যেকোনো ভাষার সার্ভিসের পাশে একই sidecar); স্বাধীনভাবে আপডেট করা যায়; ডেভেলপার শুধু ব্যবসায়িক লজিকে মনোযোগ দেন।
  • খরচ: প্রতিটি সার্ভিসের পাশে একটি অতিরিক্ত প্রসেস (সামান্য রিসোর্স ও latency overhead)।

জনপ্রিয় sidecar proxy: Envoy (Istio-র ভিত্তি), Linkerd-proxy।

৩.৮ Service Mesh — sidecar-গুলোর সমন্বিত নেটওয়ার্ক

যখন আপনার সব সার্ভিসের পাশে এমন sidecar proxy থাকে এবং সেগুলো একটি কেন্দ্রীয় ব্যবস্থা দিয়ে নিয়ন্ত্রিত হয়, তখন তৈরি হয় একটি Service Mesh — সার্ভিস-টু-সার্ভিস যোগাযোগ পরিচালনার একটি নিবেদিত অবকাঠামো স্তর।

Service mesh দুটি যৌক্তিক অংশে বিভক্ত:

Data Plane (ডাটা প্লেন):
সব sidecar proxy-গুলো মিলে data plane গঠন করে। এটি প্রকৃত ট্র্যাফিক বহন করে — সার্ভিসগুলোর মধ্যে প্রতিটি অনুরোধ এই proxy-গুলোর মধ্য দিয়ে যায়, এবং এখানেই retry, load balancing, TLS, metrics সংগ্রহ ইত্যাদি বাস্তবে ঘটে।

Control Plane (কন্ট্রোল প্লেন):
data plane-এর সব proxy-কে নিয়ন্ত্রণ ও কনফিগার করে। এটি প্রকৃত ট্র্যাফিক বহন করে না; বরং নিয়ম/নীতি (traffic routing rules, security policy, telemetry config) সব sidecar-এ বিতরণ করে এবং তাদের আচরণ সমন্বিত রাখে। আপনি control plane-এ একটি নিয়ম সেট করেন, এটি সব sidecar-এ প্রয়োগ হয়।

Service Mesh কী কী দেয় (মূল ক্ষমতা):
- Traffic Management: বুদ্ধিমান routing, load balancing, canary deployment (নতুন সংস্করণে ধীরে ধীরে ট্র্যাফিক), A/B testing, traffic splitting।
- Resilience: retry, timeout, circuit breaking — কোড ছাড়াই, কনফিগ দিয়ে (অধ্যায় ১১-এর প্যাটার্ন অবকাঠামো স্তরে)।
- Security: স্বয়ংক্রিয় mutual TLS (mTLS) — সব সার্ভিস-টু-সার্ভিস যোগাযোগ এনক্রিপ্টেড ও পারস্পরিক-প্রমাণিত; fine-grained access policy।
- Observability: স্বয়ংক্রিয় metrics, distributed tracing, ও logging — কোনো অতিরিক্ত অ্যাপ কোড ছাড়াই প্রতিটি সার্ভিস-কলের দৃশ্যমানতা।

৩.৯ Istio — সবচেয়ে জনপ্রিয় Service Mesh

Istio হলো একটি open-source service mesh (Google, IBM, Lyft-এর সহযোগিতায়), যা Kubernetes-এর সাথে গভীরভাবে যুক্ত। এর আর্কিটেকচার:

  • Data Plane: প্রতিটি pod-এ একটি Envoy proxy sidecar হিসেবে স্বয়ংক্রিয়ভাবে inject করা হয়। সব ট্র্যাফিক Envoy-র মধ্য দিয়ে যায়।
  • Control Plane (istiod): Istio-র নতুন সংস্করণে control plane একত্রিত হয়ে istiod নামে একটি একক উপাদান — যা service discovery (Kubernetes থেকে), কনফিগারেশন বিতরণ (routing rules), ও certificate management (mTLS-এর জন্য) সামলায়।

Istio-র মূল ব্যবহারিক ক্ষমতা:
- VirtualService ও DestinationRule: YAML কনফিগ দিয়ে ট্র্যাফিক রাউটিং নিয়ন্ত্রণ — যেমন "১০% ট্র্যাফিক নতুন v2-তে, ৯০% v1-তে" (canary), বা header-ভিত্তিক রাউটিং।
- স্বয়ংক্রিয় mTLS: এক কনফিগে সব সার্ভিসের মধ্যে এনক্রিপ্টেড যোগাযোগ — অ্যাপ কোড অপরিবর্তিত।
- Resilience কনফিগ: retry, timeout, circuit breaker, fault injection (ইচ্ছাকৃতভাবে ব্যর্থতা ঢুকিয়ে পরীক্ষা — chaos engineering) — সব declarative YAML-এ।
- Observability: Prometheus (metrics), Jaeger (tracing), Kiali (mesh visualization)-এর সাথে integration — স্বয়ংক্রিয় দৃশ্যমানতা।

৩.১০ কখন Service Mesh ব্যবহার করবেন (গুরুত্বপূর্ণ সতর্কতা)

Service mesh শক্তিশালী, কিন্তু এটি উল্লেখযোগ্য অপারেশনাল জটিলতা ও রিসোর্স overhead যোগ করে (প্রতিটি pod-এ একটি proxy, একটি control plane চালানো, শেখার বক্ররেখা)।

  • ব্যবহার করুন যখন: আপনার অনেক (ডজনখানেক+) microservice আছে, বিভিন্ন ভাষায়; mTLS/নিরাপত্তা, fine-grained traffic control (canary), ও গভীর observability দরকার; এবং একটি প্ল্যাটফর্ম টিম এটি পরিচালনা করতে পারে।
  • এড়িয়ে চলুন যখন: কম সার্ভিস, সরল সিস্টেম, বা ছোট টিম — তখন mesh-এর জটিলতা সুবিধার চেয়ে বেশি; একটি লাইব্রেরি (যেমন resilience4j) বা API Gateway-ই যথেষ্ট হতে পারে।

মূল নীতি: service mesh একটি অবকাঠামোগত সমাধান — এটি ব্যবসায়িক সমস্যা সমাধান করে না, বরং নেটওয়ার্ক-সমস্যাগুলোকে অ্যাপ কোড থেকে সরিয়ে নেয়। প্রয়োজন প্রমাণিত হলে তবেই গ্রহণ করুন।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

Event Sourcing-এর বাস্তব প্রয়োজন: ধরুন আপনি একটি ব্যাংকিং বা ই-ওয়ালেট সিস্টেম বানাচ্ছেন। নিয়ন্ত্রক (regulator) দাবি করে — প্রতিটি লেনদেনের সম্পূর্ণ, অপরিবর্তনীয় ইতিহাস রাখতে হবে; "গত বছরের অমুক তারিখে এই অ্যাকাউন্টের ব্যালেন্স কত ছিল" তা প্রমাণ করতে হবে; এবং কোনো বিরোধ হলে ঠিক কী ঘটেছিল তা পুনর্গঠন করতে হবে।

state-oriented ডিজাইনে এটি প্রায় অসম্ভব — কারণ আপনি শুধু বর্তমান ব্যালেন্স রাখেন, ইতিহাস overwrite হয়ে যায়। Event Sourcing এখানে নিখুঁত সমাধান: প্রতিটি deposit/withdraw একটি immutable event; বর্তমান ব্যালেন্স event-গুলোর যোগফল; অতীতের যেকোনো অবস্থা সেই তারিখ পর্যন্ত event replay করে পাওয়া যায়; এবং সম্পূর্ণ audit trail স্বয়ংক্রিয়ভাবে থাকে। read-heavy ব্যালেন্স query-র জন্য CQRS দিয়ে একটি denormalized read model রাখা হয়।

Service Mesh-এর বাস্তব প্রয়োজন: এখন ধরুন এই ব্যাংকিং সিস্টেমে ৪০টি microservice (Java, Go, Python মিশ্রিত)। নিয়ন্ত্রক দাবি করে — সব internal সার্ভিস-যোগাযোগ অবশ্যই এনক্রিপ্টেড (mTLS); এবং আপনার গভীর observability দরকার (কোন কল ধীর, কোথায় ব্যর্থতা)।

প্রতিটি সার্ভিসে (তিন ভাষায়) আলাদাভাবে mTLS, retry, tracing লেখা — দুঃস্বপ্ন ও ত্রুটিপ্রবণ। Istio service mesh এই সমস্যা সমাধান করে: একটি কনফিগে সব সার্ভিসে স্বয়ংক্রিয় mTLS; কোড ছাড়াই retry/timeout/circuit breaking; এবং স্বয়ংক্রিয় metrics ও tracing — সব ভাষায় সমানভাবে। নতুন একটি payment সার্ভিস v2 ডিপ্লয় করতে চাইলে, Istio দিয়ে প্রথমে ৫% ট্র্যাফিক পাঠিয়ে (canary) নিরাপদে পরীক্ষা করা যায়।

এই দুই প্রযুক্তি মিলে একটি নিয়ন্ত্রক-সম্মত, নিরাপদ, পর্যবেক্ষণযোগ্য ও audit-যোগ্য ব্যাংকিং সিস্টেম গড়ে তোলে।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples — প্রোডাকশনে ব্যবহারযোগ্য)

Event-Sourced Aggregate (Python)

class BankAccount:
    def __init__(self):
        self.balance = 0
        self.version = 0

    # --- Command: ব্যবসায়িক নিয়ম যাচাই করে event তৈরি ---
    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("পর্যাপ্ত ব্যালেন্স নেই")
        return {"type": "Withdrew", "amount": amount}   # event (state বদলায় না সরাসরি)

    def deposit(self, amount):
        return {"type": "Deposited", "amount": amount}

    # --- Apply: event প্রয়োগ করে state গণনা (replay-এ ব্যবহৃত) ---
    def apply(self, event):
        if event["type"] == "Deposited":
            self.balance += event["amount"]
        elif event["type"] == "Withdrew":
            self.balance -= event["amount"]
        self.version += 1

    # --- replay: event ইতিহাস থেকে বর্তমান state পুনর্গঠন ---
    @classmethod
    def from_events(cls, events):
        acc = cls()
        for e in events:
            acc.apply(e)            # প্রতিটি event ক্রমে প্রয়োগ
        return acc

# ব্যবহার
events = load_events("account:42")          # event store থেকে
account = BankAccount.from_events(events)    # বর্তমান state পুনর্গঠন
new_event = account.deposit(100)
append_event("account:42", new_event)        # নতুন event append (overwrite নয়)

ব্যাখ্যা ও বাস্তব প্রয়োগ:
- command (deposit/withdraw) ব্যবসায়িক নিয়ম যাচাই করে শুধু একটি event তৈরি করে — state সরাসরি বদলায় না।
- apply একটি event নিয়ে state পরিবর্তন করে — এটিই replay-এর একক একক ধাপ।
- from_events সব event ক্রমে প্রয়োগ করে বর্তমান state পুনর্গঠন করে।
- নতুন পরিবর্তন মানে event store-এ একটি event append — পুরোনো কিছু overwrite হয় না (immutable, পূর্ণ audit)।
- প্রোডাকশনে: version দিয়ে optimistic concurrency (একই সময়ে দুটি লেখা সংঘর্ষ রোধ); নিয়মিত snapshot; event versioning কৌশল।

Istio Canary Deployment (VirtualService — সরাসরি ব্যবহারযোগ্য)

apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payment-route
spec:
  hosts: [payment-service]
  http:
    - route:
        - destination: { host: payment-service, subset: v1 }
          weight: 90              # ৯০% পুরোনো স্থিতিশীল সংস্করণে
        - destination: { host: payment-service, subset: v2 }
          weight: 10              # ১০% নতুন সংস্করণে (canary)
      retries:
        attempts: 3               # কোড ছাড়াই retry
        perTryTimeout: 2s         # প্রতি চেষ্টায় timeout

ব্যাখ্যা: এই Istio কনফিগ অ্যাপ কোড স্পর্শ না করেই — ১০% ট্র্যাফিক নতুন v2-তে পাঠাচ্ছে (canary: ছোট অংশে নতুন সংস্করণ পরীক্ষা, সমস্যা হলে দ্রুত ফিরে আসা সহজ), এবং একই সাথে retry + timeout (অধ্যায় ১১-এর resilience) প্রয়োগ করছে। weight বাড়িয়ে ধীরে ধীরে v2-তে পুরো ট্র্যাফিক সরানো যায়।

Istio mTLS সক্ষম করা (PeerAuthentication)

apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: banking
spec:
  mtls:
    mode: STRICT       # এই namespace-এর সব সার্ভিস-যোগাযোগ বাধ্যতামূলক এনক্রিপ্টেড

ব্যাখ্যা: এই একটি কনফিগ banking namespace-এর সব সার্ভিস-টু-সার্ভিস যোগাযোগে mutual TLS বাধ্যতামূলক করে — সব ট্র্যাফিক এনক্রিপ্টেড ও পারস্পরিক-প্রমাণিত হয়, অথচ কোনো অ্যাপ্লিকেশন কোড পরিবর্তন লাগে না। নিরাপত্তা/compliance প্রয়োজনে এটি service mesh-এর সবচেয়ে শক্তিশালী সুবিধাগুলোর একটি।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • ব্যাংকিং ও ফিনটেক: প্রায় সর্বত্র event sourcing-এর ধারণা (ledger) ব্যবহৃত — প্রতিটি লেনদেন immutable event, audit ও compliance-এর জন্য অপরিহার্য।
  • LMAX (ট্রেডিং প্ল্যাটফর্ম): event sourcing-এর বিখ্যাত প্রবক্তা — অত্যন্ত উচ্চ-পারফরম্যান্স ট্রেডিং সিস্টেম event-চালিত আর্কিটেকচারে।
  • Lyft: Envoy proxy তৈরি করে (পরে Istio-র ভিত্তি) — তাদের বিশাল microservices fleet-এ consistent নেটওয়ার্কিং ও observability-র জন্য।
  • Google / IBM: Istio তৈরি ও পৃষ্ঠপোষকতা; Google নিজে বিশাল-স্কেলে অভ্যন্তরীণভাবে mesh-জাতীয় প্যাটার্ন ব্যবহার করে।
  • Kubernetes ইকোসিস্টেম: Istio ও Linkerd এখন cloud-native microservices-এ mTLS, traffic management ও observability-র স্ট্যান্ডার্ড সমাধান।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- সরল CRUD অ্যাপে event sourcing ব্যবহার করা — বিশাল, অপ্রয়োজনীয় জটিলতা।
- ছোট সিস্টেমে (কয়েকটি সার্ভিস) service mesh যোগ করা — overhead সুবিধার চেয়ে বেশি।

Intermediate Mistakes:
- event sourcing-এ snapshot না রাখা — লক্ষ event replay-তে ধীরগতি।
- event versioning/schema evolution আগে থেকে পরিকল্পনা না করা — পরে পুরোনো event পড়তে গিয়ে আটকে যাওয়া।
- event store-কে mutable ভাবা বা event edit করার চেষ্টা — immutability-র মূল নীতি ভঙ্গ।

Production Mistakes:
- event sourcing-এ optimistic concurrency (version) ছাড়া সমান্তরাল লেখা — lost update।
- service mesh control plane redundant না রাখা।
- sidecar-এর latency/রিসোর্স overhead বিবেচনা না করা।
- mTLS/security policy ভুল কনফিগ করে সার্ভিস-যোগাযোগ ভেঙে ফেলা।

Scalability Mistakes:
- event store অসীম বাড়তে দেওয়া — archiving/snapshot কৌশল ছাড়া।
- event sourcing-এ সরাসরি event store-এ জটিল query করার চেষ্টা (CQRS read model না বানানো)।

Architecture Mistakes:
- event sourcing ও service mesh-কে "trend" হিসেবে যোগ করা, প্রকৃত প্রয়োজন ছাড়া।
- event sourcing-এ event-গুলোকে ব্যবসায়িক ঘটনা না করে কারিগরি CRUD operation হিসেবে মডেল করা (যেমন RowUpdated — অর্থহীন)।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: Event Sourcing কী?

একটি entity-র বর্তমান অবস্থা সরাসরি সংরক্ষণের বদলে, তার ওপর ঘটে যাওয়া প্রতিটি ঘটনাকে (event) immutable, append-only ক্রমে সংরক্ষণ করা; বর্তমান অবস্থা = এই event-গুলো replay করে গণনা করা ফল। event-ই source of truth।

Intermediate প্রশ্ন: Event Sourcing-এর প্রধান সুবিধা ও চ্যালেঞ্জ কী?

সুবিধা — সম্পূর্ণ audit trail, time-travel (অতীতের state), debugging, নতুন read model সহজে তৈরি। চ্যালেঞ্জ — event versioning/schema evolution, eventual consistency, জটিলতা, সরাসরি query কঠিন (CQRS লাগে), এবং ক্রমবর্ধমান storage।

Intermediate প্রশ্ন: Sidecar proxy প্যাটার্ন কী?

প্রতিটি সার্ভিস instance-এর পাশে একটি সহায়ক proxy (আলাদা প্রসেস/container) চলে, যার মধ্য দিয়ে সার্ভিসের সব নেটওয়ার্ক ট্র্যাফিক যায়। এটি discovery, retry, mTLS, metrics-এর মতো নেটওয়ার্ক-কাজ অ্যাপ কোড থেকে আলাদা করে, ভাষা-নিরপেক্ষভাবে।

Advanced প্রশ্ন: Service Mesh-এ Data Plane ও Control Plane-এর পার্থক্য কী?

Data plane হলো সব sidecar proxy — যা প্রকৃত সার্ভিস-টু-সার্ভিস ট্র্যাফিক বহন করে এবং retry/load balancing/mTLS/metrics বাস্তবে প্রয়োগ করে। Control plane (যেমন istiod) প্রকৃত ট্র্যাফিক বহন করে না; এটি proxy-গুলোকে কনফিগার ও সমন্বয় করে — routing rules, security policy, certificate বিতরণ করে।

Advanced প্রশ্ন: কখন service mesh ব্যবহার করবেন, কখন নয়?

ব্যবহার করুন — অনেক (ডজন+) সার্ভিস, বহু ভাষা, mTLS/নিরাপত্তা, fine-grained traffic control (canary), গভীর observability দরকার, এবং পরিচালনার টিম আছে। এড়ান — কম সার্ভিস, সরল সিস্টেম, ছোট টিম; তখন mesh-এর অপারেশনাল জটিলতা ও overhead সুবিধার চেয়ে বেশি; লাইব্রেরি বা API Gateway যথেষ্ট।

System Design প্রশ্ন: একটি audit-critical ব্যাংকিং সিস্টেম ডিজাইন করুন যেখানে সম্পূর্ণ লেনদেন ইতিহাস ও নিরাপদ সার্ভিস-যোগাযোগ দরকার।

ডাটা স্তরে Event Sourcing — প্রতিটি লেনদেন immutable event, পূর্ণ audit ও time-travel; read-heavy ব্যালেন্স/statement-এ CQRS read model; snapshot দিয়ে replay অপ্টিমাইজ; event versioning কৌশল। অবকাঠামো স্তরে Service Mesh (Istio) — স্বয়ংক্রিয় mTLS (এনক্রিপ্টেড সার্ভিস-যোগাযোগ), কোড ছাড়াই retry/circuit breaking, canary deployment, ও observability (tracing/metrics)। সব উপাদান redundant।

১০. সেরা চর্চা (Best Practices — সরাসরি প্রয়োগযোগ্য)

  • Event Sourcing শুধু যেখানে audit/history/temporal query সত্যিই দরকার — সরল CRUD-এ নয়।
  • event-গুলোকে ব্যবসায়িক ঘটনা হিসেবে মডেল করুন (MoneyWithdrawn), কারিগরি CRUD হিসেবে নয় (RowUpdated)।
  • snapshot ও event versioning কৌশল শুরু থেকেই পরিকল্পনা করুন; event immutable রাখুন।
  • Event Sourcing-এ optimistic concurrency (version) দিয়ে সমান্তরাল লেখা সুরক্ষিত করুন।
  • query-র জন্য CQRS read model ব্যবহার করুন — সরাসরি event store-এ জটিল query নয়।
  • Service Mesh শুধু যখন স্কেল ও প্রয়োজন (mTLS, traffic control, observability) তা সমর্থন করে — overhead বুঝে।
  • mesh control plane redundant রাখুন; mTLS/policy পরিবর্তন সাবধানে (যোগাযোগ ভেঙে না ফেলে)।
  • নতুন সংস্করণে canary deployment (Istio weight) ব্যবহার করুন — নিরাপদ rollout-এ।
  • সব প্যাটার্নের ট্রেড-অফ ও overhead বুঝে গ্রহণ করুন — trend হিসেবে নয়।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Event Sourcing = current state নয়, প্রতিটি পরিবর্তনের immutable event ক্রম সংরক্ষণ; state = event replay-এর ফল; event-ই source of truth।
- Event Store = append-only; replay দিয়ে state পুনর্গঠন; snapshot দিয়ে অপ্টিমাইজ।
- সুবিধা: audit trail, time-travel, debugging, নতুন read model; চ্যালেঞ্জ: versioning, eventual consistency, জটিলতা, query।
- Event Sourcing + CQRS স্বাভাবিক জুটি — event store source of truth, denormalized read model query-র জন্য।
- Sidecar Proxy = প্রতি সার্ভিসের পাশে proxy; নেটওয়ার্ক-লজিক অ্যাপ কোড থেকে আলাদা, ভাষা-নিরপেক্ষ।
- Service Mesh = sidecar-গুলোর সমন্বিত নেটওয়ার্ক স্তর; Data Plane (প্রকৃত ট্র্যাফিক, proxy) vs Control Plane (config/coordination)।
- মূল ক্ষমতা: traffic management (canary), resilience (retry/circuit breaking), security (mTLS), observability।
- Istio = জনপ্রিয় mesh; Envoy (data plane) + istiod (control plane); declarative YAML কনফিগ। প্রয়োজন প্রমাণিত হলে তবেই গ্রহণ।

গুরুত্বপূর্ণ পরিভাষা: Event Sourcing, Event Store, Append-Only, Immutable, Replay, Snapshot, Aggregate, Projector, Time Travel, Event Versioning, Upcasting, CQRS, Sidecar Proxy, Envoy, Service Mesh, Data Plane, Control Plane, istiod, mTLS, Traffic Management, Canary Deployment, VirtualService, Observability, Fault Injection।
