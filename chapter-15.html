📖 অধ্যায় ১৫

অধ্যায় ১৫: Service Discovery, API Gateway, Backend For Frontend (BFF), SAGA Pattern ও CQRS

১. অধ্যায় পরিচিতি (Chapter Introduction)

এতদিন আমরা microservices-এর মৌলিক উপাদানগুলো একে একে শিখেছি — কীভাবে তারা যোগাযোগ করে (অধ্যায় ৭), message queue দিয়ে decouple হয় (অধ্যায় ৮), এবং distributed transaction-এর চ্যালেঞ্জ (অধ্যায় ১৪)। কিন্তু যখন আপনার ৫টি নয়, ৫০টি বা ৫০০টি সার্ভিস থাকে, তখন কিছু নতুন, কঠিন প্রশ্ন জন্ম নেয় — যেগুলো একটি বা দুটি সার্ভিসে কখনো ভাবতে হয়নি।

প্রথমত, সার্ভিসগুলো ক্রমাগত উঠছে-নামছে (auto-scaling), তাদের IP বদলাচ্ছে। তাহলে Service A কীভাবে জানবে Service B এই মুহূর্তে কোথায় (কোন IP-তে) আছে? — এর উত্তর Service Discovery।

দ্বিতীয়ত, একটি মোবাইল অ্যাপকে কি ৫০টি সার্ভিসের ৫০টি ঠিকানা জানতে হবে? প্রতিটির authentication, rate limiting আলাদাভাবে সামলাতে হবে? — না, এর সমাধান একটি একক প্রবেশদ্বার: API Gateway। আর যখন বিভিন্ন client (মোবাইল, ওয়েব, IoT)-এর ভিন্ন প্রয়োজন, তখন আসে Backend For Frontend (BFF)।

তৃতীয়ত, অধ্যায় ১৪-এ আমরা দেখেছি একাধিক সার্ভিস জুড়ে atomic transaction কঠিন এবং 2PC blocking সমস্যা তৈরি করে। এর আধুনিক সমাধান SAGA Pattern — যা এই অধ্যায়ে বিস্তারিত আলোচনা করব।

চতুর্থত, একটি সিস্টেমে read ও write-এর চাহিদা প্রায়ই খুব ভিন্ন। এদের আলাদা করে অপ্টিমাইজ করার শক্তিশালী প্যাটার্ন CQRS।

এই পাঁচটি প্যাটার্ন একসাথে আধুনিক microservices আর্কিটেকচারের কাঠামো গড়ে তোলে। এগুলো গভীরভাবে বুঝলে আপনি একটি প্রকৃত production-grade distributed system ডিজাইন করতে পারবেন।

২. শেখার লক্ষ্য (Learning Objectives)

এই অধ্যায় শেষে আপনি গভীরভাবে বুঝতে ও প্রয়োগ করতে পারবেন:

  • Service Discovery — client-side vs server-side, service registry, health-based discovery
  • API Gateway — দায়িত্ব, প্যাটার্ন, এবং কেন এটি single point of failure না করতে হয়
  • Backend For Frontend (BFF) — কখন ও কেন প্রতিটি client-এর জন্য আলাদা gateway
  • SAGA Pattern — Choreography vs Orchestration, compensating transaction
  • CQRS — read/write মডেল আলাদা করা, কখন উপযুক্ত, Event Sourcing-এর সাথে সম্পর্ক
  • এই প্যাটার্নগুলো কীভাবে একসাথে কাজ করে এবং তাদের ট্রেড-অফ

৩. মূল ধারণা (Core Concepts)

৩.১ Service Discovery — সার্ভিসরা কীভাবে একে অপরকে খুঁজে পায়

একটি স্থির (static) জগতে, Service A জানে Service B http://192.168.1.10:8080-এ আছে — কনফিগে হার্ডকোড করা। কিন্তু আধুনিক ক্লাউডে এটি অসম্ভব: সার্ভিস auto-scale করে (নতুন instance যোগ/সরে), crash করে নতুন IP-তে restart হয়, container প্রতিবার নতুন ঠিকানা পায়। তাই IP হার্ডকোড করা মানেই ভাঙন।

Service Discovery হলো সেই প্রক্রিয়া যার মাধ্যমে সার্ভিসগুলো রানটাইমে একে অপরের নেটওয়ার্ক অবস্থান (IP+port) গতিশীলভাবে খুঁজে পায়। এর কেন্দ্রে থাকে একটি Service Registry — একটি ডাটাবেস যেখানে প্রতিটি চলমান সার্ভিস instance তার ঠিকানা নিবন্ধন (register) করে।

দুটি প্রধান প্যাটার্ন:

Client-Side Discovery:
client (অর্থাৎ caller সার্ভিস) সরাসরি service registry-কে জিজ্ঞেস করে "Service B-এর সুস্থ instance-গুলো কোথায়?", একটি তালিকা পায়, এবং নিজেই একটি বেছে নেয় (নিজে load balancing করে)।
- সুবিধা: কম network hop (সরাসরি কল); client বুদ্ধিমান load balancing করতে পারে।
- অসুবিধা: প্রতিটি client-এ discovery লজিক থাকতে হয় (প্রতিটি ভাষায়); registry-র সাথে coupling বাড়ে।
- উদাহরণ: Netflix Eureka + Ribbon।

Server-Side Discovery:
client শুধু একটি load balancer/router-কে অনুরোধ পাঠায়; সেই router registry দেখে সঠিক instance-এ রুট করে। client discovery সম্পর্কে কিছুই জানে না।
- সুবিধা: client সরল থাকে; discovery লজিক কেন্দ্রীভূত।
- অসুবিধা: অতিরিক্ত network hop; router একটি গুরুত্বপূর্ণ উপাদান (redundant রাখতে হয়)।
- উদাহরণ: Kubernetes Service (DNS + kube-proxy), AWS ELB।

Registration কীভাবে হয়:
- Self-Registration: instance চালু হয়ে নিজে registry-তে register করে এবং নিয়মিত heartbeat পাঠায় (জীবিত আছে জানাতে); heartbeat থামলে registry তাকে সরিয়ে দেয়।
- Third-Party Registration: একটি আলাদা "registrar" (যেমন orchestrator) instance-গুলোর জীবন পর্যবেক্ষণ করে registry আপডেট করে। Kubernetes এভাবে কাজ করে।

জনপ্রিয় টুল: Consul, etcd, ZooKeeper, Netflix Eureka, এবং Kubernetes-এর built-in DNS-ভিত্তিক discovery। (লক্ষ্য করুন — registry নিজে strong consistency দরকার, তাই অধ্যায় ১৩-এর consensus এর ভিত্তি।)

৩.২ API Gateway — সিস্টেমের একক প্রবেশদ্বার

যখন একটি client (মোবাইল/ওয়েব) সরাসরি ডজনখানেক microservice-এর সাথে কথা বলে, অনেক সমস্যা হয়: client-কে সব সার্ভিসের ঠিকানা জানতে হয়; প্রতিটিতে আলাদাভাবে authentication করতে হয়; একটি স্ক্রিন রেন্ডার করতে হয়তো ৭টি আলাদা কল লাগে (chatty, ধীর, বিশেষত মোবাইলে); এবং internal আর্কিটেকচার client-এ ফাঁস হয়ে যায়।

API Gateway হলো সব client অনুরোধের একটি একক প্রবেশদ্বার, যা অনুরোধ গ্রহণ করে সঠিক backend সার্ভিসে রুট করে এবং অনেক সাধারণ দায়িত্ব (cross-cutting concern) এক জায়গায় সামলায়।

API Gateway-এর দায়িত্ব (বাস্তবে যা যা করে):
- Routing: অনুরোধকে সঠিক সার্ভিসে পাঠানো (যেমন /orders/* → Order Service)।
- Authentication & Authorization: এক জায়গায় টোকেন/JWT যাচাই — প্রতিটি সার্ভিসে আলাদা করতে হয় না।
- Rate Limiting & Throttling: অপব্যবহার রোধ (অধ্যায় ১১)।
- Request Aggregation / Composition: একাধিক সার্ভিসের কল একত্র করে একটি client-friendly উত্তর তৈরি (chatty কল কমায়)।
- Protocol Translation: বাইরে REST, ভেতরে gRPC — অনুবাদ করা।
- SSL Termination, Caching, Logging, Monitoring, Request/Response transformation।

মূল সতর্কতা — API Gateway একটি সম্ভাব্য Single Point of Failure ও bottleneck। তাই এটি অবশ্যই redundant (একাধিক instance) ও scalable হতে হবে; এবং এতে অতিরিক্ত ব্যবসায়িক লজিক না রেখে একে পাতলা (thin) রাখতে হবে — নইলে এটি একটি নতুন মনোলিথে পরিণত হয়।

জনপ্রিয় টুল: Kong, AWS API Gateway, NGINX, Apigee, Spring Cloud Gateway, Envoy।

৩.৩ Backend For Frontend (BFF)

একটি একক API Gateway সব client-কে একই উত্তর দেয়। কিন্তু সমস্যা — একটি মোবাইল অ্যাপের প্রয়োজন একটি ডেস্কটপ ওয়েব অ্যাপ থেকে ভিন্ন। মোবাইলে কম ডাটা, কম কল, ছোট payload দরকার (ব্যান্ডউইথ/ব্যাটারি); ওয়েবে হয়তো বেশি বিস্তারিত ডাটা; একটি smart TV বা IoT-এর আবার ভিন্ন প্রয়োজন।

BFF (Backend For Frontend) প্যাটার্নে — একটি সাধারণ gateway-র বদলে প্রতিটি client টাইপের জন্য একটি আলাদা, উপযোগী backend/gateway তৈরি করা হয়। যেমন Mobile BFF, Web BFF, IoT BFF। প্রতিটি BFF তার নির্দিষ্ট client-এর প্রয়োজন অনুযায়ী ডাটা একত্র করে, ছাঁটে, ও ফরম্যাট করে।

  • সুবিধা: প্রতিটি client-এর জন্য অপ্টিমাইজড ও সরল API; frontend টিম তাদের নিজের BFF দ্রুত পরিবর্তন করতে পারে অন্যকে প্রভাবিত না করে; over-fetching কমে।
  • অসুবিধা: একাধিক BFF মানে কোড ডুপ্লিকেশন ও রক্ষণাবেক্ষণের ভার বাড়ে; সাধারণ লজিক শেয়ার করার পরিকল্পনা লাগে।
  • কখন: যখন client টাইপগুলোর প্রয়োজন উল্লেখযোগ্যভাবে ভিন্ন। কম client বা সদৃশ প্রয়োজন হলে একটি সাধারণ gateway-ই যথেষ্ট।

সম্পর্ক: BFF হলো API Gateway প্যাটার্নের একটি বিশেষায়িত রূপ — "এক gateway সবার জন্য"-র বদলে "প্রতি frontend-এর জন্য এক gateway"।

৩.৪ SAGA Pattern — distributed transaction-এর আধুনিক সমাধান

অধ্যায় ১৪-এ আমরা দেখেছি — একাধিক সার্ভিস জুড়ে atomicity দরকার, কিন্তু 2PC blocking ও ধীর। SAGA এর সমাধান দেয় ভিন্নভাবে: একটি বড় distributed transaction-কে ছোট ছোট লোকাল transaction-এর একটি ক্রম হিসেবে দেখা হয়। প্রতিটি ধাপ তার নিজের সার্ভিসে স্থানীয়ভাবে commit করে এবং পরের ধাপকে ট্রিগার করে।

মূল চাতুর্য: যদি কোনো ধাপ ব্যর্থ হয়, তাহলে rollback করার বদলে (যা ইতিমধ্যে committed লোকাল transaction-এ সম্ভব নয়), আগের সফল ধাপগুলোর জন্য Compensating Transaction চালানো হয় — অর্থাৎ একটি বিপরীত কাজ যা পূর্বের প্রভাব বাতিল করে। যেমন "টাকা কাটা হয়েছিল" → compensation: "টাকা ফেরত দাও"; "পণ্য রিজার্ভ হয়েছিল" → compensation: "রিজার্ভ ছেড়ে দাও"।

SAGA-এর দুটি বাস্তবায়ন শৈলী:

১. Choreography (কোরিওগ্রাফি — বিকেন্দ্রীভূত):
কোনো কেন্দ্রীয় নিয়ন্ত্রক নেই। প্রতিটি সার্ভিস একটি event publish করে, এবং পরের সার্ভিস সেই event শুনে নিজের কাজ করে ও নিজের event publish করে — এভাবে একটি শৃঙ্খল চলে (অধ্যায় ৭-এর event-driven)। ব্যর্থতায় সংশ্লিষ্ট সার্ভিস একটি "failed" event publish করে, যা শুনে আগের সার্ভিসগুলো compensation চালায়।
- সুবিধা: loose coupling, কোনো single point of failure নেই, সরল ও দ্রুত (কম সার্ভিসে)।
- অসুবিধা: পুরো প্রবাহ কোথাও স্পষ্ট লেখা নেই — বোঝা ও debug করা কঠিন; cyclic dependency-র ঝুঁকি; বেশি সার্ভিসে জটিল।

২. Orchestration (অর্কেস্ট্রেশন — কেন্দ্রীভূত):
একটি কেন্দ্রীয় Orchestrator (SAGA coordinator) পুরো প্রবাহ নিয়ন্ত্রণ করে — সে ধাপে ধাপে প্রতিটি সার্ভিসকে কমান্ড পাঠায়, উত্তরের জন্য অপেক্ষা করে, এবং সিদ্ধান্ত নেয় পরের ধাপ নাকি compensation। প্রবাহটি orchestrator-এ একটি state machine হিসেবে স্পষ্ট থাকে।
- সুবিধা: প্রবাহ স্পষ্ট ও কেন্দ্রীভূত (বোঝা/debug সহজ); জটিল প্রবাহ সামলানো সহজ; cyclic dependency নেই।
- অসুবিধা: orchestrator একটি অতিরিক্ত উপাদান (redundant রাখতে হয়); সামান্য coupling (orchestrator সব সার্ভিস জানে)।
- উদাহরণ: Netflix Conductor, Temporal, AWS Step Functions, Camunda।

ব্যবহারিক নিয়ম: কম ধাপ ও সরল প্রবাহে Choreography; বেশি ধাপ, জটিল শর্ত, বা স্পষ্ট দৃশ্যমানতা দরকার হলে Orchestration। SAGA সর্বদা eventual consistency দেয় (তাৎক্ষণিক atomicity নয়) — এটি গ্রহণযোগ্য কি না তা ব্যবসায়িকভাবে নিশ্চিত করুন।

৩.৫ CQRS — Command Query Responsibility Segregation

ঐতিহ্যগতভাবে আমরা একই মডেল (একই টেবিল, একই object) দিয়ে ডাটা পড়ি ও লিখি। কিন্তু read ও write-এর চাহিদা প্রায়ই মৌলিকভাবে ভিন্ন: লেখা (write) সাধারণত normalized, validation-ভারী, ও কম-ঘন; পড়া (read) প্রায়ই অনেক বেশি ঘন, denormalized, ও বিভিন্ন ভিউতে দরকার। একটি মডেল দিয়ে উভয় সামলালে আপস (compromise) করতে হয়।

CQRS (Command Query Responsibility Segregation) এই দুটিকে আলাদা করে: Command (write — যা state বদলায়) এবং Query (read — যা শুধু ডাটা ফেরত দেয়) — দুটির জন্য আলাদা মডেল, এবং প্রায়ই আলাদা ডাটা স্টোর ব্যবহার করা হয়।

কীভাবে কাজ করে:
- Write side (Command): ব্যবসায়িক নিয়ম ও validation সহ একটি normalized মডেলে লেখা হয় (যেমন একটি RDBMS)।
- Read side (Query): এক বা একাধিক denormalized, query-অপ্টিমাইজড read model (যেমন Elasticsearch, একটি denormalized view, বা cache) — যা দ্রুত পড়ার জন্য তৈরি।
- দুই পক্ষ সিঙ্ক হয় সাধারণত event বা replication-এর মাধ্যমে — write হলে একটি event read model আপডেট করে (প্রায়ই asynchronously, তাই eventual consistency)।

সুবিধা:
- read ও write স্বাধীনভাবে scale করা যায় (যেমন read-heavy সিস্টেমে অনেক read replica)।
- প্রতিটি দিক তার নিজের জন্য অপ্টিমাইজড (read model দ্রুত query-র জন্য, write model integrity-র জন্য)।
- একাধিক বিশেষায়িত read view তৈরি করা যায়।

অসুবিধা / খরচ:
- উল্লেখযোগ্য জটিলতা ও কোড বৃদ্ধি — দুটি মডেল রক্ষণাবেক্ষণ।
- read ও write-এর মধ্যে eventual consistency (read সামান্য পুরোনো হতে পারে — UI-তে সামলাতে হয়)।
- এটি একটি বিশেষায়িত প্যাটার্ন — সব জায়গায় নয়। সরল CRUD অ্যাপে CQRS over-engineering। শুধু তখনই ব্যবহার করুন যখন read/write চাহিদা সত্যিই খুব ভিন্ন বা scale খুব বেশি।

Event Sourcing-এর সাথে সম্পর্ক: CQRS প্রায়ই Event Sourcing (অধ্যায় ১৬-এ বিস্তারিত)-এর সাথে জোড়ায় ব্যবহৃত হয় — যেখানে সব পরিবর্তন event হিসেবে সংরক্ষিত হয়, এবং সেই event থেকে read model গুলো তৈরি করা হয়। তবে দুটি স্বাধীন প্যাটার্ন — একটি ছাড়া অন্যটি ব্যবহার করা যায়।

৪. বাস্তব সমস্যা (Real-World Problem Statement)

ধরুন আপনার একটি food delivery অ্যাপ আছে যাতে ডজনখানেক microservice (User, Restaurant, Order, Payment, Delivery, Notification)। একটি অর্ডার দেওয়ার সময় এই প্যাটার্নগুলো কীভাবে একসাথে কাজ করে দেখুন:

  1. মোবাইল অ্যাপ একটি অনুরোধ পাঠায় — কিন্তু ডজন সার্ভিসের ঠিকানা জানে না, জানার দরকারও নেই। এটি Mobile BFF-এ যায় (BFF মোবাইলের জন্য পাতলা, অপ্টিমাইজড payload দেয়)।

  2. BFF/API Gateway টোকেন যাচাই করে (auth), rate limit চেক করে, এবং অর্ডার অনুরোধ Order Service-এ রুট করে।

  3. Order Service-এর Payment, Inventory, Delivery — সবার ঠিকানা Service Discovery (যেমন Kubernetes DNS/Consul) থেকে রানটাইমে পায় — হার্ডকোড নয়, কারণ এই সার্ভিসগুলো auto-scale করছে।

  4. অর্ডার সম্পন্ন করতে payment, inventory reservation, ও delivery assignment — তিনটি সার্ভিস জুড়ে atomicity দরকার। 2PC-র blocking এড়িয়ে এখানে একটি SAGA (Orchestration) ব্যবহার করা হয়: orchestrator ধাপে ধাপে payment → inventory → delivery চালায়; inventory ব্যর্থ হলে payment-এ compensating "refund" চালায়। eventual consistency গ্রহণযোগ্য।

  5. ব্যবহারকারীর "Order Status" পেজ অত্যন্ত ঘন পড়া হয় (read-heavy), কিন্তু অর্ডার write তুলনায় কম। তাই CQRS ব্যবহার করে একটি denormalized read model (যেমন একটি ডকুমেন্ট স্টোর) তৈরি করা হয় — যা সব সার্ভিসের event শুনে অর্ডারের সম্পূর্ণ চিত্র এক জায়গায় রাখে, ফলে status query দ্রুত ও সস্তা।

এই পাঁচটি প্যাটার্ন মিলে সিস্টেমটিকে scalable, maintainable ও resilient করে। প্রতিটির অনুপস্থিতিতে একটি নির্দিষ্ট সমস্যা ফিরে আসে — discovery ছাড়া hardcoded IP ভাঙন, gateway ছাড়া chatty/অনিরাপদ client, SAGA ছাড়া inconsistent অর্ডার, CQRS ছাড়া ধীর status পেজ।

৬. ইমপ্লিমেন্টেশন উদাহরণ (Implementation Examples — প্রোডাকশনে ব্যবহারযোগ্য)

SAGA Orchestrator (Python — ধারণাগত, state machine)

class OrderSaga:
    def execute(self, order):
        completed = []           # সফল ধাপ — ব্যর্থতায় compensate করতে
        try:
            payment_id = payment_service.charge(order)      # ধাপ ১
            completed.append(("payment", payment_id))

            reservation = inventory_service.reserve(order)  # ধাপ ২
            completed.append(("inventory", reservation))

            delivery_id = delivery_service.assign(order)    # ধাপ ৩
            completed.append(("delivery", delivery_id))

            return "Order confirmed"
        except Exception as e:
            # কোনো ধাপ ব্যর্থ — সফল ধাপগুলো বিপরীত ক্রমে compensate
            self.compensate(completed)
            return f"Order failed, rolled back: {e}"

    def compensate(self, completed):
        for step, ref in reversed(completed):   # বিপরীত ক্রমে undo
            if step == "payment":
                payment_service.refund(ref)            # টাকা ফেরত
            elif step == "inventory":
                inventory_service.release(ref)         # রিজার্ভ ছাড়া
            elif step == "delivery":
                delivery_service.cancel(ref)           # delivery বাতিল

ব্যাখ্যা ও বাস্তব প্রয়োগ:
- orchestrator ধাপগুলো ক্রমে চালায় এবং প্রতিটি সফল ধাপ completed-এ রাখে।
- কোনো ধাপ ব্যর্থ হলে compensate সফল ধাপগুলোকে বিপরীত ক্রমে undo করে — প্রতিটি ধাপের জন্য একটি নির্দিষ্ট compensating action (refund/release/cancel)।
- বাস্তব প্রোডাকশনে: এই saga state durable-ভাবে (DB-তে) সংরক্ষণ করুন, যাতে orchestrator crash করলেও কোথায় ছিল তা পুনরুদ্ধার করা যায়; প্রতিটি step ও compensation idempotent হতে হবে (অধ্যায় ১৪) কারণ retry হতে পারে; timeout ও DLQ যুক্ত করুন। Temporal/Step Functions এসব স্বয়ংক্রিয়ভাবে দেয়।

CQRS — read model event দিয়ে আপডেট (Python)

# Write side — command, normalized write store-এ লেখে + event publish
def place_order(cmd):
    order = write_db.insert_order(cmd)          # validation, business rules
    event_bus.publish("OrderPlaced", {
        "order_id": order.id, "user": cmd.user,
        "items": cmd.items, "total": order.total
    })
    return order.id

# Read side — event শুনে denormalized read model আপডেট
def on_order_placed(event):
    read_db.upsert_order_view({                 # denormalized, query-অপ্টিমাইজড
        "order_id": event["order_id"],
        "user_name": lookup_user_name(event["user"]),  # আগেই join করে রাখা
        "item_count": len(event["items"]),
        "total": event["total"],
        "status": "placed"
    })

# Query side — দ্রুত পড়া, কোনো join নেই
def get_order_view(order_id):
    return read_db.find_order_view(order_id)     # এক lookup, অত্যন্ত দ্রুত

ব্যাখ্যা: write side normalized store-এ লেখে ও একটি event publish করে। read side সেই event শুনে একটি denormalized view তৈরি করে (যেমন user নাম আগেই যুক্ত করে রাখা) — তাই query-তে কোনো ব্যয়বহুল join লাগে না, পড়া অত্যন্ত দ্রুত। লক্ষ্য করুন read model write-এর সামান্য পরে আপডেট হয় (eventual consistency)।

Kubernetes Service Discovery (DNS — সরল, বাস্তব)

apiVersion: v1
kind: Service
metadata:
  name: payment-service        # এই নামই DNS হয়ে যায়
spec:
  selector:
    app: payment               # এই label-যুক্ত সব pod-এ load balance
  ports:
    - port: 80
      targetPort: 8080

ব্যাখ্যা: Kubernetes-এ একটি Service তৈরি করলে অন্য সার্ভিস শুধু http://payment-service নামে কল করতে পারে — IP জানার দরকার নেই। Kubernetes ভেতরে DNS + endpoint tracking দিয়ে এই নামকে সুস্থ pod-এর IP-তে রূপান্তর করে (server-side discovery) এবং load balance করে। pod auto-scale/restart-এ IP বদলালেও নাম অপরিবর্তিত — এটিই discovery-র সৌন্দর্য।

৭. ইন্ডাস্ট্রি কেস স্টাডি (Industry Case Studies)

  • Netflix: Eureka (service discovery), Zuul (API gateway), Conductor (SAGA orchestration) — এই প্যাটার্নগুলোর অনেকগুলোর জনপ্রিয়করণে Netflix অগ্রণী; BFF প্যাটার্নও তাদের বিভিন্ন ডিভাইসের (TV, মোবাইল, ওয়েব) জন্য ব্যবহৃত।
  • SoundCloud: BFF প্যাটার্নের উৎপত্তির সাথে যুক্ত — মোবাইল ও ওয়েবের ভিন্ন প্রয়োজনে আলাদা backend তৈরি করে।
  • Uber: বিশাল microservices fleet-এ service discovery, API gateway, এবং অর্ডার/ট্রিপ প্রবাহে SAGA-জাতীয় প্যাটার্ন ব্যবহার করে।
  • Kubernetes (industry standard): built-in DNS-ভিত্তিক service discovery দিয়ে এই সমস্যা স্ট্যান্ডার্ড করেছে; Istio (service mesh — অধ্যায় ১৬) discovery ও routing আরও উন্নত করে।
  • Banking/E-commerce: অর্ডার ও পেমেন্ট প্রবাহে SAGA + idempotency + outbox ব্যাপকভাবে ব্যবহৃত; অর্ডার status-এ CQRS।

৮. সাধারণ ভুল (Common Mistakes)

Beginner Mistakes:
- সার্ভিস IP হার্ডকোড করা — auto-scale/restart-এ ভাঙন।
- API Gateway-কে single point of failure রেখে দেওয়া (redundant না করা)।

Intermediate Mistakes:
- API Gateway-তে ভারী ব্যবসায়িক লজিক রাখা — এটি একটি নতুন মনোলিথ হয়ে যায়।
- SAGA-তে compensating transaction ডিজাইন না করা বা সেগুলো idempotent না করা।
- CQRS-কে সব জায়গায় ব্যবহার করা — সরল CRUD-এ over-engineering।

Production Mistakes:
- SAGA orchestrator-এর state durable না রাখা — crash-এ saga "আটকে" বা অর্ধসম্পন্ন থাকে।
- SAGA-তে eventual consistency-র প্রভাব UI/ব্যবসায় না বোঝা (ব্যবহারকারী মাঝপথের অবস্থা দেখে)।
- CQRS-এ read model sync ব্যর্থতা/lag মনিটর না করা — stale read নীরবে।
- service registry-কে redundant/consistent না করা — discovery ব্যর্থ হলে সব সার্ভিস অন্ধ।

Scalability Mistakes:
- একটি BFF/gateway-তে সব client চাপিয়ে অপ্টিমাইজেশন হারানো; বা উল্টো — অপ্রয়োজনে বহু BFF বানিয়ে রক্ষণাবেক্ষণ বিস্ফোরণ।
- Choreography SAGA বহু সার্ভিসে ব্যবহার করে প্রবাহ অবোধ্য করে তোলা।

Architecture Mistakes:
- distributed transaction-এ কোনো কৌশল (SAGA) ছাড়াই কাজ — partial failure-এ inconsistent state।
- discovery, gateway, SAGA, CQRS — প্রতিটির ট্রেড-অফ না বুঝে "trend" হিসেবে যোগ করা।

৯. ইন্টারভিউ দৃষ্টিভঙ্গি (Interview Perspective)

Beginner প্রশ্ন: Service Discovery কেন দরকার?

আধুনিক ক্লাউডে সার্ভিস auto-scale/restart করে IP বদলায়, তাই হার্ডকোড করা যায় না। Service discovery সার্ভিসগুলোকে রানটাইমে একে অপরের অবস্থান গতিশীলভাবে খুঁজতে দেয়, একটি service registry-র মাধ্যমে।

Intermediate প্রশ্ন: API Gateway কী দায়িত্ব পালন করে?

একক প্রবেশদ্বার হিসেবে routing, authentication/authorization, rate limiting, request aggregation, protocol translation, SSL termination, logging — এসব cross-cutting concern এক জায়গায় সামলায়, যাতে client সরল থাকে ও সার্ভিসগুলোকে বারবার এসব করতে না হয়।

Intermediate প্রশ্ন: BFF প্যাটার্ন কখন ব্যবহার করবেন?

যখন বিভিন্ন client টাইপের (মোবাইল/ওয়েব/IoT) প্রয়োজন উল্লেখযোগ্যভাবে ভিন্ন — প্রতিটির জন্য আলাদা, অপ্টিমাইজড backend তৈরি করে। কম বা সদৃশ client হলে একটি সাধারণ gateway-ই যথেষ্ট।

Advanced প্রশ্ন: SAGA-তে Choreography আর Orchestration-এর মধ্যে কীভাবে বাছবেন?

Choreography বিকেন্দ্রীভূত (event-driven, কোনো coordinator নেই) — loose coupling ও সরলতা দেয়, কিন্তু প্রবাহ অস্পষ্ট ও বড় সিস্টেমে debug কঠিন। Orchestration কেন্দ্রীভূত (একটি orchestrator) — প্রবাহ স্পষ্ট ও জটিল প্রবাহ সামলানো সহজ, কিন্তু একটি অতিরিক্ত উপাদান। কম/সরল ধাপে Choreography; বেশি/জটিল ধাপে Orchestration।

Advanced প্রশ্ন: CQRS কী এবং এর প্রধান ট্রেড-অফ কী?

Command (write) ও Query (read)-এর জন্য আলাদা মডেল (ও প্রায়ই আলাদা স্টোর) ব্যবহার — যাতে প্রতিটি স্বাধীনভাবে scale ও অপ্টিমাইজ হয়। ট্রেড-অফ: উল্লেখযোগ্য জটিলতা ও দুটি মডেলের রক্ষণাবেক্ষণ, এবং read/write-এর মধ্যে eventual consistency। সরল CRUD-এ এটি over-engineering।

System Design প্রশ্ন: একটি food delivery সিস্টেমের অর্ডার flow ডিজাইন করুন (multiple services সহ)।

client → client-নির্দিষ্ট BFF → API Gateway (auth, rate limit, routing)। সার্ভিসগুলো Service Discovery (Kubernetes DNS/Consul) দিয়ে একে অপরকে খুঁজে। অর্ডার সম্পন্নে payment+inventory+delivery জুড়ে SAGA (Orchestration) — ব্যর্থতায় compensating refund/release; প্রতিটি step idempotent + outbox দিয়ে নির্ভরযোগ্য event। read-heavy order status-এ CQRS — event থেকে denormalized read model। সবই redundant ও monitored।

১০. সেরা চর্চা (Best Practices — সরাসরি প্রয়োগযোগ্য)

  • IP হার্ডকোড করবেন না — সর্বদা service discovery (Kubernetes DNS/Consul) ব্যবহার করুন; registry redundant ও consistent রাখুন।
  • API Gateway পাতলা (thin) ও redundant রাখুন — ব্যবসায়িক লজিক সার্ভিসে, gateway-তে নয়।
  • BFF শুধু তখনই যখন client প্রয়োজন সত্যিই ভিন্ন — অপ্রয়োজনে বহু BFF এড়ান।
  • microservices-এ atomicity দরকার হলে SAGA ব্যবহার করুন (2PC নয়); compensating transaction ডিজাইন করুন ও সব step idempotent করুন।
  • SAGA state durable রাখুন ও Orchestration-এ Temporal/Step Functions-এর মতো প্রমাণিত টুল বিবেচনা করুন।
  • CQRS শুধু যেখানে read/write চাহিদা সত্যিই খুব ভিন্ন বা scale খুব বেশি; সরল CRUD-এ নয়।
  • CQRS/SAGA-তে eventual consistency-র প্রভাব UI ও ব্যবসায় স্পষ্টভাবে সামলান।
  • সব প্যাটার্নের ট্রেড-অফ বুঝে যোগ করুন, trend হিসেবে নয়; সব কিছু monitor করুন।

১১. অধ্যায় সারসংক্ষেপ (Chapter Summary)

মূল শেখা:
- Service Discovery = সার্ভিসরা রানটাইমে একে অপরের অবস্থান খুঁজে পায়; client-side vs server-side; service registry + heartbeat; Consul/etcd/Kubernetes DNS।
- API Gateway = একক প্রবেশদ্বার; routing, auth, rate limit, aggregation, protocol translation; redundant ও thin রাখতে হয়।
- BFF = প্রতি client-টাইপের জন্য আলাদা, অপ্টিমাইজড gateway; ভিন্ন client প্রয়োজনে উপযোগী।
- SAGA = distributed transaction-কে লোকাল transaction-এর ক্রমে ভাগ; ব্যর্থতায় compensating transaction; Choreography (বিকেন্দ্রীভূত) vs Orchestration (কেন্দ্রীভূত); eventual consistency।
- CQRS = read ও write-এর আলাদা মডেল/স্টোর; স্বাধীন scaling ও অপ্টিমাইজেশন; eventual consistency; বিশেষায়িত প্যাটার্ন (সর্বত্র নয়); প্রায়ই Event Sourcing-এর সাথে।

গুরুত্বপূর্ণ পরিভাষা: Service Discovery, Service Registry, Client/Server-Side Discovery, Self/Third-Party Registration, Heartbeat, API Gateway, Cross-Cutting Concern, Request Aggregation, Protocol Translation, BFF, SAGA, Compensating Transaction, Choreography, Orchestration, Orchestrator, CQRS, Command, Query, Write/Read Model, Denormalized, Eventual Consistency, Event Sourcing।

Interview Challenge:
